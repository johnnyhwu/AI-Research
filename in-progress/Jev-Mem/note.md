# Jev-Mem 論文筆記

Nov 4, 2026 · @YHHW

**論文:** Jev-Mem: System-One-Controlled Agentic Memory for Efficient AI Agents(Jiang, Li, Li;UT Dallas) **arXiv:** [2609.23986](https://arxiv.org/abs/2609.23986) · **程式碼:** [libingzheren/Jev-Mem](https://github.com/libingzheren/Jev-Mem)

## 三十秒版本

**Jev-Mem 把 agent 記憶系統裡所有「要做判斷」的步驟,交給只輸出 0 到 1 分數的小模型 Jev;大 LLM 只在最後寫答案。**

記憶 = 一句話一個節點 + 四種邊(語意、時間、因果、實體)。

- **寫入:** 規則先挑出最多 10 個舊記憶當候選,Jev 只判斷這幾對要不要建語意邊、因果邊;實體邊與時間邊由規則直接建立。
- **讀取:** Jev 先替問題訂搜尋計畫(走哪幾種邊、每種能看幾個鄰居、最多幾層),再從錨點逐輪往外找:每輪 Jev 打分、只留前 10 名,並判斷證據夠了沒。

在 LoCoMo 上,和同架構的前作 MAGMA 相比:建構時間快約 9 倍,查詢延遲少 37%,總分 0.700 → 0.777,提升主要來自對抗題。

最值得帶走的通用技巧是 **RRF**:合併多份檢索結果時,只看名次、不看分數。

## 問題:記憶系統裡的高頻小判斷

agent 記憶系統每寫入一句、每回答一題,都要做好幾個判斷:這句是哪種記憶、跟誰有關、該去哪找、找到的夠不夠、哪個最有用。這些判斷的答案都是「是 / 否」或一個分數,不是一段文字。現有系統不是用寫死的規則(快但死板),就是讓大 LLM 逐字生成再解析(懂語意但慢、貴),而且這些判斷位在使用者要等的那條路上。

論文要回答三個問題:① 小模型怎麼貫穿寫入與讀取;② 弱模型控制記憶會不會拖累最終準確度;③ 什麼記憶結構與檢索流程適合這種輕量控制。

## 方法全貌

**系統分三層:Jev 做所有判斷(System One),中間是共用的記憶,大 LLM 只寫最後的答案(System Two)。** 名稱借自認知心理學的雙歷程理論,這裡只取「快的直覺判斷 vs. 慢的深思」這層比喻。

&#91;embedded content: 方法全貌 · 寫入 5 步、讀取 5 步加迴圈\]

左欄每寫入一句,最多 2 次 Jev 呼叫。右欄每一輪最多 2 次(停止判斷、打分);打分完繞回「證據夠了嗎?」形成迴圈,夠了才沿中間那條線交給 System Two。

**Jev 的介面:一份狀態 + 一批是非題。** 每道是非題(論文稱 Noul)由一句指令、true 條件、false 條件組成,回傳 \[0, 1\] 的分數;只能選一個的情況改用選擇題(Choice),回傳選項與分布。同一份狀態的多道題一次問完,不生成文字,也就不需要解析。實際輸入範例見【概念 7】。

- 正文把這些分數叫「機率」,但附錄 B.1 明說它們不保證經過校準。所以後文的 0.60、0.95 等門檻都是工程設定,不能讀成「有 60% 把握」。

## 記憶結構:節點與四種邊

**一句話一個節點,只存一份;節點之間有四種邊,同一對節點可以同時有好幾種。** 邊的用途:索引找到一條記憶後,沿著邊把相關的記憶一起帶出來。

&#91;embedded content: 為什麼需要邊 · 論文附錄 B 的例子\]

問題和 m2 很像,索引直接命中;m1 是沿著寫入時建好的因果邊、實體邊帶出來的。

- 推論:因果邊只在「文字裡看得出因果」時才會建立(見【概念 4】),而明講因果的句子通常會提到同一件事,本來就容易被相似度找到。所以邊的價值主要是「把前因後果一起帶出」,而不是「找到相似度完全找不到的句子」。

**一筆觀察**(式 4):

```latex
o_t = (x_t,\ \tau_t,\ \mu_t)
```

x\_t 是內容;τ\_t 是時間戳,記的是「這句話被說出的時間」,不一定是事件時間(m2 的購買其實發生在 5/15);μ\_t 是來源,具體欄位論文未說明。節點另外存 embedding、實體清單與四個類型分數。

**整份記憶**(式 5、6):

```latex
\mathcal{M}_t = \big(V_t,\ \{E^g_t\}_{g\in\mathcal{G}},\ I^{\text{vec}}_t,\ I^{\text{lex}}_t\big),\quad \mathcal{G}=\{\text{semantic},\ \text{temporal},\ \text{causal},\ \text{entity}\}
```

V\_t 是節點清單;E^g\_t 是第 g 種邊的清單,四種各一份;I^vec、I^lex 是向量索引與關鍵字索引,是讀取時的入口。用 CS 的話說:一組節點,搭配四份鄰接串列(每種關係一份),再加兩個索引。

| 邊 | 意思 | 怎麼建 |
| --- | --- | --- |
| 語意 | 兩句在講同一個具體主題或事實 | Jev 判斷 |
| 因果 | 一句導致或解釋另一句,有方向 | Jev 判斷,正反兩個方向各問一題 |
| 實體 | 提到同一個對象 | 名稱相同用規則;寫法不同才問 Jev |
| 時間 | 時間上相鄰,不代表有關係 | 規則(依程式碼) |

實體邊與語意邊的差別見【概念 1】;實體怎麼抽、時間邊怎麼連見【概念 3】。

## 寫入路徑

**每來一句話:全部收下 → 打類型分數 → 規則挑最多 10 個候選 → 判斷並建邊。每句最多 2 次 Jev 呼叫,不隨記憶庫變大而增加。** 對應總覽圖左欄。

1. **全部收下。** 附錄設定關閉了「要不要存」的過濾,所有非空的句子都會成為節點。理由:有些話當下不重要,之後的問題才顯示它有用。「挑選」被移到建邊與讀取兩處,所以 Jev 判斷錯頂多少一條邊,原句還在。
2. **打類型分數**(第 1 次 Jev 呼叫,式 7):四題一次問完。名稱借自認知心理學的記憶分類,這裡只是四個是非題標籤,可以同時都高。這裡的 semantic 指「一般性事實」,和語意邊無關。分數算了但後續沒有用到,見【概念 2】。

```latex
t(v) = \big(t_{\text{episodic}},\ t_{\text{semantic}},\ t_{\text{procedural}},\ t_{\text{preference}}\big)
```

3. **挑候選**(規則,式 8):用便宜的訊號替所有舊記憶打粗分,取前 K\_w = 10 名。這是「先粗篩、再精排」的兩段式,讓每句的 Jev 成本固定。代價:粗篩沒選上的舊記憶永遠建不了邊。

```latex
C(v) = \operatorname{TopK}_{u\in V_t}\ s_{\text{cand}}(v,u)
```

- 依程式碼:s\_cand = 2 × 向量相似 + 共同實體 2 分 + 關鍵字重疊比例 + 0.25 ÷ (1 + 相差天數)。只要同一個說話者,就會因共同實體拿到同樣的 +2。

4. **判斷並建邊**(第 2 次 Jev 呼叫,式 9):新記憶與 10 個候選之間的語意、雙向因果(必要時加實體別名)合成一次問完,分數 ≥ 0.60 才建邊;實體名稱相同與時間相鄰則由規則直接建。完整條件見【概念 4】。

```latex
P(g \mid v, u) \ge \theta_{\text{rel}} = 0.60
```

**定期整理:** 每 20 次寫入,只針對第 20 句和它的候選,判斷是否重複、矛盾、過時、值得補連結,並在「分開 / 合併 / 歸納 / 不確定」中選一個。原句一律保留;只有合併或歸納的分數 ≥ 0.85、矛盾 < 0.85,且有提供摘要器時,才請 LLM 寫出新條目。疑問見【概念 5】。

## 讀取一:搜尋計畫(路由、預算、深度)

**往外找之前,Jev 只看問題,一次決定三件事:開哪幾種邊、每種邊能看幾個鄰居、最多走幾層。**

&#91;embedded content: 搜尋計畫 · 自編分數,票數依式 13、14\]

由上往下就是計畫的產生過程:第三排是路由的產出,第四排是預算的產出,最後一排是深度。

**路由**(式 12):各種邊的需求分數 ≥ 0.10 就開啟。每種邊各自判斷,所以「何時 + 為何」可以同時開時間與因果(多標籤);作者前作 MAGMA 則是只能選一類的單標籤意圖(WHY / WHEN)。「喜歡吃什麼」這類題,時間與因果的需求可能只有 0.05,就不走這兩種邊。

```latex
p_g(q) \ge \theta_{\text{act}} = 0.10
```

**預算**(式 13、14):總共 80 張「看鄰居的票」,每種開啟的邊保底 1 張,剩下的按需求分數比例分。理由:時間邊、實體邊由規則建立、連得很密,不分疊的話會淹沒稀疏但關鍵的因果邊。扣票規則見【概念 6】。

```latex
b_g = m + \operatorname{LRound}_g\Big[(B - m\,|A|)\cdot \frac{p_g^{\gamma}}{\sum_{j\in A} p_j^{\gamma}}\Big]
```

B = 80 總票數;A 是開啟的邊,|A| 是種數;m = 1 保底;γ = 1 表示單純照比例,大於 1 會更集中給高分的邊;LRound 是最大餘數取整:先捨去小數,差幾張就給小數最大的邊,總數剛好等於 B。

自編例子(分數總和 2.85;保底後剩 80 − 4 = 76 張):

| 邊 | 分數 | 76 × 分數 ÷ 2.85 | 捨去小數 | 補差額 | 加保底 |
| --- | --- | --- | --- | --- | --- |
| 語意 | 0.50 | 13.33 | 13 | 0 | 14 |
| 時間 | 0.90 | 24.00 | 24 | 0 | 25 |
| 因果 | 0.85 | 22.67 | 22 | +1 | 24 |
| 實體 | 0.60 | 16.00 | 16 | 0 | 17 |

**深度**(式 15):層數 = 8 × 多跳需求,無條件進位後夾在 1 到 8 之間。例:0.05 → 1 層;0.40 → 4 層;1.00 → 8 層。這是上限,停止判斷或票用完都會提早結束。

```latex
D(q) = \min\Big\{D_{\max},\ \max\big(1,\ \lceil D_{\max}\, h(q)\rceil\big)\Big\},\quad D_{\max} = 8
```

## 讀取二:錨點、逐輪展開、打分

**從錨點出發,每一輪「沿邊找鄰居 → Jev 打分 → 只留前 10 名」,重複到該停為止。** 對應總覽圖右欄的迴圈。

**錨點**(式 16):向量索引與關鍵字索引各給一份排名,用 RRF 合併(只看名次,κ = 60,原理見「值得帶走」),排最前的成為錨點,也就是起始證據。依程式碼最多取 30 個。

**一輪做什麼:**

1. 先做停止判斷(下一節);夠了就停。
2. 從「前線」(上一輪新加入的節點)沿已開啟的邊找還沒找到的鄰居,每走一條連結撕一張該種邊的票。同一個鄰居被多條連結碰到時只保留一筆。
3. 一次 Jev 呼叫,替所有鄰居各打 4 個分數(輸入見【概念 7】)。
4. 合成總分,排序後取前 10 名(束寬,beam)加入證據,成為新前線。

停下後,證據依總分取前 K 條交給 System Two;論文未寫 K,依程式碼為 40。

**打分公式**(式 23):

```latex
s(v \mid q, E_d) = \frac{1}{\sum_{i=1}^{5}\lambda_i}\Big[\lambda_1 z_v + \lambda_2 a_v + \lambda_3\, p_g(q)\,\ell_v + \lambda_4 n_v + \lambda_5 \tfrac{\pi_e + c_v}{2}\Big]
```

| 符號 | 意思 | 誰算的 |
| --- | --- | --- |
| z | 問題與鄰居的向量相似度 | 規則 |
| a | 鄰居含有回答需要的事實嗎 | Jev |
| p | 走過來那種邊的需求分數(路由時算好) | Jev(路由) |
| ℓ | 走過來的這條連結有用嗎 | Jev |
| n | 帶來證據裡沒有的新資訊嗎 | Jev |
| π | 寫入時存在這條邊上的分數(見【概念 4】) | 寫入時存下 |
| c | 能支持現有證據嗎 | Jev |
| λ1 到 λ5 | 依程式碼為 0.25、0.35、0.15、0.15、0.10,合計 1;論文未給 | 設定 |

自編例子(延續「何時買、為何買」;B 沿因果邊走來,C 沿時間邊走來、只是相鄰的閒聊):

| 項目(權重) | B 小分數 | B 加權 | C 小分數 | C 加權 |
| --- | --- | --- | --- | --- |
| z(0.25) | 0.60 | 0.150 | 0.55 | 0.138 |
| a(0.35) | 0.90 | 0.315 | 0.20 | 0.070 |
| p × ℓ(0.15) | 0.85 × 0.80 | 0.102 | 0.90 × 0.30 | 0.041 |
| n(0.15) | 0.70 | 0.105 | 0.60 | 0.090 |
| (π + c) ÷ 2(0.10) | (0.90 + 0.80) ÷ 2 | 0.085 | (0.50 + 0.30) ÷ 2 | 0.040 |
| 總分 |  | 0.757 |  | 0.378 |

差距主要來自權重最高的 a;路由的需求分數 p 也在這裡乘進總分。

**近期調整**(式 24、25):問題在意新舊時(路由算出的 r 高),替較新的鄰居輕推一下。新鮮度 ρ = 1 ÷ (1 + 比基準早幾天),基準 τ\* 論文未定義,依程式碼是「目前證據中最新的時間」。新鮮度的權重是 0.1 × r,最多約占 9%,只是輕推。

```latex
s_e(v) = \frac{s(v) + 0.1\,r(q)\,\rho_v}{1 + 0.1\,r(q)}
```

- 推論(依設定檔數字):錨點最多 30、證據上限 60、每輪最多加 10,所以錨點填滿時最多只能展開約 3 輪;式 15 的 8 層上限在這份設定下實際上走不到。

## 讀取三:何時停止

**每輪開始前,Jev 看問題與手上的證據打四個分數;「證據夠了」或「再找也沒用」就停,否則繼續展開。** 第一次檢查發生在任何展開之前,錨點本身夠用就完全不走邊。

&#91;embedded content: 停止判斷 · 式 17 到 22 與附錄 B.5 的上限\]

由上往下依序檢查,右邊三個綠框是三種停法;三關都沒停,才回到上一節的一輪展開。

四個分數(式 17 到 20,第 d 輪):s 證據足夠(每個需要的事實都有記憶支持);u 再找一輪可能補到缺口或解決矛盾;m 仍缺必要證據;c 有未解決的矛盾。

```latex
s_d \ge \theta_{\text{suff}}\ \wedge\ m_d < \theta_{\text{cont}}\ \wedge\ c_d < \theta_{\text{cont}} \ \Rightarrow\ \text{停:夠了};\qquad u_d < \theta_{\text{cont}} \ \Rightarrow\ \text{停:沒用}
```

θ\_suff = 0.95,θ\_cont = 0.15(三處共用)。兩條規則互補:第一條防「找太少」,第二條防「找不停」,避免越找越多干擾。u 怎麼在看不到下一輪的情況下判斷,見【概念 8】。

自編例子:

| 時點 | s | m | c | u | 結果 |
| --- | --- | --- | --- | --- | --- |
| 第 0 輪(只有「舊車壞了」) | 0.60 | 0.70 | 0.00 | 0.80 | 不夠、值得找 → 展開 |
| 第 1 輪(加入「買了新車」) | 0.97 | 0.05 | 0.02 | 0.10 | 停:夠了 |
| 另一種第 1 輪(找來的都不相關) | 0.70 | 0.40 | 0.00 | 0.10 | 停:沒用 |

上限(附錄 B.5):深度 8、節點 60、檢查過的邊 2400、Jev 呼叫 16 次、15 秒,以及四疊票全部用完。時間類問題送給 Jev 的證據,會標明時間戳是「被說出的時間」並附上句中的時間詞,避免把對話日期當成事件日期。

## 實驗

**和同架構的前作 MAGMA 相比,建構快約 8.9 倍、查詢延遲少 37%,總分 +0.077;準確度的提升大半來自對抗題。** 全文只有兩張表,沒有消融實驗,只報告 LoCoMo 一個測驗集,回答模型為 gpt-4o-mini。

- **Table 1**:「Performance on the LoCoMo benchmark evaluated using the LLM-as-a-Judge metric. Higher scores indicate better performance. LLM model is based on gpt-4o-mini.」
- **Table 2**:「System efficiency comparison with total memory build time (in seconds) and average query latency (in seconds).」

**指標:** LoCoMo 是超長、多場次的對話記憶測驗集,題目分五類;其中對抗題問的是對話裡沒說過的事,正確做法是回答不知道(題型說明屬一般知識,論文未解釋)。LLM-as-a-Judge 讓另一個 LLM 判斷答案是否與標準答案一致,測的是**最終答案**,不單獨評檢索。建構時間 = 把整段對話存成記憶的總秒數;查詢延遲 = 每題從檢索到回答的平均秒數。

## 值得帶走:RRF(倒數名次融合)

**要把好幾份檢索結果合成一份時,不看各自的分數,只看名次:每份清單按名次給一點分,加總後重排。**

**解決的問題:** 不同檢索器的分數尺度不同——向量給 0 到 1 的相似度,關鍵字(如 BM25)可以是 0 到幾十。直接相加,尺度大的那一路會壓倒另一路;名次則永遠是 1、2、3…,天生可比。

```latex
\text{RRF}(d) = \sum_{r \in R,\ d \in r} \frac{1}{k + \text{rank}_r(d)},\qquad k = 60
```

d 是一筆候選;R 是所有結果清單,只加 d 有出現的那幾份;rank 從 1 開始;沒出現在某份清單 = 那份貢獻 0。

**為什麼有效:** 只用名次,所以不受分數尺度與分布影響,不需正規化、不需訓練;取倒數,越前面貢獻越多,排很後面趨近於零;k 讓前幾名的差距變小:

&#91;embedded content: 由公式 1/(k + 名次) 計算 · 名次 1 到 10\]

k = 0 時,第 2 名只剩第 1 名的一半,第 1 名獨大;k = 60 時,前 10 名幾乎一樣。所以 k = 60 的效果是:**在幾份清單裡都排前面,比在一份清單裡拿第 1 更值錢。**

自編例子:X 只在向量清單排第 1;Y 在兩份清單都排第 2。

| k | X | Y | 誰贏 |
| --- | --- | --- | --- |
| 0 | 1/1 = 1.000 | 1/2 + 1/2 = 1.000 | 平手 |
| 60 | 1/61 = 0.0164 | 1/62 + 1/62 = 0.0323 | Y,約為 X 的兩倍 |

**怎麼用:** 適用於向量加關鍵字的混合檢索、同一問題改寫成多個版本分別檢索後合併、多個 embedding 模型的結果合併。每一路先取前 N 名再融合,名次從 1 算起。

```python
def rrf(result_lists, k=60):
    scores = {}
    for results in result_lists:            # 每一份檢索結果
        for rank, doc_id in enumerate(results, start=1):
            scores[doc_id] = scores.get(doc_id, 0) + 1 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)
```

**代價:** 丟掉分數大小的資訊——某一路的第 1 名「極度相關」或「勉強相關」,在 RRF 裡看起來一樣。

來源(一般知識,不是論文內容):Cormack、Clarke、Büttcher 於 2009 年 SIGIR 提出,k = 60 是原論文的建議值。Jev-Mem 用它合併向量與關鍵字索引的結果來選錨點(式 16)。

## 【概念 1】實體邊與語意邊的差別

**實體邊問「兩句有沒有提到同一個對象」,語意邊問「兩句是不是在講同一件具體的事」。** 兩者獨立,最容易混淆的是 ② 與 ③。

&#91;embedded content: 實體邊 vs 語意邊 · 四種組合,自編例子\]

|  | 實體邊 | 語意邊 |
| --- | --- | --- |
| 怎麼建 | 實體名稱完全相同 → 規則直接建;寫法不同才問 Jev「是否同一個對象」 | 每一對都問 Jev |
| false 條件 | 沒有共同對象 | 只共用一般對話用語,沒有具體共同主題 |

哪些字算「實體」論文未說明;附錄例子把 Mira 與 bicycle 都列為實體,但依程式碼實際只抓得到大寫開頭的字(見【概念 3】)。

## 【概念 2】類型分數:有沒有用到?能不能拿來篩候選?

**類型分數有算、有存,但在找候選、判斷關係、讀取打分三處都沒有被使用;它適合當加分,不適合當篩選門檻。**

**有沒有用到**(依程式碼):

| 環節 | 用到類型分數嗎 | 依據 |
| --- | --- | --- |
| 寫入:挑候選 | 否 | 粗篩只算向量、共同實體、關鍵字、時間 |
| 寫入:判斷關係 / 讀取:路由、打分、停止 | 否 | 送給 Jev 的節點只有 id、內容、時間、實體 |
| 讀取:總分公式(式 23) | 否 | 五個分量都沒有類型 |
| 交給 System Two 的內容、定期整理 | 未確認 | 未檢視這兩段程式碼 |

論文只說分數「標注在節點上」。推論:它是預留欄位;代價是每次寫入的兩次 Jev 呼叫中,有一次的產出沒有影響後續結果。

**能不能只跟同類型的舊記憶比?** 不建議當硬門檻,原因有三:

- **會漏掉跨類型的關係。** 自編例子:「我討厭塞車」(喜好)與「我改騎腳踏車上班了」(事件)之間有一條有價值的因果邊,同類型篩選會讓這對永遠不被比較。
- **類型是分數不是標籤。** 一句話可以同時是事件與喜好,「同類型」需要另訂門檻。
- **粗篩的目標是不漏。** 粗篩沒選上的永遠建不了邊,再加硬過濾只會漏更多。

| 做法 | 效果 | 風險 |
| --- | --- | --- |
| 論文:不看類型 | 不會因類型漏掉 | 類型分數空轉 |
| 同類型才比 | 候選更集中 | 跨類型的因果、喜好關係全漏 |
| 同類型加一點分 | 同類型優先,跨類型仍有機會 | 加分幅度需要調 |

## 【概念 3】實體怎麼抽?時間邊會不會連到無關的句子?

**實體與時間邊都是便宜的固定規則,而且連得很寬:實體邊大致等於「同一個說話者」,時間邊等於「時間相鄰」。** 論文兩者都沒寫清楚,以下依程式碼。

**實體抽取:** 不是 Jev,也不是 LLM,而是正則規則——抓大寫開頭、長度大於 2、不在常見字清單裡的字,加上「I'm X」句型,最多 5 個;呼叫方自備實體清單時改用那份,但 LoCoMo 的跑法沒有自備。

- 每句存成「\[Mira\]: …」,說話者名字一定被抓到,所以同一個說話者的句子之間幾乎都有實體邊(仍限於 10 個候選之內)。
- 小寫的 bicycle 抓不到;句首大寫的字會被誤抓。自編例:「\[Mira\]: Yesterday I went to Paris.」抽出 Mira、Yesterday、Paris。

**時間邊:** 會連到無關的句子。規則不看內容,也不受 10 個候選限制。

&#91;embedded content: 時間邊的兩條規則 · 依程式碼\]

在 LoCoMo 上更明顯:同一場對話的每句話時間戳都是同一個場次日期,時間差為 0,新句子幾乎一定連到前 9 句。所以時間邊的意思是「時間上靠近」,用來排時間線、找上下文;要不要走由路由決定,走到的句子還要經過 Jev 打分才會留下。論文正文那句「時間戳先後直接建時間關係」太籠統:相差兩天、又不是緊鄰的兩句,不會有時間邊。

## 【概念 4】建邊條件總整理,以及邊分數 π

**語意、因果、實體別名問 Jev,只在新記憶與 10 個候選之間,門檻 0.60;實體名稱相同與時間相鄰用規則。每條邊建立時都存下一個分數 π,讀取打分時再用。** 依附錄 B.2 與程式碼。

**第 0 步:候選資格**(只影響語意、因果、實體邊)——粗篩分數 = 2 × 向量相似(只加給向量搜尋前 10 名)+ 共同實體 2 分 + 關鍵字重疊比例(最多 1)+ 0.25 ÷ (1 + 相差天數),取前 10 名。

| 邊 | 要是候選嗎 | 誰判斷 | 建立條件 | 方向 | 存下的 π |
| --- | --- | --- | --- | --- | --- |
| 語意 | 要 | Jev | 「兩句在講同一個具體主題」≥ 0.60 | 新 → 候選 | Jev 當時的分數(0.60 到 1) |
| 因果:候選導致新 | 要 | Jev | ≥ 0.60,且文字本身要支持因果;只是先後、同一人說的不算 | 候選 → 新 | 同上 |
| 因果:新導致候選 | 要 | Jev | 同上,另問一題 | 新 → 候選 | 同上 |
| 實體:名稱相同 | 要 | 規則 | 實體清單有任一個完全相同 | 新 → 候選 | 固定 1.0 |
| 實體:別名 | 要 | Jev | 沒有任何相同實體時才問「是否同一對象」,≥ 0.60 | 新 → 候選 | Jev 當時的分數 |
| 時間:序列 | 不用 | 規則 | 同一份對話裡緊鄰的前一句 | 雙向各一條 | 讀取時補 0.5 |
| 時間:鄰近 | 不用 | 規則 | 往前最多 9 句,且時間差 ≤ 24 小時 | 舊 → 新 | 讀取時補 0.5 |

- 推論:因果邊只抓得到「文字裡看得出來」的因果,不會替兩句話推理出隱藏的原因。
- 時間的鄰近邊其實存了「越近越大」的權重,但讀取程式讀的是另一個欄位名稱,讀不到就一律補 0.5。結果在打分第五項上,實體邊(1.0)永遠比時間邊(0.5)多 0.25,再乘權重 0.10。

**π 怎麼走到讀取端(論文例子,分數自編):** 寫入 m2 時,Jev 給「m1 導致 m2」0.90 ≥ 0.60,建因果邊並存下 0.90。讀取時從 m1 沿這條邊走到 m2,打分公式第五項的 π 就是 0.90。

## 【概念 5】定期整理為什麼只檢查第 20 句

**論文沒有解釋為什麼是 20,也沒說為什麼只檢查一句;程式碼的做法是每第 20、40、60… 次寫入,只檢查那一句和它的候選。**

附錄原文只說「每成功寫入 20 次,評估一次候選配對」,有兩種讀法,文字無法判定:

| 讀法 | 檢查範圍 | 每句平均額外成本 |
| --- | --- | --- |
| A(程式碼的做法) | 只檢查第 20 句與它的候選 | 約 0.05 次 Jev 呼叫 |
| B | 這 20 句都檢查 | 約 1 次 Jev 呼叫 |

- 推論:降頻是為了成本。每句都做的話,寫入的 Jev 呼叫會從最多 2 次變 3 次,而寫入速度正是本文主打的賣點。
- 依讀法 A,實際被整理到的大約只有 1/20 的句子,而且是哪些句子取決於寫入順序,不是挑最需要整理的。
- 論文沒有「關掉整理」的對照實驗,也沒說實驗時有沒有提供摘要器,所以這個機制對準確度的貢獻未知。

## 【概念 6】預算:80 是不是超參數?多種邊時怎麼扣票?

**80 是人為設定的固定超參數,論文沒說怎麼選、也沒做敏感度實驗;票只在「從已找到的節點走向還沒找到的節點」時扣,而且按連結數扣。**

**80 數的是什麼:** 「最多提出 80 個候選鄰居」,跨所有回合共用,不是 80 條邊,也不是 Jev 呼叫次數;另有「最多檢查 2400 條邊」的獨立上限。依程式碼,附錄的數字與設定檔 `jev_mem.json` 一致,但程式內建預設值不同:

| 參數 | 附錄 / jev\_mem.json | 程式碼內建預設 |
| --- | --- | --- |
| 總預算 B | 80 | 20 |
| 集中程度 γ | 1.0 | 1.5 |
| 啟動門檻 | 0.10 | 0.15 |
| 最大層數 | 8 | 5 |

repo 另有一份 `jev_mem_accuracy.json`(預算同為 80,其他門檻不同);Table 1、2 用哪一份跑,論文未說明。推論:80 不隨記憶庫大小調整,搬到更大的記憶庫時這是第一個要重調的數字。

**扣票規則:** 從前線節點列出它的所有連結(出去與進來的都列),一條一條檢查:對方已經找到 → 跳過不扣;這種邊的票用完 → 跳過;否則扣該種邊 1 張,對方放進待打分清單(放進清單不算「找到」)。

&#91;embedded content: 扣票規則 · 自編例子,規則依程式碼\]

四條連結都指向 B,待打分清單只留一筆(保留分數最高的那條連結),但票已經照連結數扣掉。對照:若 B 一開始也是錨點,四條全部跳過,一張票都不扣。

- 推論:這解釋了時間票為什麼總是最快用完——時間邊本來就密,相鄰兩句之間又常有 2 到 3 條時間連結,每看一個時間鄰居就可能吃掉好幾張票。

## 【概念 7】Jev 的輸入長什麼樣子,以及層數為什麼也被輸入

**每次呼叫 = 一份共用的「狀態」+ 一批題目,每題的指令裡直接寫出要看狀態的哪個欄位,回傳每題一個數字。** 類比:閱讀測驗——一篇文章配好幾題,每題註明「請看第幾段」。附錄 B.1 說明題目編號只是記帳用,模型看不到,所以位置必須寫在指令裡。

**候選打分的一次呼叫**(論文附錄 B.4 的例子:證據裡已有 m1,沿因果邊走到 m2;結構依程式碼,數值自編):

```json
{
  "query": "When did Mira buy a new bicycle, and why?",
  "evidence": [
    {"id": "m1", "content": "Mira: My old bicycle broke.",
     "timestamp": "2024-05-14 10:00", "entities": ["Mira"]}
  ],
  "candidates": [
    {"id": "m2",
     "content": "Mira: I bought a new bicycle yesterday because my old one broke.",
     "timestamp": "2024-05-16 10:00", "entities": ["Mira"],
     "graph": "causal", "source_id": "m1", "target_id": "m2",
     "relation": {"sub_type": "caused_by", "probability": 0.9}}
  ]
}
```

| 題目 | 指令(中譯) | 用到的欄位 | Jev 回答(自編) |
| --- | --- | --- | --- |
| candidate\_0\_relevance(a) | candidates\[0\].content 有沒有回答 query 需要的事實? | 問題 + 鄰居內容 | 0.93 |
| candidate\_0\_relation\_usefulness(ℓ) | 這條邊(種類與方向)有沒有把 evidence 連到對 query 有用的資訊? | 問題 + 連結資訊 + 證據 | 0.88 |
| candidate\_0\_new\_information(n) | 有沒有 evidence 裡沒有、跟回答有關的細節? | 問題 + 鄰居內容 + 證據 | 0.81 |
| candidate\_0\_supports\_current\_evidence(c) | 能不能獨立佐證 evidence 裡跟 query 有關的說法? | 問題 + 鄰居內容 + 證據 | 0.74 |

鄰居有多個時,candidates 清單變長,題目變成 candidate\_1\_…、candidate\_2\_…,仍是一次送出、一次拿回。只有 a 是「問題 vs 鄰居」,其餘三題都拿鄰居對照現有證據,所以同一個鄰居在證據不同時會拿到不同分數。

**讀取時三次呼叫各看什麼:**

| 呼叫 | 輸入 |
| --- | --- |
| 路由 | 只有問題 |
| 候選打分 | 問題 + 前 40 條證據 + 這一輪所有鄰居 |
| 停止判斷 | 問題 + 前 40 條證據 + 目前層數 |

**層數為什麼也被輸入:論文未說明。** 它確實在停止判斷的狀態裡,但四道停止題的指令都只指名 query 與 evidence,沒有一題要求看層數。兩種讀法無法判定:給 Jev 當背景、讓它在走深後傾向停止;或者只是記錄用、實際沒有作用。程式碼裡層數唯一明確影響判斷的地方,是 Jev 呼叫失敗時的預設答案(第 0 層預設「不夠」,之後預設「夠了」)。推論:「走多深」實際上由規則控制(層數上限與節點上限),不是 Jev。

## 【概念 8】Jev 怎麼判斷「值得繼續找」

**Jev 看不到下一輪的鄰居,只能根據「問題 + 手上的證據」判斷;所以這題實際在問「說得出還缺什麼嗎」,而不是「記憶庫裡找得到嗎」。** 附錄 B.5 的標準:true = 指得出具體缺少的事實或矛盾,而且更多記憶可能補上;false = 已沒有指得出的缺口,或更多記憶不太可能有幫助。

類比:偵探翻筆記。他不知道下一個房間有什麼,但看得出自己「知道兇手是誰、卻不知道動機」,於是判斷值得再搜;筆記已經完整、或根本說不出缺什麼,就不再搜。

自編例子(問題:何時買、為何買):
