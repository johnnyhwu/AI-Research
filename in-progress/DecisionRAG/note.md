# DecisionRAG：用決策模型沿樹導航的檢索

Nov 11, 2026 · @YHHW

## 30 秒版本

DecisionRAG（arXiv 2610.35868v1，Cornell / ASAPP）把檢索改成沿著語料樹往下走：每一層把所有候選寫進同一個 context，由決策模型（Jev 1.13）在一次 forward pass 內對每個候選回答「值不值得往下翻」，留下前幾名、剪掉其餘，最後對前幾段出一題多選一做重排。全程不生成 token，查詢時不需要第一階段檢索器。

- **準確度**：遠勝 BM25 與「向量檢索 + 8B reranker」；和最強的「向量檢索 + GPT-5 重排」大約打平。混入向量檢索候選的混合版在四個資料集上持平或小勝，而四個資料集的最佳成績都出自混合版，所以標題的「retriever-free」名不符實。
- **延遲**：同一棵樹上，把 GPT-5 的逐字生成換成決策模型的判斷，準確度相當，延遲快 34 到 145 倍。
- **兩個反直覺的結果**：通用決策模型當重排器，可以勝過專門訓練的 8B reranker；沿樹導航勝在「排得準」，而不是「找得全」。
- **最值得帶走的兩個通用概念**：多題共用一個 context 時，用「位置編號重疊 + 遮罩」消除題目順序偏差；樹狀導航的召回上限，由節點描述的品質決定。

## 追問索引

以下五個問題各自在文末獨立成節，不需要先讀完前文。

- **Q1**：每一輪判斷，模型的輸入和輸出到底長什麼樣？
- **Q2**：同一個 context 放越多候選，判斷品質會不會變差？
- **Q3**：notepad 是直接放進段落層嗎？
- **Q4**：位置編號是不是都當作接在 context 後面？
- **Q5**：主結果表為什麼看不到 BM25？

## 1 問題：檢索器跟不上生成模型

在 RAG 裡，決定生成模型能看到什麼的是檢索器，而檢索器遠比生成模型笨。檢索器漏掉的證據，生成模型再強也救不回來，論文稱之為**能力不對稱**（capability asymmetry）。

**例子**：查詢「Christopher Nolan 2000 年那部電影的主角是誰？」要先推出「Nolan 的 2000 年作品是 Memento」，才知道該去找 Memento 頁面中介紹主角 Leonard Shelby 的段落，而「Memento」這個詞根本不在查詢裡。BM25 只比字面，會把標題剛好含「2000」和「film」的 Gladiator (2000 film) 排在 Memento 前面；dense retrieval 把查詢和段落分開編碼，同樣沒有機會在讀過查詢後推理這一步。

> Figure 1（原 caption：「Capability asymmetry: a simple retriever bottlenecks a powerful LLM (a); decision models level the playing field (b).」）：簡單的檢索器成為強大 LLM 的瓶頸；以決策模型做檢索，讓兩邊能力拉平。Figure 2(a) 的 BM25 分數為示意。

**現有補救做法都卡在某一處**

| 做法 | 強模型參與判斷？ | 能找回第一階段漏掉的？ | 速度 |
| --- | --- | --- | --- |
| BM25／dense retrieval | 否 | 不適用 | 快 |
| 重排序（reranker） | 是，但只看第一階段的候選 | 否 | 中 |
| 生成式導航（LLM 逐步搜尋，或沿文件階層逐字寫出要保留的分支） | 是 | 是 | 慢 |
| DecisionRAG 想達成的 | 是 | 是 | 快 |

由此衍生三個挑戰，後文以編號引用：

- **C1 不依賴第一階段檢索器**：強模型要直接決定「看什麼」，而不只是重排。
- **C2 不能逐字生成**：每一步判斷都要快。
- **C3 規模**：語料可達數百萬段，不可能讓模型逐段讀過。

## 2 方法

離線先把語料整理成一棵樹；上線時，審查員（決策模型）在每一層對所有候選出是非題、只保留前幾名，到段落層保留前 r 段，最後對前 m 段出一題決選題。比喻就是在圖書館找資料：先看分區，再挑書，最後翻到段落。

上半部只建一次；下半部每個查詢都走一遍。強調框是審查員出題的地方：前兩個是是非題，最後一個是決選題；虛線框是可選的補救後門，把段落送回段落層。C1–C3 對應第 1 節的三個挑戰。

### 2.2 是非題：讀一次 context，同時回答 n 題

每個候選各自一題 yes／no，所有題目共用同一個 context，一次 forward pass 答完（論文 Equation 2）：

```latex
p_i^{\text{bin}} = P(\text{Yes} \mid s,\ Q_i)
```

- s：共享 context，即使用者問題加上所有候選的描述。
- Q\_i：第 i 題，例如「回答問題所需的資訊在頁面 i 裡嗎？」
- p\_i^bin：第 i 個候選的分數，用來排序與剪枝。

每題的機率只在自己的 yes 和 no 之間分配，所以跨題加總不必為 1。Figure 3a 的示意：Memento (film) 0.96、Christopher Nolan 0.81、Gladiator (2000 film) 0.07，加總 1.84。因為每題獨立，候選數只受 context 長度限制；一層太大時拆成多個平行請求，再合併分數排序。三輪判斷的完整輸入輸出範例見 **Q1**。

### 2.3 同一張桌子：分數為什麼能互相比較

題目之間彼此看不到，但所有候選都寫在同一個 context 裡，所以每一題都是在「看過全部對手」的條件下作答：有更好的候選在場，看起來還不錯的候選分數就會被壓低。

|  | 分開判斷：每個請求只放一段 | 一起判斷：同一個 context |
| --- | --- | --- |
| A：主角是 Leonard Shelby（真答案） | 0.85 | 0.93 |
| B：Nolan 的電影生涯（相關但無答案） | 0.88 | 0.30 |
| 排第一 | B（錯） | A（對） |

（表中數字為自編示意。）分開判斷時，兩個分數不是同一把尺量出來的，放在一起排序就會出錯。這不是數學保證：分數仍是各自的二選一，壓低對手的效果靠模型自己學會。論文 6.2 節把這個效果稱為 calibration（校準），用得比統計上的原意寬鬆，實際指「分數彼此可比」。

### 2.4 決選題：最後一步只排第一名

對前 m 段出唯一一題「哪一段最相關？」，所有候選搶同一份機率（Equation 3）：

```latex
p_i^{\text{mul}} = P(a_i \mid s,\ Q,\ \mathcal{A}), \qquad \sum_{i=1}^{m} p_i^{\text{mul}} = 1
```

- s：新的 context，只放問題和前 m 段；Q 是那一題；A = {a\_1, …, a\_m} 是 m 個段落選項。
- Figure 3b 示意：主角段落 0.91、「讓 Nolan 一舉成名」0.09。

|  | 是非題 | 決選題 |
| --- | --- | --- |
| 用在哪 | 每一層篩選 | 只在最後一步 |
| 目標 | 召回：不要漏 | 第一名排對 |
| 候選上限 | 只受 context 長度限制 | 最多 255 個選項（Jev 的限制） |
| 機率怎麼分 | 每題各自在 yes／no 間分 | 所有候選搶同一份 1 |

實際設定 m = 20（Natural Questions 為 5）；前 m 名照決選機率重排，其餘維持是非題排序；MTRAG 只把決選第一名提到最前面，原因論文未說明。

### 2.5 剪枝與預算

被剪掉的分支，這個查詢不會再看，因此每層預算刻意偏寬（用成本換召回），名額可以是固定的前 k 個，也可以是機率門檻。

### 2.6 補救剪錯的兩個後門

- **dense 候選**：另用向量檢索撈前 20 段（ConditionalQA 為 10 段），去重後依頁面與章節按閱讀順序併入段落層。用了它就需要事先建好的向量索引，系統不再是「無檢索器」，準確說法是「導航為主、向量檢索補漏」的混合版。
- **notepad**（只用在多輪對話資料集）：記錄最近幾輪中各自排第一的段落所屬的頁面，按「最近」排序，不按名次。在 MultiDoc2Dial 上，最近 2 個 notepad 頁面的所有段落直接加入段落層的是非題，不經頁面層篩選。它保證這些段落「能被看到」，不保證「會被選上」。細節見 **Q3**。

### 2.7 語料樹從哪來

每個節點都要有一段短描述，供審查員判斷：段落用內文，頁面用標題（有些資料集加章節標題），群用一句摘要。有現成結構就沿用，例如 metadata 欄位、HTML 的 h1／h2、網址路徑；樹不必處處一樣深，MTRAG 只替超過 60 段的長頁多插一層章節。沒有結構時（Wikipedia）先分群再寫描述，做法與原理見「值得帶走」第二點。查詢時不需要向量檢索，但建樹時可能用到 embedding 來分群。

### 2.8 自訓審查員：一次 forward pass 怎麼同時答多題

論文自訓的開源審查員（Appendix G）以 Qwen3-Base 為底，把輸出頭換成評分頭。輸入排法：每個候選一題，題後接「no」「yes」兩個選項，全部接在共享 context 之後；**每一題的位置編號都從 context 結束處起算，題目之間以 attention 遮罩互相隔開**。

> **重點（推論，論文未說明動機）**：位置重疊加遮罩，讓每一題在位置上對稱，消除了「題目排第幾」造成的偏差。但候選內容本身仍按順序寫在 context 裡，這部分的位置偏差沒有被消除，論文也沒有檢驗。機制細節見 **Q4**。

評分頭：取題目結尾 token 的向量 q，以及兩個選項結尾 token 的向量，算餘弦相似度乘上學到的溫度 τ（上限 100），再做 softmax：

```latex
P(\text{yes}) = \frac{\exp(\tau \cos(q, v_{\text{yes}}))}{\exp(\tau \cos(q, v_{\text{yes}})) + \exp(\tau \cos(q, v_{\text{no}}))}
```

例（數字自編）：cos(q, v\_yes) = 0.30、cos(q, v\_no) = 0.10、τ = 20，則 P(yes) = 1 / (1 + e^-4) ≈ 0.982。Jev 本身是否這樣做，論文未說明。

## 3 實驗：準確度與延遲

準確度和最強的「向量檢索 + GPT-5 重排」大約打平，混合版小勝；延遲快一個數量級，但成本只在小語料上佔優。

### 3.1 讀表需要的最少知識

| 資料集 | 內容 | 規模 | 每題正確段落數 |
| --- | --- | --- | --- |
| MultiDoc2Dial（MD2D） | 美國政府說明中心的多輪客服對話 | 413 頁、4,110 段；4,201 輪 | 1 |
| ConditionalQA（CQA） | 英國政府指南的情境題 | 652 頁、5.8 萬段；271 題 | 1–22 |
| MTRAG | IBM Cloud 技術文件的多輪對話 | 8,578 頁、7.2 萬段；188 輪 | 1–7 |
| Natural Questions（NQ） | 真實搜尋問題，答案在 Wikipedia | 10.9 萬頁、268 萬段；500 題 | 1–3 |

- **R@k（Recall@k）**：正確段落中有幾成出現在前 k 名，衡量「有沒有找回來」。MD2D 每題只有 1 個正確段落，所以它的 R@1 等於「第一名對不對」。
- **Hit@1**：第一名剛好是正確段落之一的題目比例，衡量「第一名排對沒有」，用在正確段落不只一個的資料集。
- 主指標：MD2D 看 R@1、CQA 看 Hit@1、MTRAG 看 R@5、NQ 看 Hit@1。
- MTRAG 的正確答案有一部分由 GPT-5 補標，而 GPT-5 也是被比較的 baseline，數字要打折看（Appendix A.3）。

### 3.3 提升來自導航，還是來自 Jev

論文 6.5 節讓 Jev 直接重排向量檢索前 100 段，打分方式與 DecisionRAG 最後一步完全相同，兩邊只差「候選從哪來」。CQA 與 NQ 可和 Table 2 用同一批題目串起來（Table 8 原 caption：「Jev reranking the dense top 100 versus DecisionRAG with dense candidates, both using the same dense index (%).」）。

| Hit@1（%） | Dense 前 100 + Qwen3-Reranker | Dense 前 100 + Jev 重排 | DecisionRAG + dense 候選 |
| --- | --- | --- | --- |
| CQA（271 題） | 64.6 | 65.7（+1.1） | 73.4（+7.7，95% CI \[2.6, 13.3\]） |
| NQ（500 題） | 48.0 | 59.4（+11.4） | 66.4（+7.0，95% CI \[3.4, 10.8\]） |

MD2D 與 MTRAG 上，導航與 Jev 重排持平（R@1 49.9 對 51.2，1,000 輪抽樣；R@5 38.3 對 38.7，官方原始標註）。四個資料集中有兩個，導航沒有額外貢獻。

> **重點一：Jev 重排勝過 Qwen3-Reranker。** 這打破的不是「檢索之後要重排」，而是「重排就該用專門訓練的 reranker」。兩者有兩個差別，論文沒有拆開：模型本身（通用決策模型 vs 專用 8B reranker），以及打分方式（100 段放進同一個 context 一起判斷再加決選題 vs 每對問題與段落各自打分）。幅度也依資料而異：NQ 差 11.4 點，CQA 只差 1.1 點。

> **重點二：導航勝在排得準，而不是找得全。** 向量檢索前 100 名其實更常包含正確段落（NQ 98.4% 對 94.0%；CQA 98.5% 對 91.1%），但在兩邊都包含正確段落的題目上，導航把它排第一的比例更高（NQ 70.1% 對 61.9%；CQA 76.7% 對 67.3%）。作者推測原因是導航把整頁段落按閱讀順序交給審查員，而向量檢索給的是來自不同頁面的零散段落；這個解釋沒有經過實驗驗證。

### 3.4 延遲與成本

取自 Table 5：延遲為每查詢中位數秒數，成本為每查詢 API 美分。DecisionRAG 計時只用了 48、50、24、100 個查詢（Table 15）。

|  | MD2D | CQA | MTRAG | NQ |
| --- | --- | --- | --- | --- |
| 延遲：Dense + Qwen3-Reranker | 7.5 | 3.3 | 14.3 | 5.8 |
| 延遲：Dense + GPT-5 重排 | 11.8 | 14.4 | 12.2 | 15.0 |
| 延遲：DecisionRAG | 0.68 | 0.82 | 1.76 | 1.73 |
| 成本：Dense + GPT-5 重排 | 1.40 | 1.20 | 1.90 | 1.40 |
| 成本：DecisionRAG | 0.22 | 0.29 | 1.73 | 2.33 |

這些倍數不是公平控制下的加速比（論文 Appendix F 自承），兩邊的部署條件不同：

|  | Qwen3-Reranker 那一列 | DecisionRAG 那一列 |
| --- | --- | --- |
| 模型 | 8B 專用 reranker | Jev 1.13，大小未公開 |
| 硬體 | 單張 RTX A6000，本機執行 | 供應商線上服務，硬體不明 |
| 平行度 | 100 段分批送進同一張 GPU | 每查詢最多同時 8 個請求 |

**保守結論**：在論文的測試條件下，「Jev API + 沿樹導航」端到端比「本機單卡 8B reranker」與「GPT-5 重排」快一個數量級；決策模型這一類模型本身是否比 reranker 快，這篇沒有證據。從結構看（推論），「同一張桌子」把所有段落串成一條長序列，attention 計算量隨長度平方成長，不一定比 cross-encoder 逐對打分省。成本方面，大語料時反而較貴：NQ 每查詢 2.33 美分，高於 GPT-5 重排的 1.40，因為頁面層要判斷約 17,500 個標題。Jev 1.13 只能透過 API 使用，改用自訓模型後的延遲與成本論文沒有測。

### 3.5 同一棵樹：用判斷 vs 用生成

論文 6.3 節保持樹與預算不變，只把審查員換成 GPT-5（低推理強度），讓它讀完一層後逐字寫出要保留的編號。兩邊都走 API，是全篇最乾淨的延遲比較（Table 6；CQA 271 題，NQ 只用前 100 題且無信賴區間）。

|  | Hit@1 | R@10 | 延遲（秒） | 成本（美分） |
| --- | --- | --- | --- | --- |
| CQA：GPT-5 生成式 | 73.8 | 73.6 | 28.2 | 6.1 |
| CQA：DecisionRAG | 69.7 | 71.9 | 0.82 | 0.29 |
| CQA：DecisionRAG + dense | 73.4 | 76.3 | 0.85 | 0.29 |
| NQ：GPT-5 生成式 | 59.0 | 82.5 | 250.8 | 57.2 |
| NQ：DecisionRAG | 65.0 | 86.5 | 1.73 | 2.33 |
| NQ：DecisionRAG + dense | 64.0 | 88.5 | 1.64 | 2.33 |

準確度互有勝負（CQA GPT-5 +4.1，NQ DecisionRAG +6.0），延遲差 34 到 145 倍，成本差 21 到 25 倍。NQ 上 GPT-5 每查詢超過 4 分鐘，因為它得先讀完整層再逐一寫出編號，分群層要選 150 個時還常常需要追問補齊。這是全篇最直接支持「決策模型適合做檢索決策」的證據。

## 4 值得帶走

兩個與這篇論文無關也成立的概念。

### 4.1 多題共用一個 context 的實作技巧

**適用情境**：一段很長的共同前綴，後面接 N 個彼此獨立的判斷，例如同一問題配 N 個候選段落、同一段文字的 N 個分類題、同一個 prompt 配 N 個回覆交給 reward model 打分。

**做法：兩個機制缺一不可**

1. 把前綴和 N 個分支串成一條序列。
2. 每個分支的位置編號，都從前綴結束處重新起算。
3. attention 遮罩：每個分支只看得到前綴和自己，看不到其他分支。

算出來的結果等同於「前綴 + 第 i 個分支」分開跑 N 次，但前綴只算一次。

**好處**：前綴計算共用；每個分支與前綴的相對距離相同，不會因為排第幾而被偏好或壓低。

**限制**

- 前綴內部的順序偏差還在：候選內容若寫在前綴裡，開頭和結尾的候選與分支的距離仍然不同。
- 需要能自己控制位置編號和遮罩，也就是開源權重；API 模型做不到。
- 前綴很長時，attention 計算量隨長度平方成長，省下的部分可能被抵消。

**相關做法**（一般知識）：推論框架的 prefix caching（如 vLLM）在請求間共用前綴計算，但不改位置編號；訓練時的 sequence packing 把多筆樣本串接並互相遮罩；speculative decoding 的 tree attention 讓多條候選路徑共用前綴。

### 4.2 樹狀導航的上限由節點描述決定

上層做決定時，審查員只看得到節點的短描述，看不到底下的內容。描述看不出某分支有答案，那個分支就被剪掉，而且救不回來。所以描述品質直接決定整個系統的召回上限（論文 Limitations 承認此點，但沒有量化）。

**沒有現成結構時的建法**（論文在 Wikipedia 上的做法，Appendix A.4、B.5）

1. 每頁取「標題 + 第一句」，轉成向量（e5-base-v2）。
2. k-means 分成 1,000 群。
3. 請 LLM（Qwen3-8B）讀每群的頁面標題，寫一句 30 字內的描述。
4. 描述必須點名比較不典型的成員：摘要天生描述多數成員的主題，少數成員會從描述中消失，審查員就不會為它們保留這一群。這個 prompt 設計沒有做消融驗證。

**有現成結構時**：章節標題、網址路徑、metadata 都可當描述；樹不必處處一樣深，只在節點太大的地方多切一層。

**可套用之處**（推論）：任何「看描述選分支」的路由問題，例如 agent 依工具描述選工具、依 skill 描述選 skill、多 agent 之間分派任務、RAPTOR 的摘要樹、PageIndex 的目錄導航。路由器再強，也受限於它看到的選項描述。

## 追問專節

### Q1 每一輪判斷，模型的輸入和輸出到底長什麼樣？

每一輪都重新組一個 context：「使用者問題 + 編號的候選描述（依所屬頁面分組、按閱讀順序）」，後面接題目。上一輪的分數不帶進下一輪的輸入（Appendix B.1）。以查詢「Christopher Nolan 2000 年那部電影的主角是誰？」為例：

**第 ① 輪：頁面層是非題**

- context：問題；頁面 1 Memento (film)；頁面 2 Christopher Nolan；頁面 3 Gladiator (2000 film)；…其餘候選標題。
- 題目：每頁一題「回答問題所需的資訊在頁面 n 裡嗎？」（yes／no），同一次 forward pass 答完。
- 輸出：每頁一個 P(yes)，例如 0.96、0.81、0.07，加總 1.84（Figure 3a）。
- 用途：留前 k 頁，展開它們的全部段落。

**第 ② 輪：段落層是非題**

- context：問題；頁面 Memento (film) 底下的段落 1「主角是 Leonard Shelby…」、段落 2「讓 Nolan 一舉成名…」；頁面 Christopher Nolan 底下的段落 3「Nolan 的婚姻…」。
- 題目：每段一題「第 n 段含有回答問題所需的資訊嗎？」
- 輸出：每段一個 P(yes)，彼此獨立，加總不必為 1。
- 用途：排序後留前 r 段，前 m 段進第 ③ 輪。

**第 ③ 輪：決選題**

- context：新組的，只放問題和前 m 段。
- 題目：一題「哪一段最相關？」，選項就是這 m 段（實際問句論文未給，Figure 3b 只是示意）。
- 輸出：一個機率分布，例如 0.91、0.09，加總為 1。
- 用途：前 m 名照此重排，第 m+1 到 r 名維持第 ② 輪順序。

頁面的描述依資料集而定：MD2D 與 MTRAG 用標題加章節標題，CQA 用標題加最上層章節標題，NQ 只用標題。NQ 在第 ① 輪之前還多一層「主題分群」，做法相同。

### Q2 同一個 context 放越多候選，判斷品質會變差嗎？

在這個設計裡，「題目變多」和「context 變長」永遠一起發生，所以實際要問的是「一個請求放越多候選，排序會不會變差」。在論文測過的範圍內不會；從 1 個加到約 50 個反而變好，之後持平。

- **固定難度，只改請求大小**（6.2 節，Figure 6，NQ 289 題）：每題固定 200 個候選，拆成每個請求 m 個再合併排序。Hit@1 從每請求 1 個的 47.8% 升到 50 個的 54.3%，到 100、200 個都持平。原 caption：「Hit@1 on Natural Questions when a fixed pool of 200 candidates is split into requests of m candidates and ranked together (289 questions; band: 95% interval).」
- **非常長的 context**（Appendix F，MTRAG 188 輪）：篩 8,578 個頁面標題時，每請求最多 150k tokens 與最多 10k tokens 兩種拆法，R@5 與 nDCG@5（考慮名次的排序品質）差 −0.7 與 −0.2 點，信賴區間都含 0。
- **容易誤讀的 Figure 5**：候選池從 5 長到 1,000 時 Hit@1 一路下降（1,000 個時 47.6%），但池子變大時混入更多 hard negative，題目本身變難，不能當成 context 變長傷品質的證據；它該看的是同樣池子大小下，一起判斷一直勝過分開判斷。

**沒被回答的**：每題 yes／no 的絕對正確率論文沒測，只測排序。P(yes) 的絕對值可能隨 context 長度漂移而不影響排序（推論），所以若要拿 P(yes) 對門檻值，這件事沒有被驗證。排序只測到 200 個候選；長 context 只測了「篩頁面標題」這一種任務。

### Q3 notepad 是直接放進段落層嗎？

在 MultiDoc2Dial 上，是。notepad 在三輪中各自這樣進來：

| 輪次 | notepad 怎麼進來 | 原文講清楚了嗎 |
| --- | --- | --- |
| ① 說明中心層 | 最近取過的頁面所屬的中心一定保留 | 清楚（B.2） |
| ② 頁面層 | context 列出 notepad 頁面 | 不清楚，見下 |
| ③ 段落層 | 最近 2 個 notepad 頁面的所有段落直接加入是非題，不經頁面層篩選 | 清楚（4.2、B.2） |

原文對頁面層只有一句「The page-stage context lists the notepad pages.」，有兩種讀法：當作提示資訊（仍要靠自己的是非題爭名額，可能被剪），或當作額外候選。推論讀法 A 較合理，因為 ① 已保證那一頁會出現在候選裡，但原文無法區分。

三個常見誤解：

- notepad 記的是「最近」不是「名次」：每輪結束後，只有那一輪排第一的段落所屬頁面移到最前面；連續兩輪落在同一頁只佔一個位置。
- 段落加入的是段落層的是非題，還得擠進前 m 名才進決選題。後門保證「能被看到」，不保證「會被選上」。
- MTRAG 也用 notepad，但是否也把段落直接加進段落層，論文沒說。

### Q4 位置編號是不是都當作接在 context 後面？

是，但光靠位置編號不夠，要和 attention 遮罩一起用。原文：所有題目都從 context 結束後的位置開始，且彼此不能互相 attend（Appendix G）。例（長度自編）：

|  | 在序列中實際的格子 | 給模型的位置編號 |
| --- | --- | --- |
| context | 0–999 | 0–999 |
| 題目 1 | 1000–1019 | 1000–1019 |
| 題目 2 | 1020–1044（排在題目 1 後面） | 1000–1024（與題目 1 重疊） |

- **位置編號重疊**：每一題感受到的自己和 context 的距離，都與「只有這一題」時相同（一般知識：Qwen3 用 RoPE，attention 看的是相對距離）。
- **attention 遮罩**：題目 2 看不到題目 1；少了它，題目 2 會讀到題目 1，就不再是獨立判斷。

兩者合起來，等同於把 n 個「context + 第 i 題」分開跑 n 次，但 context 只算一次。

**為什麼這樣設計（推論，論文未說明）**：若位置照實際順序往後排，越後面的題目離 context 越遠，模型可能偏好或壓低後面的候選。從同一位置起算，題目在位置上對稱，消除了「題目排第幾」的偏差。**但候選內容在 context 裡仍有先後順序**：候選 1 的描述在開頭、候選 200 在結尾，兩者與題目的距離不同，這部分偏差沒有被消除，論文也沒測過打亂候選順序的影響。選項「no」「yes」的位置編號怎麼排，論文未交代。
