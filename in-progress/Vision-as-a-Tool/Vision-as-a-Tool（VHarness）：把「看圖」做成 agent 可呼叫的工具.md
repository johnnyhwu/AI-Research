# Vision-as-a-Tool（VHarness）：把「看圖」做成 agent 可呼叫的工具

Nov 20, 2026 · @YHHW

## 論文資訊

- **標題**：Vision-as-a-Tool: Visual Harness for Multimodal Agentic Coding
- **作者單位**：北京大學、Microsoft Research、University of Edinburgh、南京大學（Haolin Yang 等，Furu Wei 團隊）
- **連結**：[arXiv 2611.17797v1](https://arxiv.org/abs/2611.17797)（2026-11-13）· [Project page](https://vision-as-a-tool.github.io/)

## 三十秒版本

**情境**。要 agent 把一張網頁截圖還原成 HTML，它得反覆「寫程式 → 渲染 → 和目標比對 → 修改」。比對這一步如果只靠 agent 自己的眼睛，看不出「文字繞著插圖排成圓弧」這類版面差異，還容易提早收工；看不到圖的純文字模型，則根本跑不了這個迴圈。

**核心發現**。給寫程式的 agent 配上一組「外接眼睛」工具，背後是另一個能看圖的模型（Gemini-3.8-Flash），做出來的成品就更像目標：

- 測試的四個能看圖的模型，在網頁、向量圖、3D 三種任務上全部進步，3D 進步最多。例如 GPT-5.6-sol 的 3D 成品和目標的外觀相似度，從 0.705 提高到 0.812（滿分 1）。
- 原本看不到圖的純文字模型也能完成任務，表現和一個能看圖的模型（GPT-5.5）不用工具時差不多。
- 如果不包成固定工具，而是讓 agent 自己隨意發問同一個外接模型，進步只剩大約四成。可見「把看圖整理成幾個固定工具」本身就有用。
- 代價是 agent 做更多輪，它自己輸出的文字量變成原本的 2 到 6 倍。

**方法怎麼對應**。五個工具分兩組：`transcribe`、`grep`、`inspect` 由粗到細看懂目標；`diff` 找出差異並排好優先順序，`align` 確認單點。每個工具背後都是同一個模型，搭配一份專屬提示詞和嚴格的 JSON 格式，透過 MCP 交給 agent，由它自己決定什麼時候呼叫。

## 怎麼讀

**主軸**：看圖寫程式的迴圈裡，最關鍵的一步是「比對渲染結果和目標差在哪」。這篇把「看」和「比對」做成 agent 隨時可以呼叫的工具。

## 一、問題：迴圈缺一個可靠的比對者

看圖寫程式（截圖轉 HTML、點陣圖轉 SVG、四視角圖轉 Blender 3D 腳本）都跑同一個迴圈。四步裡，寫程式和渲染都有確定的工具可用，唯一不確定的是「比對」：要有人看得出渲染結果哪裡和目標不像，下一輪才知道要改哪裡。

&#91;embedded content: 看圖寫程式的迴圈 · 4 步，比對是瓶頸\]

**現有做法：自己看圖**（論文原名 Thinking-with-Images）。由 agent 底層的多模態大型語言模型（MLLM，能同時讀圖和文字的模型）自己比對，頂多先把圖裁切、放大再看。這造成兩個問題：

|  | 多模態 agent | 純文字 agent |
| --- | --- | --- |
| 現在怎麼做 | 自己看圖；或為單一任務設計的修正流程（修網頁的 DesignRepair、修 SVG 的 Chat2SVG） | 外接固定視覺模組，或只會看單張圖答題的流程 |
| 卡在哪 | 裁切、放大只是給同一雙眼睛看更大的圖，上限＝自己的視力；為單一任務設計的流程換任務就得重寫 | 只會看一張圖，不會拿目標和渲染結果互比，撐不起迴圈（見【概念 1】） |

後果可以看論文 Figure 2（caption：*Qualitative comparisons across Image-to-HTML, Image-to-SVG, and Image-to-3D tasks.*）第一列：目標頁面的文字繞著插圖排成圓弧，baseline 沒看出來，排成了一條直欄。「做完了沒」也靠同一雙眼睛判斷，附錄 C.1 指出 baseline 常漏看細小的位移或缺漏就提早收工。

**一句話**：迴圈缺一個可靠、可呼叫的「比對者」。

## 二、方法：VHarness

原本的迴圈不動，只新增兩層：一個「視覺工具箱」，和工具背後的「外接眼睛」。寫碼者本身不改、不訓練。

### 系統地圖

&#91;embedded content: VHarness 系統地圖 · 五個工具、一個外接模型\]

| 本文名稱 | 論文原名 | 是什麼 |
| --- | --- | --- |
| 寫碼者 | coding agent，Pθ | 在 Claude Code 裡寫程式的模型，可以是多模態或純文字 |
| 渲染器 | rendering environment R | 把程式轉成圖：瀏覽器截圖、SVG 點陣化、Blender 渲染 |
| 視覺工具箱 | VHarness，五個 atomic actions | `transcribe`、`grep`、`inspect`、`align`、`diff` |
| 外接眼睛 | external visual utilities Uϕ | 工具背後實際看圖的模型，Gemini-3.8-Flash |
| 自己的眼睛 | intrinsic vision | 寫碼者本身的看圖能力，只有多模態才有 |

論文自己的類比：寫碼者像在終端機工作的工程師，工具箱是**視覺版的 Unix 指令**（`grep` 找東西、`diff` 比兩份檔案），外接眼睛是指令背後真正執行的程式。多模態寫碼者兩種眼睛都能用；純文字寫碼者只能用工具箱。

### 一次執行怎麼走

沒有固定流程，由寫碼者自己決定何時呼叫哪個工具。以下是自編例子，順序依論文 2.3 節的描述（論文沒有給逐步的實際紀錄）。目標是一張「文字繞著插圖排成圓弧」的網頁：

| 步 | 寫碼者的問題 | 呼叫 | 拿回什麼 |
| --- | --- | --- | --- |
| 1 | 這頁大概分幾塊？ | `transcribe(目標圖)` | 版面骨架：頁首、中段（插圖＋環繞文字）、頁尾 |
| 2 | 標題在哪、長什麼樣？ | `grep` → `inspect` | 標題的位置框；文字、粗體無襯線、#1A1A1A |
| 3 | 先寫第一版 | （寫 code.html → 渲染） | render.png |
| 4 | 和目標差在哪？ | `diff(目標圖, 渲染圖)` | 最顯眼的排第一：「中段文字排成直欄，目標是圓弧」 |
| 5 | 那一區目標怎麼排？ | `grep` → `inspect`（看目標那一區） | 細節描述，接著改程式、再渲染 |
| 6 | 這行字對了嗎？ | `align(渲染圖的區域, "Summer Sale")` | true 或 false |
| 7 | 回到第 4 步 | `diff` | 回空清單或判斷已完成，就停止 |

1–2 步是「看懂目標」，4–7 步是「比對與確認」。不固定流程的理由是：同一套工具要能用在 HTML、SVG、3D，而固定流程正是「為單一任務設計」的做法的弱點。

### 五個工具：各自回答什麼問題、吃什麼、吐什麼

動手前要回答三個問題（骨架、位置、外觀，由粗到細），渲染後要回答兩個（單點對不對、整張差在哪）。輸出格式取自論文 Figure 9、10 的提示詞原文。

| 階段 | 工具 | 回答的問題 | 輸入 | 輸出 |
| --- | --- | --- | --- | --- |
| 看懂目標 | `transcribe` | 整體骨架是什麼？ | 目標圖（3D：四張視角圖） | JSON 結構樹：區塊、閱讀順序、並排關係；不含座標、顏色、字型。3D 版輸出零件分解與材質 |
| 看懂目標 | `grep` | 某個東西在哪？ | 一張圖＋文字查詢 | 所有符合的元素：類別、位置框、文字、信心分數 |
| 看懂目標 | `inspect` | 這個東西長什麼樣？ | 一張圖或其中一塊＋模式（文字／圖像） | 文字模式：逐字內容＋一行固定選項的字型描述；圖像模式：自由描述 |
| 比對 | `align` | 這一處對不對？ | 一張圖或其中一塊＋預期的文字 | `{"match": true 或 false}`，只看字義與用字，忽略字型 |
| 比對 | `diff` | 整張圖差在哪？ | 目標圖＋渲染圖 | 差異清單，兩種格式（見下）；沒有差異回 `[]` |

**位置框格式**：`[上, 左, 下, 右]`，數值縮放到 0–1000，不是像素。頁面高 3000 px 時，「上＝40」等於 40/1000 × 3000 = 120 px。

各工具的輸出範例（自編例子，格式依論文提示詞）：

```json
// transcribe
{"layout":"flow","children":[{"block":"block_1"},
  {"layout":"row","children":[{"graphic":"asset_03"},{"block":"block_2"}]},
  {"block":"block_3"}]}
// grep(目標圖, "主標題")
[{"category":"text","bbox":[40,80,95,920],"text":"Summer Sale","confidence":0.93}]
// align(渲染圖的標題區, "Summer Sale")
{"match": false}
```

論文未說明：`transcribe` 裡 `block_1` 這些編號從哪裡來；各工具的參數定義（例如 `inspect` 的模式由誰指定）；`align` 內文說能檢查「文字或規格」，但只附了檢查文字的提示詞。

#### `inspect` 的兩種模式

差別在於看的是哪一種區塊（自編例子，同一頁的兩個區塊）：

|  | 文字模式 | 圖像模式 |
| --- | --- | --- |
| 用在哪 | 標題、段落、按鈕上的字 | 插圖、圖示、SVG 形狀、3D 零件 |
| 輸出 | `Summer Sale` 加上 `[type] family: sans-geometric · weight: bold · width: normal · slant: normal · text-colour: #1A1A1A` | 「橘色圓形太陽，中間三條白色波浪線，外圈 12 道短放射線，沒有文字。」 |
| 寫碼者拿去做什麼 | 直接對應 CSS：bold → `font-weight: 700`，顏色 → `color` | 用 SVG 或 CSS 把這個圖形畫出來 |

文字模式用固定選項（推論）：每個選項都能直接對到一個 CSS 屬性，寫碼者不用猜「看起來有點粗」是哪個值。圖形種類無窮，只能自由描述。

#### `diff` 的兩種輸出格式

&#91;embedded content: diff 成對位置框 · 自編例子，圓形＝插圖、灰線＝文字、虛線框＝兩個位置框\]

|  | 依顯眼程度排序 | 成對位置框 |
| --- | --- | --- |
| 回答 | 錯什麼？先修哪個？ | 這個元素在兩張圖裡各在哪？ |
| 每一條 | where、what、prominence（high／medium／low），大問題先列 | tag、target\_bbox、render\_bbox；渲染圖裡缺這個元素就填 `null` |
| 例子 | 中段／文字排成插圖下方的直欄，目標是繞插圖一圈／high | 環繞文字／\[250,133,750,867\]／\[545,367,955,633\] |
| 工程類比 | 依嚴重程度排序的 code review 意見 | git diff 的「這段在舊檔第 10–20 行，在新檔移到第 40–60 行」 |
| 寫碼者接著做什麼（推論） | 決定修改順序 | 把兩個框各自裁下，用 `inspect` 細看再改 |

成對位置框要給兩個框，是因為畫錯的元素在兩張圖裡位置不同，一個框沒辦法同時框住兩邊。論文未說明什麼情況用哪種格式。

`diff` 和 `align` 的分工：`diff` 找出問題並排優先順序，`align` 在改完之後確認某一點真的對了，就像先跑 diff、修完再用 assert 鎖住。

### 工具背後：同一個模型，每個工具一份提示詞

五個工具背後是同一個通用模型（Gemini-3.8-Flash），沒有訓練，也沒有專門的視覺模型。每個工具真正的內容是**自己專屬的一份提示詞**，有些還按情境分版本：`transcribe` 分 HTML／SVG 與 3D 兩版，`inspect` 分文字與圖像兩版，`diff` 分兩種輸出格式，`grep` 與 `align` 各一版。

一次呼叫實際發生的事（以 `grep` 為例）：

1. 寫碼者呼叫 `grep(./target.png, "主標題")`。
2. MCP 伺服器把參數填進固定模板：「這是一張 {寬}x{高} px 的圖，找出所有符合 "{查詢}" 的元素……只回嚴格 JSON」。
3. 模板連同圖片送給 Gemini-3.8-Flash。
4. 收到的 JSON 原樣交回寫碼者。

實作是一個用 FastMCP 寫的常駐 MCP 伺服器，工具掛在 `mcp__atomic__*` 名稱底下。提示詞做的五件事，就是工具和「直接問模型」的差別：

- **限定輸出結構**：只能回嚴格 JSON，欄位固定。
- **限定用詞**：`inspect` 的字重只能從 thin 到 black 的固定選項裡挑。
- **規定順序**：`diff` 先列大問題，後列小細節。
- **規定不做什麼**：`transcribe` 不准給座標、顏色、字型。
- **統一座標**：所有位置框都縮放到 0–1000。

工程類比：這是把 LLM 包成**有型別的函式**。呼叫端只看得到函式簽名（輸入什麼、回傳什麼結構），提示詞是函式內部的實作。

論文未說明：附錄只附了「沒有工具箱的 baseline」和「Freestyle」兩種給寫碼者的使用說明，帶工具箱時寫碼者收到的說明沒有附上；提示詞放在 system 還是 user 角色也沒有交代。

### 什麼時候停止

兩邊都不設最少輪數或 token 預算，「判斷成品看起來完成了」就停。差別在由誰判斷：baseline 靠自己的眼睛，常提早收工；帶工具箱時靠外接眼睛確認，`diff`、`inspect` 會持續回報剩下的差異。具體的停止條件（例如是不是 `diff` 回空清單）論文未說明。這個設計同時影響品質和成本，見實驗的 token 分析。

## 三、實驗

四個多模態寫碼者加上工具箱後，在三個任務上全部變好，3D 提升最大。提升一部分來自「多一雙眼睛」，一部分來自「包成固定工具」，代價是寫碼者的輸出 token 變成 2.0–6.4 倍。

**設定**：三個任務各 100 題（HTML、SVG 選自公開來源的高複雜度案例，3D 抽自 3DCodeBench）。所有寫碼者都跑在 Claude Code，推理強度 high、200K context。指標：

| 指標 | 一句話 | 測哪一面 |
| --- | --- | --- |
| DINOv2 ↑ | 用 DINOv2 視覺模型把兩張圖轉成向量，算相似度（0–1） | 整體外觀像不像 |
| Chamfer ↓ | 兩個 3D 模型表面點的最近距離平均 | 3D 形狀差多少（只用在 3D） |

論文另有 SigLIP2、LPIPS、SSIM、Pixel MSE、輪廓 F1、Uni3D 等指標，方向都和下表一致。

### 主結果

Table 1（caption：*Quantitative comparison of final rendered artifacts with (w/) and without (w/o) VHarness across Image-to-HTML, Image-to-SVG, and Image-to-3D (100 cases per task).*）的精簡版，格式為「沒有工具箱 → 有工具箱」：

| 寫碼者 | HTML（DINOv2） | SVG（DINOv2） | 3D（DINOv2） | 3D（Chamfer） |
| --- | --- | --- | --- | --- |
| GPT-5.5 | .888 → .905 | .852 → .879 | .662 → .750 | .0094 → .0058 |
| GPT-5.6-sol | .906 → .913 | .888 → .902 | .705 → .812 | .0157 → .0035 |
| Claude Opus 4.8 | .717 → .872 | .722 → .787 | .534 → .702 | .0339 → .0086 |
| GLM-5.3-Flash | .902 → .922 | .897 → .921 | .759 → .819 | .0056 → .0035 |
| GLM-5.2（純文字，只有「有」） | .895 | .866 | .662 | .0092 |

Claude Opus 4.8 的 baseline 明顯偏弱，最大的提升幅度來自它；其餘三個模型在 HTML 上只多 .007–.020。

純文字的 GLM-5.2 因預算只跑隨機 50 題。在相同的 50 題上（Table 8），它和「沒有工具箱的 GPT-5.5」是 .895 vs .894（HTML）、.866 vs .861（SVG）、.662 vs .670（3D），大致打平。

### 功勞拆解：Freestyle 消融

Freestyle 保留同一個 Gemini，但只給寫碼者一個「自由提問」的工具，問題由寫碼者自己寫。Table 3（caption：*Ablation study on replacing the five atomic actions with a single free-form MLLM interface (Freestyle) using GPT-5.6-sol on the Image-to-3D benchmark.*）：

|  | 沒有工具箱 | Freestyle | 五個工具 |
| --- | --- | --- | --- |
| DINOv2 ↑ | .705 | .748 | .812 |
| Chamfer ↓ | .0157 | .0070 | .0035 |

總提升中，「多一雙眼睛」的份量在 DINOv2 約佔 40%（.043 / .108），在 Chamfer 約佔 71%（.0087 / .0122）；其餘來自「包成五個固定工具」。只測了一個模型、一個任務。

### 成本：為什麼寫碼者的輸出 token 反而變多

Table 5（caption：*Average recorded output tokens per case by the coding agent Pθ across Image-to-HTML, Image-to-SVG, and Image-to-3D.*）顯示，加上工具箱後寫碼者的輸出 token 變成 2.0–6.4 倍。工具回傳的 JSON 屬於輸入 token，不在這張表裡；增加的部分都是寫碼者自己寫出來的。

| 來源 | 說明 | 根據 |
| --- | --- | --- |
| 輪數變多 | baseline 自己判斷完成就停；有工具箱時 `diff` 持續回報差異，迴圈繼續 | 論文附錄 C.1 |
| 每次呼叫工具都要寫 | 決定叫哪個工具、寫查詢、讀完結果再思考下一步 | 推論 |
| 修改次數變多 | 每輪針對新回報的差異改程式 | 推論；baseline 的修改次數沒有報告 |

推論（只有 4 個模型，算不上嚴格的相關）：工具呼叫最少的 GLM-5.3-Flash（每題 11–36 次，Table 7），token 倍數也最小（2.0–3.0 倍）；呼叫最多的 GPT-5.5（92–285 次）是 3.3–6.3 倍。純文字 GLM-5.2 在 HTML 每題輸出 68.6 萬 token、呼叫工具 733 次。

實際成本還更高：寫碼者的輸入 token 和外接眼睛（Gemini）那一側的花費，論文都沒有報告。

## 【概念 1】外接固定視覺模組和「把視覺當工具」差在哪？

**一句話**：兩者都是「agent 自己不看，請外面的模型看」；差別不在有沒有外接，而在外接的東西**能不能拿兩張圖互比**。看圖寫程式的迴圈需要的不只是「看懂一張圖」，而是「說出兩張圖差在哪」。

同一個例子（自編）：目標頁面的文字繞著插圖排成圓弧，agent 第一版寫成一條直欄。

|  | 外接固定模組（MM-REACT、ViperGPT 等） | 看圖答題流程（SeeingEye、DRP 等） | 把視覺當工具（VaaT） |
| --- | --- | --- | --- |
| 外面的模型 | 專門模型：圖說、OCR、版面偵測 | 一個通用多模態模型 | 一個通用多模態模型，包成五個固定工具 |
| 給它目標圖時，agent 拿回什麼 | 「一張有插圖和文字的頁面」＋幾個文字框座標；說不出「圓弧」 | 問「文字怎麼排？」能答「繞插圖呈圓弧」 | 骨架、位置、字型顏色，依呼叫的工具而定 |
| 能不能拿兩張圖比 | 不行 | 不行，設計上只看一張靜態圖 | 可以：`diff` 回「中段排成直欄，目標是圓弧」並附兩邊位置 |
| 撐不撐得起迴圈 | 撐不起 | 撐不起 | 撐得起 |

推論：照這個對照，VaaT 並不是全新的類別，而是把「純文字推理者＋外部看圖模型」這個既有做法，針對寫程式迴圈補上「比對」和「確認」兩個動作。
