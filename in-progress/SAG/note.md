### 前言 (Introduction)

在現有的 RAG（檢索增強生成）系統中，當 Agent 需要處理跨文件、多步驟的複雜推論（Multi-hop）時，正面臨兩難：傳統的**向量檢索**只看語意相似度，容易在推理中途斷鏈；而**圖譜檢索（GraphRAG）**雖然能建立關聯，但建置成本極高，且會將完整的句子強行拆碎成失去上下文的三元組（Triples），在資料持續增加時也極難進行維護與更新。

為了解決這個痛點，本篇論文提出了 **SAG（SQL-Retrieval Augmented Generation）** 架構。它的核心思想是：**「不要在線下建構死板的全局圖譜，而是在查詢時用 SQL 動態連連看」**。
*   **線下階段**：SAG 不拆解三元組，而是將文本片段轉換為一個保留完整語意的「事件（Event）」，並平行抽取多個「實體（Entities）」作為標籤，同步寫入標準的 SQL 資料庫與向量索引中，天然支持無痛的增量寫入（Append-only）。
*   **線上階段**：當收到查詢時，系統先找出種子事件，接著利用 **SQL JOIN** 的確定性關聯，將共用實體的事件瞬間串接成「動態超邊（Dynamic Hyperedges）」。這讓系統不需要複雜的圖演算法，就能精準跨越文件找出隱藏的邏輯鏈結。

在 HotpotQA、2WikiMultiHop 和 MuSiQue 三個標準多跳推論基準測試中，SAG 在 9 個 Recall@K 指標中取得了 8 個第一。特別是在推論鏈最長、最難作弊的 MuSiQue 資料集上，達到了 **80.0% 的 Recall@5**。此外，SAG 已在實際生產環境中部署，證明了在處理數億筆資料的規模下，依然能保持秒級檢索延遲的工程可行性。


### 一、 核心痛點：現有 RAG 架構的兩難困境

在構建基於 LLM Agent 的數據基礎設施時，處理跨文件、多步驟關聯查詢是檢索階段的最大挑戰。現有的兩大檢索範式（向量檢索與圖譜檢索）在工程落地時，分別面臨了難以調和的系統性缺陷。

#### 1.1 Naive RAG (向量檢索) 的盲點：缺乏邏輯約束與多步斷鏈

傳統的向量檢索（Dense Retrieval）本質上是**語意相似度匹配（Semantic-similarity matching）**。它將文本切塊（Chunking）後映射到向量空間，並在查詢時返回 Top-K 相似的片段。這種設計在處理多步推理任務時，存在以下根本限制：

*   **無法建立顯式實體關聯 (Explicit Associative Chains)**：
    向量檢索擅長尋找語意相近的段落，但無法復原實體之間明確的邏輯鏈條，尤其是當查詢涉及時間限制（Temporal constraints）、特定實體角色或多步驟依賴關係時。
*   **誤差的連鎖累積與放大 (Error Accumulation)**：
    對於需要多步順序檢索（Sequential retrieval）的 Agent 任務，檢索過程就像一條連鎖反應鏈。如果第一步檢索（Step 1）因為語意相似度不夠高而發生微小偏離，這個誤差就會在後續的推理鏈中被呈指數級放大，最終導致整個檢索路徑徹底斷鏈。
*   **字面特徵的盲區**：
    許多在推論鏈中扮演「橋樑（Bridge）」角色的中間證據，其字面與語意可能跟使用者的原始問題高度不相關。單純依靠向量空間的距離，這些關鍵的「中間跳板」往往會因為相似度分數過低，在一開始就被過濾掉。

---

#### 1.2 GraphRAG (圖譜檢索) 的代價：語意破碎、增量更新困難與分數衰減

為了解決向量檢索缺乏邏輯結構的問題，近年來學界提出了結構增強型方法（如 GraphRAG、HippoRAG）。這些方法通常在線下利用 LLM 抽取三元組，並構建一個全局知識圖譜（Global Knowledge Graph）。然而，這種結構化嘗試在工程實務上付出了極大的代價：

*   **語意破碎化 (Semantic Fragmentation)**：
    傳統知識圖譜將關係限制為二元組 `(主體, 關係, 客體)`。然而，現實世界中的事件通常是 N 元關係（涉及多方、時間、地點等多個維度）。將複雜事件強行拆解為多個獨立的二元三元組，會徹底摧毀文本原始的上下文語意，導致資訊流失。
*   **工程災難：難以維護與增量更新 (Maintenance Overhead)**：
    在現實系統中，數據是持續且動態增加的（Append-only）。知識圖譜的構建包含「實體抽取」、「實體對齊（Entity Merging）」與「關係正規化」等步驟。當有新文獻寫入時，為了保持全域圖譜的正確性，系統往往需要重新運行上述複雜流程，甚至重新計算全局節點權重（如 PageRank）。這種高昂的線下維護成本，使系統極難進行即時的增量更新。
*   **線上檢索與線下結構的脫節 (Systematic Decoupling)**：
    論文指出，許多花費高昂代價在線下建構的複雜圖結構，在線上查詢時，往往又退化為單純對「圖節點」或「社區摘要」進行扁平的向量相似度匹配，導致精心設計的結構在最終檢索階段未能發揮真正的結構化約束作用。
*   **多步傳遞時的分數衰減與雜訊累積 (Score Decay & Noise)**：
    如 HippoRAG 等方法，在線上會利用 Personalized PageRank 演算法在圖上傳播分數。
    1.  **衰減效應**：隨着跳轉步數（Hops）增加，遠端目標節點的分數會因為阻尼係數（Damping factor）而嚴重衰減，導致深層的答案難以被排到前列。
    2.  **雜訊放大**：圖譜中高頻、通用的「中心節點（Hub Nodes）」會將無關的訊號向外擴散，導致無關的雜訊節點分數上升，進一步干擾檢索精準度。

### 二、 SAG 的設計哲學與底層概念

SAG (SQL-Retrieval Augmented Generation) 的核心設計哲學在於**「重分配檢索管線中的職責（Redistribute responsibilities）」**。它不試圖去開發更強大的黑盒子模型，而是利用計算機科學中發展最成熟的基礎設施（關聯式資料庫與向量資料庫），重新設計知識的儲存與關聯方式。

---

#### 2.1 重新定義基礎建設：SQL、向量與 LLM 的嚴格分工

SAG 捨棄了「利用 LLM 在線下建構全局複雜圖譜」的重工業路徑，改為在線上查詢時進行輕量級的動態關聯。系統的三大核心組件有著極其嚴格的職責劃分：

*   **SQL 資料庫（確定性關聯引擎）**：
    *   **職責**：負責精確的結構化過濾與關聯（Filtering & Joining）。
    *   **優勢**：SQL 不懂語意，但它在處理「A 是否等於 B」的精確比對上，擁有毫秒級的效能與 100% 的確定性。透過標準的關聯操作，它可以無損且不衰減地串聯不同文本。這使得整個檢索系統天然支持併發處理、標準資料庫橫向擴展與無痛的增量寫入（Append-only）。
*   **向量資料庫（語意模糊擴展引擎）**：
    *   **職責**：負責解決別名、同義詞、打錯字及「換句話說（Paraphrasing）」的語意對齊。
    *   **優勢**：向量檢索不被用來做多步推論（那不是向量的強項），而是專門用來作為實體與事件的「容錯與對齊安全網」，確保字面不完全一致的關鍵字能被順利拉進 SQL 的比對範圍中。
*   **LLM（高價值語意決策大腦）**：
    *   **職責**：僅用於線下抽取「事件與實體」，以及線上對最終被大幅壓縮的候選集合（如 Top 100）進行「聯合推理排序（Joint assessment）」。
    *   **優勢**：LLM 不被浪費在漫長且無邏輯的圖走訪（Graph Traversal）上，這使得整套系統的 token 消耗與 API 呼叫成本極低。

---

#### 2.2 核心機制剖析：什麼是「潛在超邊 (Latent Hyperedge)」？

在傳統圖論中，一個邊（Edge）只能連接兩個節點（主體 $\rightarrow$ 客體），這被稱為二元圖。然而，現實世界中的知識多為多元關係（N-ary relations）。為此，SAG 引入了**「超圖（Hypergraph）」**中的**「超邊（Hyperedge）」**概念：

*   **超邊 (Hyperedge) 的定義**：
    一個超邊可以同時包含任意數量的節點。在 SAG 中，一個文本區塊（Chunk）對應一個保留完整語意的「事件 $e$」，以及一組與之關聯的「實體集合 $\mathcal{U}(e)$」。這個**事件與實體集合的綁定關係，本質上就定義了一個超邊**。
*   **潛在 (Latent) 的含義**：
    在線下建置索引時，系統**不會**去計算實體與實體之間的全局連線，也不會繪製出任何顯性的圖譜。這些超邊關係只是以「事件-實體」的多對多資料表形式，**潛伏（Latent）**在 SQL 資料庫中。
*   **線上動態具現化 (Dynamic Instantiation)**：
    只有在使用者發出查詢、系統下達 SQL JOIN 語法的那一瞬間，共用實體的事件才會在記憶體中被動態地鏈接起來，形成局部的超圖結構。查詢結束後，這個臨時圖譜即被釋放，完全沒有維護全局靜態圖的開銷。

#### 2.3 降維打擊：為什麼 4 Hop 的邏輯推論只需要 1 Hop 的檢索？

在多步推理測試集（如 MuSiQue）中，有些問題在二元圖譜上需要進行高達 4 次跳轉（4 hops）才能抵達答案。然而，SAG 在實務設定上，通常只需要 **$H=1$（1 跳擴展）** 就能取得領先的檢索 recall。其背後的原理可以稱為**「高維度的語意壓縮」**：

1.  **實體與事件的壓縮效應**：
    在傳統圖譜中，因為節點被拆得極碎（三元組），每一次跳轉只能跨越極短的邏輯距離。但在 SAG 中，一個事件（Event）是一個保留了完整上下文的句子。一個單一事件（超邊）內部就已經自然壓縮了多個實體。
2.  **空間的跳躍**：
    當我們從問題出發命中第一個種子事件時，因為這個事件保留了完整細節，它內部蘊含的實體（如時間、地點、人物）已經幫我們在語意空間中完成了「第 1 與第 2 步的跨越」。
3.  **1 Hop 的 SQL 擴展**：
    接著，我們拿著這些實體作為跳板，只需下達一次 SQL `JOIN`（即 1 Hop），就能直接拉回與之相關的下一個完整事件。這個新事件內部又壓縮了後續的邏輯鏈條。

這就是為什麼 **SAG 的 1 跳 SQL 擴展，其資訊覆蓋率能直接與傳統圖譜的 3 到 4 跳相媲美**。它從根本上避免了多跳圖傳播所帶來的誤差累積與分數衰減，以極其精簡的步驟完成了複雜的多步關聯。


### 三、 線下階段 (Offline Phase)：資料攝取與索引建置

線下建置的核心任務是將非結構化的原始文檔，轉換為結構化的、可供 SQL 高效查詢的「事件-實體」索引，並同步分發到不同的儲存底座中。整個流程採取**批次處理（Batch mode）**，各文檔之間完全獨立，支持高併發寫入。

*(請在此處插入：論文 Figure 2 左上角 (1) Upload (offline) 流程圖，展示從 Corpus 抽取並寫入 SQL 與 Vector 儲存空間的過程)*

---

#### 3.1 文本處理：One-Chunk-to-One-Event 與實體抽取

當文檔輸入系統後，首先會被切割成文本區塊（Chunks）。SAG 採用 **One-Chunk-to-One-Event（一個 Chunk 對應一個事件）** 的映射策略，利用輕量級 LLM（如 Qwen3.6-Flash）平行生成兩項輸出：

1.  **事件摘要 (Event)**：將 Chunk 的核心事實濃縮為一句保留完整上下文語意、不打碎的陳述。
2.  **實體集合 (Entities)**：從 Chunk 中識別並提取關鍵的索引標籤（涵蓋時間、人物、組織、產品等 11 種預設類型）。

##### 💡 具體案例走讀：
*   **輸入原始 Chunk (ID: C001)**：
    > "在 2014 年，Facebook 宣布以 190 億美元的天價收購了知名通訊軟體 WhatsApp。這項決策主要是由馬克·祖克柏親自推動。隨後，WhatsApp 的共同創辦人揚·庫姆 (Jan Koum) 也因此加入了 Facebook 的董事會。"
*   **LLM 生成 Event (e1)**：
    > "Facebook 於 2014 年以 190 億美元收購 WhatsApp，馬克·祖克柏推動此案，隨後 WhatsApp 創辦人揚·庫姆加入 Facebook 董事會。"
*   **LLM 生成 Entities ($\mathcal{U}(e_1)$)**：
    > `['Facebook', 'Meta', '2014年', 'WhatsApp', '馬克·祖克柏', '揚·庫姆']`

---

#### 3.2 務實的實體策略：放棄全域對齊 (Entity Merging) 的權衡

傳統知識圖譜在線下最沉重的負擔是「實體對齊與消歧」（例如判定「馬克·祖克柏」、「祖克柏」、「Mark Zuckerberg」是否為同一個人）。若對齊失敗，圖譜就會斷鏈。

SAG 採取了極為務實的系統工程權衡（Trade-off）：**在線下完全不進行全域實體對齊**。
*   **字面標準化**：線下僅對實體進行極輕量清洗（如去空白、統一大小寫）並寫入。
*   **為何可行**：在 SAG 中，真正承載語意價值的是事件（Event），實體僅作為「連線指引（Index Points）」。SAG 選擇**將別名對齊的壓力推遲到線上查詢階段**，利用向量搜尋的模糊匹配來動態對齊。這使線下處理能完全擺脫全域圖譜鎖（Global Graph Lock）的限制，實現極高吞吐量的獨立寫入。

---

#### 3.3 三大基礎建設同步寫入：SQL、向量庫與倒排索引 (Inverted Index) 的互補作用

抽取完成後，SAG 會將數據同步寫入三個互補的底座，為線上檢索提供「結構、語意、精確字串」的三重保障：

##### 1. SQL 關聯式資料庫（儲存結構與超邊關係）
寫入 `Event_Entity_Mapping` 多對多關聯表，記錄事件與實體的綁定。這形成了「潛在超邊」：

| Event_ID | Chunk_ID | Entity_Text | Entity_Type |
| :--- | :--- | :--- | :--- |
| e1 | C001 | Facebook | 組織 |
| e1 | C001 | Meta | 組織 |
| e1 | C001 | 2014年 | 時間 |
| e1 | C001 | WhatsApp | 產品 |
| e1 | C001 | 馬克·祖克柏 | 人物 |
| e1 | C001 | 揚·庫姆 | 人物 |

##### 2. 向量資料庫（儲存語意表徵）
*   **事件向量**：將 Event 文本（如 `Facebook於2014年收購...`）轉為向量存入，用於線上問題的直接語意匹配。
*   **實體向量**：將單個實體字串（如 `揚·庫姆`）轉為向量存入，用於線上別名的模糊擴充。

##### 3. 全文檢索引擎 / 倒排索引（精確字串匹配保全網）
系統使用 Elasticsearch 建構**倒排索引 (Inverted Index)**。
*   **技術原理**：相對於「文章 $\rightarrow$ 包含哪些字」的正向索引，倒排索引是將文本拆解為詞彙，並記錄「詞彙 $\rightarrow$ 出現在哪些文章（Posting List）」的對照表。
*   **互補價值**：在工業界 RAG 中，向量搜尋常常會遺漏罕見的專有名詞、特定產品型號或機器料號（例如「晶片型號 M3-Max」）。倒排索引能在毫秒內精確定位這些特定字串所在的 Chunk，作為向量語意檢索的重要保底手段。


### 四、 線上查詢階段 (Online Phase)：動態檢索與多步擴展

當使用者輸入一個查詢 $q$ 時，SAG 系統將啟動線上檢索管線。整個線上階段不涉及任何全域圖譜走訪，而是透過「雙軌種子定位 $\rightarrow$ SQL 批次跳轉 $\rightarrow$ LLM 聯合評估」三個精密控制的步驟來召回答案。

*(請在此處插入：論文 Figure 2 下半部 (2) Search (online) 流程圖，重點展示雙軌檢索、SQL 擴充與 LLM Rerank 流程)*

---

#### 4.1 Step 1: 種子檢索 (Seed Retrieval) 的雙軌防禦機制

種子檢索的目的在於精確且廣泛地鎖定推論的第一個「起點（線頭）」。為了兼顧結構精準性與語意泛化性，SAG 採用雙軌並行設計：

##### 路徑 A：實體引導的結構化檢索 ($\mathcal{E}_R^{\text{entity}}$)
1.  **實體提取**：利用輕量級 LLM 從問題 $q$ 中提取關鍵實體集合 $\mathcal{U}_q$。
2.  **別名擴充**：拿著 $\mathcal{U}_q$ 去實體向量索引中進行相似度搜尋（閾值 $\ge 0.9$），找出所有意思相近的別名，形成擴充實體集 $\hat{\mathcal{U}}_q$（例如由 `{WhatsApp}` 擴充為 `{WhatsApp, whatsapp messenger}`）。
3.  **SQL 召回**：利用 SQL 的 `OR` 邏輯，精確抓出關聯到這群實體中**任何一個**的事件集合。其數學定義（論文公式 1）為：
$$\mathcal{E}_R^{\text{entity}} = \{e \mid \exists u \in \hat{\mathcal{U}}_q : \text{SQL-Join}(e, u)\}$$

##### 路徑 B：直接的向量語意檢索 ($\mathcal{E}_R^{\text{direct}}$)
*   同時，系統將問題 $q$ 轉換為向量，直接在事件向量庫中比對，撈出語意相似度大於閾值 $\tau$（預設 0.4）的事件集合 $\mathcal{E}_R^{\text{direct}}$。這條路徑用來保底，預防實體提取漏接的情況。

##### 合併與流量控制（種子預算 $K_{\text{seed}} = 50$）
系統將雙軌結果進行聯集去重（論文公式 2）：
$$\mathcal{E}_R = \mathcal{E}_R^{\text{entity}} \cup \mathcal{E}_R^{\text{direct}}$$
為了防止第一步就撈起過多元件，此處設置了**總管閥門 $K_{\text{seed}} = 50$**。若合併後數量大於 50，系統會依向量相似度排序，只保留 Top 50 的事件作為後續擴展的「種子」。

---

#### 4.2 Step 2: 查詢時動態擴展 (Query-Time Expansion) 的運作邏輯

有了種子事件 $\mathcal{E}_R$ 後，系統需要往外跳轉（Hop）來尋找間接的關鍵證據。SAG 利用 **「反向收集 $\rightarrow$ 正向撈回」** 的 SQL 批次查詢，在線上動態具現化超邊結構：

```
[初始種子事件集] ──(SQL反查)──> [前線實體集 (Entity Frontier)] ──(SQL Join)──> [擴展事件集]
```

1.  **收集前線實體 (Entity Frontier)**：
    系統將 $\mathcal{E}_R$ 中所有事件所綁定的實體全部提取出來，組成一個「實體前線集合」。
2.  **全域剪枝 (Global Pruning)**：
    若前線實體包含如「2014年」等高頻通用字，會導致下一步撈出海量無關事件。為此，系統設定了**剪枝預算（Pruning Budget = 50）**。
    當前線實體數大於 50 時，系統會計算這些實體與 Query 的向量相似度，並**強制截斷只保留 Top 50 個最相關的實體**。
3.  **SQL 批次擴展**：
    系統拿著這 50 個精選實體，利用 `WHERE Entity_Text IN (...)` 語法執行一次批次 SQL `JOIN`（OR 邏輯），撈回所有新關聯的擴展事件 $\mathcal{E}_E$。
4.  **候選池合併**（論文公式 3）：
$$\mathcal{E}_{\text{cand}} = \mathcal{E}_R \cup \mathcal{E}_E$$
這群事件在當下交織成的網絡，就是臨時產生的局域超圖。

---

#### 4.3 Step 3: 候選池壓縮與 LLM 雙軌決選 (Coarse Ranking & Dual-path Output)

此階段的任務是將幾百個候選事件 $\mathcal{E}_{\text{cand}}$ 精煉為最終可供生成答案的 Top 10 Chunks。

##### 1. 向量粗篩 (Coarse Filtering)
計算 $\mathcal{E}_{\text{cand}}$ 內所有事件與 Query 的向量相似度，並快速截取 **Top 100** 的事件，記為 $\hat{\mathcal{E}}$。

##### 2. 雙軌輸出（LLM 結構路徑 + 直接語意路徑）
系統同步執行以下兩條路線，進行最終決選：

*   **路徑 A：結構化精選路徑（LLM Rerank）**
    *   將這 100 個事件 $\hat{\mathcal{E}}$ 一起送入推理 LLM。
    *   **聯合評估 (Joint Assessment)**：LLM 會通盤考量這 100 個事件，判斷哪些事件組合起來能構成多跳推論鏈，挑選出最關鍵的 $K_{\text{event}} = 5$ 個事件，並還原回對應的原始文本區塊（Chunks）$\mathcal{C}^{\text{event}}$。
*   **路徑 B：傳統語意路徑（Direct Chunk Vector）**
    *   直接拿問題 $q$ 的向量，去原始 Chunk 向量庫中檢索出相似度最高的 $K_{\text{direct}} = 5$ 個 Chunks，記為 $\mathcal{C}^{\text{direct}}$。

##### 3. 最終合併輸出
將兩路結果聯集去重（論文公式 4），輸出最終的 Top 10 Chunks ($K_{\text{out}} = 10$) 送給生成模組：
$$\mathcal{C}_{\text{out}} = \text{TopK}_{K_{\text{out}}} (\mathcal{C}^{\text{event}} \cup \mathcal{C}^{\text{direct}})$$

##### 💡 雙軌設計的系統工程考量：
結構路徑負責召回「需要跨文件拼湊、字面相似度低的邏輯證據」；語意路徑則負責召回「與問題高度相關的直球證據」。兩者高度互補，大幅提升了系統在各類問題下的檢索穩定度。


### 五、 關鍵實驗數據與客觀結論分析

本章節提煉自論文第 5 節的實驗結果與消融研究。我們將通過客觀數據，分析 SAG 架構在處理多步推理任務時的真實表現、其設計決策的合理性，以及系統在不同軟體底座下的魯棒性。

---

#### 5.1 多步推論的極限測試：與全局圖譜 (GraphRAG) 的對決

論文在三個基準多跳數據集上進行了對比測試，主要評估檢索結果的 **Recall@2** 和 **Recall@5**。

*(請在此處插入：論文 Table 2，展示 Simple Baselines、Large Embedding Models 以及 Graph-based Methods 在三個數據集上的 Recall@2/5 對比)*

##### 1. MuSiQue 數據集（難度最高，多步不可跳過）
*   **實驗結果**：在 MuSiQue 上，**SAG 取得 64.1% / 80.0% (Recall@2/5)** 的表現，顯著超越了 HippoRAG 2（基於相同的 BGE-Large 模型）的 **49.5% / 65.1%**。
*   **客觀分析**：MuSiQue 包含高達 4 步的邏輯鏈，且經過反事實過濾以防止單步語意作弊。在這個最考驗「連結能力」的測試中，SAG 領先了近 15 個百分點。這證實了利用 SQL 進行確定性局部超邊鏈接，比在全域圖上運行 PageRank 擴散能更有效地保留深層證據。

##### 2. HotpotQA 數據集（2 步推論，橋梁與比較型問題）
*   **實驗結果**：**SAG 達到 91.6% / 96.5%**，HippoRAG 2 為 **78.4% / 94.4%**。
*   **客觀分析**：隨著推理跳數減少（僅 2 步），圖傳播的分數衰減效應減弱，因此兩者在 Recall@5 的差距縮小（僅差 2.1%）。然而，在更嚴苛的 **Recall@2** 上，SAG 依然領先 13.2%。這表明 SAG 在將最關鍵證據排到最前列（Top 2）的排序能力上表現更為穩定。

##### 3. 2WikiMultiHopQA 數據集（長實體鏈，包含罕見橋樑）
*   **實驗結果**：SAG 在 Recall@2 領先（82.3% vs 76.6%），但在 **Recall@5 微幅落後於 HippoRAG 2（88.0% vs 90.4%）**。
*   **客觀分析（系統漏洞暴露）**：
    2Wiki 數據集中含有極長且出現頻率極低的實體鏈。當某個「橋樑實體」在整個語料庫中出現頻率極低時，SAG 採用的**固定剪枝預算（Pruning Budget = 50）**可能會在線上擴展階段將其提前過濾掉。相反，HippoRAG 的全域 PageRank 能通過全圖傳播到達這些低頻節點。這指出了 SAG 在處理「長尾罕見實體鏈」時的潛在缺點。

---

#### 5.2 消融實驗一：事件結構 (Event) vs. 三元組 (Triples) 的語意保留價值

為了解釋 SAG 效能領先的來源，作者在 MuSiQue 數據集上比較了「事件超邊索引」與「拆解成三元組索引」的差異。

*(請在此處插入：論文 Table 3，展示 Triple 與 Hyperedge 在 R@1, R@2, R@5, R@10 的數值)*

*   **數據對比**：
    *   **Triple-based SAG** (拆成三元組)：77.1% (Recall@5)
    *   **Hyperedge SAG** (保留完整事件)：**80.0%** (Recall@5)
*   **客觀分析**：
    1.  **管線設計的勝利**：即使將 SAG 強行拆解成三元組（77.1%），其表現依然大幅優於 HippoRAG 2（65.1%），這證明了 **SAG 這套 SQL 檢索管線設計本身就存在系統性優勢**。
    2.  **超邊的增量價值**：保留完整事件（Hyperedge）帶來了額外 2.9% 的提升。因為一個事件記錄了 N 元關係，不需要像三元組那樣經歷多次 SQL Join 走訪，從而降低了每一次跳轉引入的剪枝損失。

---

#### 5.3 消融實驗二：動態擴展 (Expansion) 如何抓出隱藏證據？

此實驗評估了「Step 2：查詢時動態擴展」對檢索品質的實際貢獻。

*(請在此處插入：論文 Table 4，對比 H=0 (Without Expansion) 與 H=1 (With Expansion) 的數據)*

*   **數據對比**：
    *   **無擴展 (H=0)**：69.4% (Recall@5)
    *   **有擴展 (H=1, 預設)**：**80.0%** (Recall@5)
    *   *註：兩者的 Recall@1 幾乎沒有變化（35.7% vs 36.2%）。*
*   **客觀分析**：
    這組數據極具說服力。擴展機制**完全沒有**提升第一名（Recall@1）的命中率，這意味著它沒有改善已有種子事件的排序。然而，它讓 Recall@5 暴增了 10.6%。這證實了**動態擴展的作用是「雪中送炭」——它找回了那些與問題語意不相關、向量檢索絕對找不到，但對於推論鏈至關重要的「中間證據（Bridge Evidence）」**。

#### 5.4 系統穩定性驗證：對底層 Embedding 模型的依賴度測試

圖譜檢索（如 HippoRAG）通常對 Embedding 模型的品質極為敏感，因為圖上節點的初始分數是由向量相似度決定的。

*(請在此處插入：論文 Table 8，展示更換為強大模型 NV-Embed-v2 後，SAG 與 HippoRAG 2 的表現變化)*

*   **數據對比**：
    *   **HippoRAG 2**：更換為強大的 NV-Embed-v2 後，Recall@5 從 **65.1% 暴漲到 74.6%**（提升近 10%）。
    *   **SAG**：更換模型後，Recall@5 僅從 **80.0% 微幅變動至 81.7%**（提升 1.7%）。
*   **客觀分析**：
    這反映了兩者在學術與工程定位上的本質差異。HippoRAG 的多跳極度依賴向量打分，因此模型變弱時，誤差會隨傳播路徑放大。而 **SAG 的結構化收益主要來自於基於字串精確匹配的 SQL JOIN，這與 Embedding 的品質無關**。這證明了 SAG 架構在工程實務上的高魯棒性：即使使用較弱、較便宜的 Embedding 模型，系統依然能維持極高的多步檢索水準。


### 六、 系統侷限性與未來優化方向

作為一項具有強烈工程落地導向的研究，SAG 雖然在多步檢索的效能與成本上取得了良好的平衡，但在特定的極端場景下，其為了換取系統簡潔性與寫入吞吐量所做的「設計妥協」，也帶來了相應的系統侷限性。本章節將客觀剖析這些侷限，並提出相應的優化方向。

---

#### 6.1 剪枝預算 (Pruning Budget) 導致的罕見實體遺漏風險

在線上擴展階段（Step 2），為了防止「高頻中心節點（Hub Nodes）」（如年份、國家名）引發關聯事件數量的組合爆炸，系統設定了 $50$ 的實體前線（Entity Frontier）剪枝預算。

*   **系統風險**：
    目前的剪枝策略主要依賴實體向量與原始查詢（Query）的相似度進行排序過濾。然而，在極深推論鏈（如 2Wiki 數據集）的場景中，某些扮演關鍵邏輯橋樑的實體，在語料庫中的出現頻率極低，且與原始問題的直接語意相關性極差。這類**「低頻但關鍵的橋樑實體」極易在此階段被類似「通用名詞」的高頻實體擠出 50 個預算之外**，導致檢索斷鏈。
*   **工程優化方向**：
    未來可引入類似資訊檢索中 **IDF（逆向文件頻率）** 的權重機制，或對實體進行頻率分層管理：給予低頻實體更高的擴展權重與專屬預算，防止其被高頻通用實體淹沒。

---

#### 6.2 輕量級實體策略的兩面刃：同義詞跨文件密度下降

SAG 線下階段的一大亮點是「完全不做全局實體對齊（Entity Merging）」，從而實現了無鎖的高效寫入。然而，這在檢索密度上帶來了副作用。

*   **系統風險**：
    若同一個實體在不同的原始 Chunk 中有著不同的字面寫法（例如 "Meta"、"Facebook" 或 "祖克柏"、"Zuckerberg"），雖然線上階段有實體向量模糊匹配（閾值 0.9）進行保底，但如果這些寫法在向量空間中的距離不夠近，系統就會在 SQL 中將它們視為兩個完全無關的索引點。這會**人為地降低跨文件實體鏈接的密度（Connection Density）**，導致漏檢。
*   **工程優化方向**：
    在不破壞線下寫入獨立性的前提下，可以在資料庫中引入一個**輕量級的「實體別名表（Entity Alias Table）」**，在背景進行非同步的實體聚合，或在線上查詢時引入更強的同義詞映射邏輯。

---

#### 3.3 邁向 Agent 記憶體：從增量寫入到版本控制

目前 SAG 的設計主要針對「唯讀文檔庫（Read-heavy archive）」的增量追加。但在實際的 Agent 長期記憶體場景中，知識並非一成不變。

*   **系統風險**：
    Agent 記憶體需要處理**知識的更新、覆蓋與過期**。例如，使用者的偏好發生改變、工作狀態已從「未完成」變更為「已完成」，或者歷史事實發生修正。目前 SAG 的「事件-實體」索引僅支持 Append-only 追加，當資料庫中同時存在相互衝突的新舊事件時，系統缺乏原生機制來識別「哪一個事件是最新且有效的」。
*   **工程優化方向**：
    需要將 SAG 索引擴展為支持**時間感知（Temporal-awareness）與版本控制（Version Substrate）**的動態記憶庫。在 SQL Schema 中引入「時間戳記」、「生效標記」以及「事件依賴關係鏈」，使檢索路徑能自動過濾掉已被宣告無效或被新事件覆蓋的歷史資訊。


   ### 結論 (Conclusion)

SAG 的成功實踐，為 RAG 與 Agent 數據基礎設施的演進提供了一條務實且新穎的思路。它證明了要在檢索階段實現穩健的多步推理，並不需要在線下建構昂貴、脆弱且難以維護的全局知識圖譜。相反地，透過「線下建立輕量級事件-實體索引，線上利用 SQL 進行動態超邊具現化」的設計，SAG 在傳統關聯式資料庫的基礎上，有效地解決了結構化關係檢索的難題。

對於 AI 軟體工程師而言，SAG 最核心的啟發在於**系統職責的精準重分配**。它避免了讓 LLM 去承擔高成本的圖走訪工作，也避免了讓向量搜尋去猜測嚴格的邏輯關聯，而是將這些任務交給運作數十年、極其成熟且高度優化的 SQL 資料庫引擎。這種「以數據庫結構設計替代複雜模型推理」的架構思維，不僅大幅降低了系統建置與 API 的調用成本，更實現了對生產環境至關重要的即時增量寫入能力。

儘管 SAG 目前在處理極長尾罕見實體與動態記憶版本控制上仍有優化空間，但其所展現的檢索可解釋性、工程易維護性以及對底層模型的高魯棒性，無疑為構建下一代大規模、高併發的 Agent 檢索增強基礎設施，奠定了一個極具參考價值的架構範式。
