# 從記得到會做：MSCE 如何把 agent 的雜亂經驗，治理成可信賴的 skill

## 前言

寫過 agent 系統的人大概都遇過這個場景：同一種任務，agent 做過十次，但第十一次還是從頭推理一遍，該找哪個設定檔、該用哪個工具指令，全部重新摸索一次。記憶系統丟回去的是一堆過去的對話紀錄，agent 得自己重新咀嚼，等於每次都在繳一樣的學費。

這篇論文提出的 MSCE（Memory–Skill Co-Evolution）想解決的正是這件事：讓 agent 從「記得發生過什麼」進化到「直接會做」。但它的重點不是「把軌跡蒸餾成 skill」這個想法本身——這件事其實已經有人做過。MSCE 真正的貢獻，是在蒸餾這一步前面，插入一整層治理機制：只有真的有證據支撐、效果驗證過、表現夠穩定的經驗，才准許升格成正式可呼叫的 skill。沒有這層把關，直接把雜訊軌跡硬蒸餾出來的 skill，很容易變成 over-specific、只在特定情境才管用的脆弱規則。

這篇文章會照著論文的邏輯，從記憶怎麼分層存放、policy 怎麼被歸納出來、skill 怎麼晉升與汰換，一路講到實驗結果驗證了什麼、又留下哪些沒交代清楚的地方。

## 記憶系統的老問題，MSCE 怎麼分工解決

作者在論文裡點出四個現有記憶系統的通病：

1. **記憶只是被動參考，沒變成能力**：軌跡被當成 context 整包丟回去，agent 每次都得重新推理一遍。
2. **原始軌跡太雜，直接蒸餾會生出脆弱的 skill**：失敗嘗試、瞎摸索、環境雜訊全部混在一起，硬蒸餾容易 overfit 到單一情境。
3. **終端回饋 sparse 又延遲，很難判斷是哪一步做對了**：一個任務往往只在結束時給一個分數，中間哪一步是關鍵轉折，沒人告訴你。
4. **一個能用的 skill 需要的東西遠不只是「成功步驟」**：還得有觸發條件、適用邊界、驗證規則、上線後的生命週期維護。

MSCE 用四個機制分別對應：分層記憶架構解決①②、跨 episode 的支持度門檻解決②、reflection-weighted value backfilling 解決③、skill 的完整結構加生命週期管理解決④。接下來就照這個順序，一個一個拆開講。

## 整體架構：從一堆雜訊軌跡，到一個可信賴的 skill

MSCE 分成建構階段跟使用階段兩條路。建構階段把原始軌跡一路往上蒸餾：

1. 先正規化成 **L1 Trace**（step 級別、留著證據）。
2. 再從多個不同 episode 裡找出重複模式，誘發成 **L2 Policy**（泛化過的做法）。
3. 通過「有正面 gain」跟「表現穩定」兩關後，正式晉升成 **Skill**。
4. 持續監控它上線後的實際表現，在 probationary、active、archived 三種狀態之間流動。

使用階段則反過來：agent 執行任務時，優先比對有沒有現成的 active skill 可以直接用；沒匹配到、或匹配到但失敗了，才退回去查 L1 trace；只有在 agent 表現出「不確定當前環境長什麼樣」的時候，才會再去查 L3 環境認知——這一層只提供環境參數，不會覆蓋 skill 原本的程序。

## 三層記憶：從逐步證據到宣告式知識

### L1：先把每一步存清楚，而且留著證據

MSCE 最底層存的不是整段對話，而是拆到「每一個 step」的紀錄，結構是 `(狀態, 動作, 觀察結果, 自我反思, 價值)` 五個欄位。論文裡有交代狀態欄位會經過「截斷、去重、規則式脫敏」處理，但沒給出具體的截斷演算法——這是論文自己留下的空白，後面會有一整節專門整理這類地方。

比較值得注意的是它對「episode」的定義。一個 episode 是回饋跟更新的單位，可能包含好幾個 step。系統用一個分類器判斷新進來的訊息跟前一個 episode 的關係：是在修正同一件事（延續舊 episode）、是延伸同一個目標（關掉舊的、開新的），還是完全無關的新任務（直接開新的）。這個邊界判斷做得準不準，直接影響後面 value backfilling 要把分數攤給哪些 step。

### L2：兩個看似無關的失敗，怎麼長成同一條 policy

L2 存的不是單一 step，而是「一群相似 trace 背後共同的模式」，結構是 `(觸發條件, 程序, 驗證規則, 適用邊界, 支持證據)`。一條新 trace 要先通過一個很低的價值門檻（只是過濾雜訊），才有資格被拿去跟既有 policy 比對相似度；比對不到既有的，就先丟進候選池，等累積到「至少兩個不同 episode」的證據，才會觸發 LLM 真正歸納出一條新 policy。

要求「不同 episode」而不是單純湊夠筆數，是刻意設計：同一段長對話裡重複出現的雜訊，不該被誤判成一個通用規律。論文附錄給了一個具體例子，剛好示範這個門檻怎麼運作：

- **任務 A**：在 Alpine 容器裡裝 `lxml` 失敗，因為缺 C 函式庫，裝完系統依賴後成功。
- **任務 B**：在 Debian 容器裝 `psycopg2` 失敗，因為缺 `pg_config`，一樣是裝完系統依賴後成功。

這兩個任務表面上完全不同——作業系統不同、套件也不同——但抽象模式一致：「容器裡 pip 因為缺系統函式庫而失敗」。因為湊到了兩個不同 episode 的證據，MSCE 才誘發出一條泛化 policy：先解析缺了什麼、判斷該用 `apk` 還是 `apt-get`、裝對應的開發套件、然後重試。原始數據長這樣：

### L3：只講環境長什麼樣，不講該怎麼做

L2 講的是「怎麼做」（程序性知識），L3 講的是「這個環境長什麼樣」（宣告式知識），兩者故意分開。論文舉的對照很直白：L3 該寫的是「Alpine 容器只內建 Python 的純 Python 套件層」這種環境事實，而「在 Alpine 遇到 pip 失敗時執行 apk add」這種帶指令性動詞的寫法，是被 L3 的 prompt 明文禁止的——那是 L2 的工作。

L3 的生成流程是：活躍的 L2 policy 先依 domain 分桶，桶裡數量夠多之後，用 cohort 的語意相似度篩選、呼叫 LLM 歸納，再決定是併入既有的環境認知還是新建一筆。至於信心分數怎麼隨新證據增減，論文只有「支持就增加、反駁就減少」的定性描述，沒有給出實際公式——這也是論文留白比較多的一塊。

L3 上線後不會蓋掉 skill 原本的程序骨架，只負責提供環境參數去「實例化」它。舉例來說，一個「安裝依賴」skill 的步驟固定是解析缺什麼、判斷套件管理工具、安裝、重試，但具體是 `apk` 還是 `apt-get` 還是 `brew`，就是 L3 判斷當前環境後填進去的變數。而且它不是每次都會被查——只有 agent 表現出「結構性不確定」（比如不知道測試檔案放哪裡）時才會觸發，但論文沒有講清楚這個「不確定」具體怎麼被偵測出來。

## 一個分數，怎麼公平分給每一個 step

一個 episode 結束時，通常只會拿到一個終端分數。但這個 episode 裡面往往有好幾個 step，獎勵該怎麼往回分配？MSCE 用的公式是：

```
V(這一步) = α × 終端分數 + (1 − α) × γ × V(下一步)
```

其中 γ = 0.9 是折扣因子，α 則是「反思權重」，由另一個獨立的 LLM 依「忠實度、因果洞察、可遷移性、具體程度」四個維度打分。直覺上，如果一個 step 的自我反思寫得有洞察力（α 高），代表這一步是關鍵轉折點，值得直接跟終端結果掛鉤；如果反思空洞（α 低），這一步的價值就主要靠「後面接的步驟表現好不好」去補。

這個結構其實很像強化學習裡的 TD（λ）/eligibility trace——用折扣把未來的價值往回傳。差別在於，這裡的混合權重不是一個固定常數，而是每個 step 動態算出來、由反思品質決定的 α。論文附錄給了一個手算範例：某個 episode 最終拿到 0.8 分，倒數第二步的 α 是 0.7，那麼這一步的價值就是 0.7×0.8 + 0.3×0.9×0.8 = 0.776。回頭對照前面 L2 那張表裡的 α 跟 V 欄位，套的正是這條公式。

這裡有個很現實的限制：α 不是客觀公式算出來的，是 LLM 當裁判給的啟發式分數。論文自己在 Limitations 裡也承認，這類治理訊號本質上是 heuristic，不是嚴謹的因果推論——這點在評估要不要把這套系統搬進正式生產環境時，值得放在心上。

## Skill 怎麼晉升、又怎麼被照顧一輩子

### 兩道晉升關卡

L2 policy 要升格成正式 skill，得先過兩關：一是 gain 要是正的（門檻設得很低，只要有正面貢獻就過）；二是「穩定性」——最近的新證據不能大幅改寫既有的觸發條件跟程序。第二關聽起來合理，但論文對「怎麼量化穩定性」只有定性描述，沒給出具體演算法，這是另一個留白。

過關之後，晉升不只是格式轉換。Skill 相對 policy 多了三個欄位：明確的證據錨點、決策指引（建議做什麼、避免什麼），以及可信度分數。而且草稿生成之後，還得通過一個**非 LLM**、規則式的驗證器：檢查 schema 是否完整、引用的證據 ID 是否真的存在、宣稱要用的工具是不是真的出現在證據裡而不是憑空發明。任何一項沒通過，草稿直接丟棄。這個設計的用意很明確——用規則邏輯把關，而不是找另一個 LLM 去審查 LLM 生成的內容，避免「幻覺配上幻覺」的循環。

可信度分數的公式也用了一個常見的統計手法：

```
η = (成功次數 + 1) / (總呼叫次數 + 2)
```

分子分母各加的 1、2 是一種 shrinkage（收縮）設計：呼叫次數還很少的時候，η 會被拉向中性的 0.5，避免小樣本就過度自信地判定一個 skill 好不好用。這跟前面 policy gain 計算裡「對照組樣本少時往中性值收縮」的手法，其實是同一套精神，論文裡至少用了兩次。

### 上線後的生命週期

## 實驗結果：治理本身，才是真正有效的地方

論文主要在 EvoAgentBench（涵蓋資訊檢索、數學推理、軟體工程、程式碼實作、知識問答五個領域）跟 LoCoMo（測長對話記憶一致性）兩個 benchmark 上驗證。比較對象分三類：純記憶型（不主動蒸餾 skill）、軌跡直接蒸餾成 skill 型（MSCE 真正的對手）、以及沒有任何記憶機制的 Vanilla Agent 當下限對照。所有方法都用同一套 runtime 跟 backbone 模型，確保比較基礎公平。

### 主結果：五個領域全面領先

![一張表格，列出 Vanilla Agent、Memento 等多個方法在資訊檢索、數學推理、軟體工程、程式碼實作、知識問答五個領域的 Pass@1 準確率與成本數字，MSCE 一列的準確率在各領域都是最高或並列最高。](img-002)
*圖 4 — MSCE 在 EvoAgentBench 五個領域的主要結果。（來源：原始論文 Table 1。）*

MSCE 在五個領域全部拿到最好或並列最好的準確率，軟體工程領域提升最多（+15.39 分，但成本也跟著從 37.3 上升到 40.8 個 turn），程式碼實作領域則是準確率打平最強對手、但成本直接砍半（從 3.9 降到 2.0 個 turn）。

有個細節論文自己沒有深入分析，但很值得留意：扣掉 MSCE 之後表現最好的 baseline，在資訊檢索、數學推理、軟體工程這三個領域，反而是**純記憶型**方法（不主動蒸餾 skill），只有程式碼實作這個領域是**軌跡直接蒸餾**型方法表現最好。一個可能的解讀是：沒有治理的蒸餾 skill 可能會主動誤導 agent 走錯方向，比乾脆不蒸餾還糟；但程式碼任務的對錯判準明確（跑測試案例），結構化程度高，即使未經治理的蒸餾也比較不容易被誤用。這是筆者自己的推論，論文並未明講。

在 LoCoMo 這個長對話記憶測試上，MSCE 在單跳、多跳、時序推理、整體分數、F1 分數上都拿到最高，但在開放域問題這一項反而輸給 Vanilla Agent（39.58 分 vs. MSCE 的 28.13 分）。這暗示開放域問題可能更依賴模型本身的通用知識，而不是檢索出來的長期記憶——記憶系統在這類問題上幫助有限，甚至可能變成雜訊。

### 消融實驗：最能說明「治理」有沒有用的一組數據

如果只能看這篇論文的一組實驗，消融研究（ablation study）是最值得看的：

![一張表格，比較完整版 MSCE 與五種消融版本（拿掉分層架構、拿掉 L3、拿掉價值校準、拿掉反思加權、拿掉 skill 結晶化）在五個領域的準確率與成本。](img-004)
*圖 5 — MSCE 各組件的消融實驗結果。（來源：原始論文 Table 3。）*

掉分幅度由大到小排列：

1. **完全拿掉分層架構**——掉最多，軟體工程領域掉 19.23 分，程式碼任務的成本從 2.0 一路飆到 5.3 個 turn。
2. **拿掉 skill 結晶化**——掉 6 到 11 分不等，而且所有領域的成本都同時上升。
3. **拿掉反思加權**——影響次之。
4. **拿掉 L3 或價值校準**——兩者影響差不多，是五個消融版本裡掉最少的。

這組數字說明了幾件事。第一，MSCE 真正的核心價值是「治理」這件事本身，不只是「分層記憶」這個架構——單純拿掉分層，掉分掉最兇，證明只是多存記憶、多檢索是不夠的。第二，skill 結晶化是組件層級消融裡貢獻最大的一項，拿掉之後準確率跟效率同時變差。第三，價值校準在每個領域都被證實必要——拿掉之後準確率全面下滑、成本全面上升，這也剛好印證了論文最核心的假設：未經治理的 skill 直接注入，反而會拖累整體表現。這不是空話，是有消融數據撐著的。

論文另外還做了跨領域遷移實驗（六組配對全部正提升，佐證學到的是可遷移的結構而非死記硬背）、長期累積實驗（累積的經驗越多，準確率單調上升，成本則是先升後降），以及模擬人類回饋的實驗（驗證獎勵量化機制確實有效，在知識問答跟軟體工程領域提升最明顯）。這幾組實驗方向都合理，但沒有帶來新的機制洞察，這裡就不逐一展開。

## 這篇論文沒告訴你的事

論文有個很一致的模式：凡是牽涉到**數字計算**的部分——gain、可信度、value backfilling、獎勵量化——都給得很仔細，公式明確。但凡是牽涉到「怎麼從自然語言或情境判斷出一個離散事件」的部分——穩定性怎麼判斷、使用者拒絕怎麼偵測、L2 候選池的分組訊號怎麼算、L3 該不該被觸發查詢——普遍只給了概念，沒有給出具體演算法或對應的 prompt。

其中最現實的一個問題是**完全沒有任何延遲數據**。整套治理管線疊了五、六層 LLM prompt（反思評分、獎勵量化、L2 歸納、L3 抽象、skill 草稿生成、驗證），Cost 指標用的是 turn 數或字元數這種代理指標，不是真實的時間測量。論文的 Limitations 只用一句話帶過「會帶來額外延遲跟成本」，沒有任何數字佐證。雖然線上更新是非同步設計，一定程度緩解了使用者等待的問題，但「新學到的 policy 或 skill 能不能來得及被下一個任務用上」這種時效性問題，論文完全沒有討論。這對想把這套系統真的搬進生產環境的人，是最大的一塊未知數。

## 結論

MSCE 的核心貢獻，不是「把 agent 的軌跡蒸餾成可呼叫的 skill」這個想法本身，而是在蒸餾這一步前面，插入一整層治理機制：分層記憶負責把雜訊過濾掉，跨 episode 的證據門檻確保歸納出來的是通用模式而非巧合，reflection-weighted value backfilling 用動態權重取代平均分攤終端回饋，skill 的完整結構加生命週期管理則確保上線後還能持續被監控、修正、汰換。消融實驗證實了這套治理機制確實在做事，尤其是 skill 結晶化跟價值校準這兩塊，拿掉之後準確率跟效率會同時受損。

即使不打算照抄整套系統架構，這篇論文有三個設計模式值得帶走：用中介治理層防止直接蒸餾的脆弱性、依訊號品質動態決定 credit assignment 而不是均勻分攤、用 shrinkage estimator 處理小樣本情境下的可信度估計。這三個手法在其他「從雜訊經驗裡篩選可靠訊號」的場景，一樣用得上。

工程落地的角度來看，這套系統目前還不夠成熟，最大的硬傷是完全沒有延遲數據——疊了這麼多層 LLM prompt 的治理管線，真實系統的延遲跟 API 成本完全沒被量化過。如果你考慮把類似的架構搬進正式產品，這一塊會是你自己得先量清楚的功課。
