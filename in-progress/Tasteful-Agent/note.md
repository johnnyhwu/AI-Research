# 論文筆記｜The Tasteful Agent：量測與訓練 agent 長任務決策的「品味」（Taste-Bench）

Oct 8, 2026 · @YHHW

## 三十秒版本

這篇論文的真正價值是一套「用 agent 已經跑過的軌跡，免費造出決策品質評測題」的配方；蒸餾與端到端的結果只能當方向性訊號。

- **問題：** LLM agent 做長任務時，中途的決策（要測哪個假設、沿用哪個實作）決定整體成敗。現有評測只看最後有沒有做完，沒有人量測決策本身的品質。論文把這種能力稱為 taste（品味）。
- **做法：** 同一個任務被 agent 嘗試多次，嘗試會在中途走向不同方向，最後結果一好一壞。把分歧點（decision fork，岔路口）之後的內容藏起來，只問模型「該選哪個方向」，答案就是紀錄下來的結果。不需要人工標註，共 502 題。
- **評測結果：** 14 個前沿模型中，最好的 GPT-5.6 Sol 只答對 59.7%，隨機猜的基準是 25%。決定性證據出現得越晚的題，模型越答不準。
- **訓練：** 讓一個「偷看過答案」的老師寫出推理，蒸餾給只看題目的學生。學生在沒見過的任務上，準確率從 30.0% 升到 47.9%。把學生的選擇寫成建議交給另一個 agent（executor），在 41 個 SWE-bench Pro 任務上成功率從 14.6% 升到 33.7%，每個岔路口都給正確建議的上限是 39.0%。
- **帶得走的：** 造題配方，以及兩個脫離論文也成立的觀念：二選一的評測要對調順序考兩次；forward KL 截斷時，保留老師機率最高的前 K 名比較自然。
- **一個保留：** 端到端實驗用的岔路口，是事先從同一任務的舊執行挖出來的。新任務沒有這些候選對，所以 33.7% 還不能當作「這套方法可以直接用在新任務上」的證據。

## 一、問題與挑戰

長任務裡，一個決策的好壞要很久之後才看得出來，所以 agent 的決策品質到目前為止都沒有被直接量測過。

### 背景：agent 的「品味」

LLM agent 正在做越來越長的任務，例如從點子一路做到論文的機器學習研究，或是跨多個版本演化一個大型軟體專案。這類任務中，agent 會做很多影響深遠的決定：要測哪個假設、要沿用哪個實作、下一個要跑哪個實驗。一個錯的決定在當下常常看起來很合理，代價要等 agent 已經花掉大半預算之後才浮現。

論文把「做出好的長程決策的能力」稱為 taste（品味）。

現有的 agent 評測（例如 SWE-bench 這類讓 agent 修真實 GitHub 問題的評測）叫做 end-to-end benchmark，意思是只報告 agent 最後有沒有完成任務，完全不報告中途每個決策的品質。

### 為什麼品味難量測：兩個困難

1. **後果延遲。** 做決定的當下，好選擇和壞選擇看起來一樣合理，差別要到後面才顯現。論文自己的例子：一份乾淨的實作和一份草率的實作，寫完的當下可以通過同樣的測試；乾淨實作的優勢，要等到之後每一次修改都變得比較容易時才看得出來。所以決策的價值只存在於「後面的工作」裡。
2. **判斷需要專家。** 要評斷一個決策好不好，需要深厚的領域知識。靠人工標註既貴又很難擴充到新領域。

### 論文的關鍵觀察

軌跡的後半段，就是前半段決策的事後證據。

實務上，agent 系統常常對同一個任務跑好幾次，這些嘗試會在中途走向不同方向。每一條分支最後都有紀錄下來的結果，所以哪個方向比較好，軌跡自己就帶著標籤。論文把這個分歧點稱為 decision fork（決策岔路口）。

出題方式：把軌跡凍結在岔路口，藏起後面所有的過程，只問模型「這兩個方向，你選哪個？」

### 為什麼一定要「同任務、同前綴」的比較

單一軌跡的結果，混雜了三件事：判斷的好壞、執行的品質、環境因素，所以看不出結果是不是判斷造成的。

如果兩次嘗試在岔路口之前完全相同（同一個任務、同一段前文），兩條分支的結果差異就主要來自岔路口的那個判斷。這是整篇論文的出發點。

這個假設不是百分之百成立：分支分開之後的執行品質仍然會影響結果。論文用後續的過濾步驟來處理，見 2.3。

## 二、方法

方法分六個部分：2.1 岔路口與標籤的數學定義、2.2 兩種造題法、2.3 過濾與人工審查、2.4 評測協議，以上是 Taste-Bench 這個評測集的建構；2.5 蒸餾與 2.6 端到端，是「品味可以訓練」的部分。

### 2.1 decision fork 的定義與標籤

一道題對應一個岔路口，標籤就是兩條分支中最終結果比較好的那一條。

**設定（論文 Section 2）。** 同一個任務 q 的多次嘗試，共用一段前綴 h\_t，到時間點 t 分成兩個候選方向 c\_1 與 c\_2。每條分支各自跑到結束，留下證據 E\_i（例如測試結果、研究分數）。再用一個函數 U 把證據換成一個數字，數字越大代表結果越好。

```latex
y = \arg\max_{i \in \{1,2\}} U(E_i)
```

- y：這道題的正確答案（標籤），是 1 或 2。
- i：分支編號。
- E\_i：第 i 條分支跑完後留下的證據。
- U：把證據換成一個分數的函數。
- arg max：取讓 U(E\_i) 最大的那個 i。

白話：誰的最終分數高，誰就是對的。

**一道題的形式與評分。** 題目是 x = (q, h\_t, c\_1, c\_2)，也就是任務、前綴、兩個候選，岔路口之後的所有內容都藏起來。受測模型 π 看到 x 後選一個，答案記為 π(x)。模型的品味估計值，就是 π(x) = y 的題數占全部題數的比例，也就是答對率：

```latex
\hat{T}(\pi) = \frac{\#\{x : \pi(x) = y\}}{N}
```

其中 N 是題目總數。

**用論文自己的例子驗算。** 請直接看 **Figure 1**，原文 caption：*"A decision fork from a machine-learning trajectory. The evaluated model chooses before the later losses reveal that candidate A is the better direction."* 意思是：一個機器學習軌跡中的岔路口；受測模型要在後面的 loss 揭曉 A 比較好之前，先做出選擇。

任務是訓練一個 masked language model。候選 A 是縮小模型、多訓練幾步，候選 B 是維持模型大小、少訓練幾步。很多步之後，A 的最終 loss 是 6.56，B 是 7.66（B 的訓練跑到逾時）。loss 越低越好，所以自編一個 U = −loss（論文沒有給這個例子的 U）：

| 項目 | 內容 |
| --- | --- |
| c\_1 | A：縮小模型、多訓練幾步 |
| c\_2 | B：維持模型大小、少訓練幾步 |
| E\_1, E\_2 | 最終 loss：6.56、7.66 |
| U(E\_1), U(E\_2) | −6.56、−7.66 |
| y | U(E\_1) 較大，所以 y = 1，答案是 A |

**兩個符號與定義上的提醒。**

- 論文裡 E\_i（證據）和 𝔼\[·\]（期望值）都用同一個字母 E，是不同的東西。
- 論文說「好品味就是選期望結果較高的方向」，但公式 (1) 的標籤只用每條分支跑一次的實際結果。一次的結果含有運氣成分，所以標籤嚴格說是「這一次誰贏」，不等於「期望上誰比較好」。論文靠 2.3 的過濾來降低這個問題。

### 2.2 兩種造題法：parallel 與 detour

岔路口有兩個來源：兩次獨立嘗試走向不同方向（parallel），或是同一次嘗試裡 agent 走錯後自己改正（detour）。兩種都由同一個 generator 模型（GPT-5.6 Sol，high reasoning effort）讀軌跡之後，找出岔路口並寫成題目。兩種的差別與它們對標籤的影響，見【概念 1】。

**Parallel（平行軌跡，論文 Section 3.1）。** 抓的是 agent 一路都沒發現的錯誤。

1. 在同一個任務裡，挑一次成功、一次失敗的嘗試配成一對（每個任務最多配 8 對，同一個模型、同一個推理設定的嘗試優先配對）。
2. generator 讀完兩份完整軌跡，各自找出決策點。
3. 成功那次在決策點之前的部分當作前綴；兩個方向各寫成一段簡短、中性的描述，當作兩個候選。
4. 成功的那條分支就是答案。

**Detour（繞路軌跡，論文 Section 3.2）。** 抓的是 agent 走錯、碰壁之後自己改正的錯誤。

1. generator 讀一份完整軌跡和它的結果，依序找出三件事：agent 選了某個方向、觀察到的失敗讓這個方向結束、agent 改走另一個方向並完成任務。
2. 岔路口放在「agent 開始走被放棄方向」的前一步，前面的部分當前綴。
3. 兩個候選是「被放棄的方向」和「後來的改正」，用平行的措辭寫成。
4. 改正的方向是答案，因為被放棄的方向產生了可觀察的失敗，改正則完成了任務。

這個構造測的是：受測模型能不能比當時行動的 agent 更早看出失敗。

**generator 的防呆規則（Appendix A.2、A.3）。** 這些規則是造題品質的關鍵，也是這套配方可以搬走的部分：

- detour 必須引用四段軌跡原文，依序是：選擇被放棄方向的那一步、使它結束的失敗、選擇改正的那一步、改正成功的證據。程式會機械地檢查三件事：原文真的出現在被引用的那一步、四步的順序正確、失敗那段確實有失敗訊號（例如非零的結束碼或錯誤訊息）。任何一項不過就丟掉。
- 如果「較好的方向」只有看到失敗之後才說得出來，就拒絕這條軌跡，因為這樣的題目只是事後諸葛，不需要判斷力。
- 兩個候選必須都是當下合理的選擇，不能有稻草人，措辭也要平行、長度與語氣相近，不能出現「正確地」「較好」這類洩漏答案的詞。
- parallel 要拒絕「結果差異主要來自打錯字、當機、運氣、缺套件」等跟方向無關的情況。

**兩個例子（Appendix B）。**

- *Parallel，工程類：* 改 Element Web 的伺服器探索驗證邏輯。候選 A：只挑出五個欄位放進設定；候選 B：把探索到的整個認證區塊直接指派進去。答案是 A，因為 B 多帶了狀態標記和錯誤欄位，而隱藏測試用 deep equality 只比對那五個欄位。
- *Detour，工程類：* 改 Ansible 的 role 文件，要加入缺少 metadata 時的標準 placeholder。agent 先選候選 B（直接擴充 helper 函式的預設回傳結構），單元測試 3 個失敗，因為既有測試直接呼叫這些 helper 並預期原本的輸出格式。後來改成候選 A（把 placeholder 放在呼叫路徑上），28 個全過。答案是 A。

**請直接看 Figure 2。** 原文 caption：*"Construction and filtering of Taste-Bench. The parallel construction contrasts branches of the same task, while the detour construction contrasts an abandoned direction with the later recovery. …"* 意思是：Taste-Bench 的建構與過濾；parallel 比較同一任務的不同分支，detour 比較被放棄的方向與後來的改正；後半說明過濾階段（見 2.3）。

**一個讀法上的提醒（推論，不是論文原文）。** parallel 有真正的對照：兩條分支在岔路口前完全相同。detour 沒有另一條平行的分支，「原方向失敗、改正成功」只是這一次執行發生的事，原方向換個執行方式也許也能成功。所以 detour 標籤的可信度，比 parallel 更依賴 generator 的規則與後面的過濾。

### 2.3 過濾與人工審查

generator 提出的 4,657 個候選岔路口，最後只有 10.8%、也就是 502 題通過全部過濾。

**原料（論文 Section 3.3、Appendix A.1）。**

- 工程類：作者自己讓 GPT-5.4 與 GPT-5.5 的 agent 在 517 個 SWE-bench Pro 任務上跑出 2,677 條有評分的軌跡。
- 研究類：1,132 次 agent 執行，來自 47 個 AI R&D 任務（RE-Bench 與 HCAST 的研究子集），軌跡取自 METR 公開釋出的 MALT 資料集。

**漏斗。** 4,657 個候選 → 1,809 個通過 generator 自己依 rubric 的檢查（generator 被要求「證據不乾淨就拒絕」，所以自己就會丟掉大半）→ 729 個通過過濾一 → 502 題。最終的 502 題分成四格：

|  | 平行（parallel） | 繞路（detour） | 合計 |
| --- | --- | --- | --- |
| 工程 | 124 | 266 | 390 |
| 研究 | 48 | 64 | 112 |

請直接看 **Figure 8**，原文 caption：*"Filtering yield per cell. Each band is one cell of the release, and its width is proportional to the number of candidate forks that remain at the indicated stage. …"* 意思是：每一格題型的篩選產出，帶子的寬度正比於各階段剩下的候選數量。逐格的提出數與釋出數在 **Table 2**（*"Proposed and released questions by cell."*）。

**兩道過濾。** 通過 rubric 的候選仍然可能不是好題目，論文用四個裁判模型（Kimi K2.5、GPT-4.1、Llama 4 Maverick、Mistral Large 3，都不是 generator）過濾兩次：

|  | 過濾一：Trivial（太簡單） | 過濾二：Undecidable（無法判定） |
| --- | --- | --- |
| 裁判看到什麼 | 只有兩個候選的文字，沒有任務和軌跡 | 完整紀錄：任務、前綴、兩條分支的完整後續、最終結果 |
| 剔除條件 | 四個裁判全部答對 | 只要有一個裁判不同意標籤 |
| 在擋什麼 | 光看措辭就能猜到答案的題 | 標籤和完整紀錄對不上的題 |

所以釋出的每一題都同時滿足：把軌跡藏起來時，至少有一個裁判答錯；把完整紀錄攤開時，四個裁判都認同標籤。

**兩個被剔除的例子（Appendix A.4）。**

- *Trivial：* 候選 A 寫著「把三題已知會過的答案寫死，其他題一律回傳空字串」，候選 B 是正常的通用流程。光看措辭就知道選 B，被剔除。
- *Undecidable：* 標籤說 A（單一像素攻擊）對，但前綴裡最後一次量測顯示 B（多策略組合）的成功率比較高（0.80 對 0.43）。標籤只是因為 B 後來在全量執行時逾時，而任務根本沒有寫時間限制，所以裁判不認同，被剔除。

**人工審查。** 作者抽 100 題（70 題是正式題，15 題被 trivial 過濾剔除，15 題被 undecidable 過濾剔除），請兩位審查員分兩階段作答：先選自己會選哪個方向，再看後續過程與結果的摘要，判斷哪個決策比較好（A、B、或兩者差不多）。結果：在有明確 A/B 判斷的 172 次判斷中，170 次與自動標籤一致（98.8%）；兩位審查員互相比較，一致率 98.6%，Cohen's κ = 0.973。這些數字怎麼讀、為什麼是 172 和 74 兩個不同的分母，見【概念 2】。審查員是看過結果才判斷的，所以這驗證的是「標籤和紀錄對得上」。

詳細數字在 **Table 9**（*"Human review after outcome disclosure. …"*，看過結果後的人工審查，每位審查員的保留判斷數與標籤一致率）。

### 2.4 評測協議

每一題都考兩次、把 A、B 的順序對調，兩次都答對才算對，目的是排除「模型只是偏好某個位置」造成的假分數。

**要解決的問題。** position bias（位置偏誤）指模型傾向選第一個或第二個選項，跟內容無關。二選一的題目最容易受它影響，光是對調順序，很多模型的答案就會改變。

**做法（Section 3.4）。**

1. 第一次：用每題固定的種子順序呈現 A、B（所有模型共用同一個順序）。
2. 第二次：完全反過來。
3. 兩次都答對，這題才算對。無法解析出答案的回應算錯。

每個受測模型收到相同的 system message 與 user message，要求只輸出一行 `ANSWER: X`，這樣答案容易抽取與計分。

**這個設計的結果：**

| 模型行為 | 分數 |
| --- | --- |
| 每次各 1/2 的機率亂猜 | 1/2 × 1/2 = 25% |
| 永遠選同一個位置 | 0%（兩次中必有一次錯） |

所以這個指標的隨機基準線是 25%，不是 50%。

**三個指標的定義。**

- accuracy（嚴格準確率）：兩次都答對的題數占全部題數的比例，這是主要指標。
- mean accuracy：把 502 × 2 = 1,004 次作答各自計分，只對一次的題也算一半，比較寬鬆。
- Average：研究類與工程類各自算嚴格準確率後，取 1:1 平均。研究只有 112 題、工程有 390 題，但兩個領域各占一半權重，所以 Average 和用 502 題直接合併算出的數字不同。

**驗算，用 GPT-5.6 Sol（Table 4）。** 兩次都對（CC）292 題、只有第一次對（CW）25 題、只有第二次對（WC）29 題、兩次都錯（WW）156 題，加起來 502 題。直接合併的嚴格準確率是 292 / 502 = 58.2%。論文標題數字 59.7% 是 Average：工程 56.9%、研究 62.5%，取 1:1 平均得 (56.9 + 62.5) / 2 = 59.7%。

Accuracies are percentages. Unparsed is the number of responses without a parseable answer over the 1,004 presentations."* 意思是：14 個模型的完整結果，P 與 D 代表平行與繞路，Eng 與 Res 代表工程與研究，Unparsed 是 1,004 次作答中無法解析出答案的次數。

### 2.5 蒸餾：把品味訓練進學生模型

讓一個「偷看過答案」的老師寫出解題推理，再訓練一個「沒看過答案」的學生，在自己的輸入下寫出同樣的推理與選擇。老師和學生是同一個模型，差別只在輸入內容。

**先定義幾個詞。**

- distillation（蒸餾）：讓學生模型學老師模型的輸出行為。
- privileged teacher（有特權資訊的老師）：老師的輸入裡多了學生拿不到的資訊，這裡就是正確答案。
- demonstration：放進老師輸入的一小段文字，寫明「這個岔路口正確的做法是這個候選，要避開另一個」。
- LoRA：不改動原模型的權重，只訓練額外加上的小型低秩矩陣。這裡 rank 16、α = 32，約 7,970 萬個可訓練參數，在單張 A100 80GB 上每個 fold 訓練約兩小時。
- context distillation（上下文蒸餾）：把「放在輸入裡的資訊」的效果，透過訓練內化進模型權重。這是一般知識，不是論文內容；論文的做法屬於這一類。

**設定（Section 5.1、Appendix G）。**

1. 訓練資料是 390 道工程題，依任務切成兩份（各 195 題，每個 repository 兩份都有）。學生在一份上訓練、在另一份上測試，所以測試題的任務學生訓練時沒見過。
2. 基礎模型是 Qwen3.6-27B（凍結），老師與學生都是它。
3. 老師的輸入 = 題目 + demonstration；學生的輸入 = 題目本身（任務、前綴、兩個打亂順序的候選），跟評測時受測模型看到的一模一樣。
4. 每題 A、B 兩種順序各一筆（兩個 view）。老師對每個 view 以 temperature 1.0 產生一段推理，上限 3,072 個 token，推理區塊格式正確且至少 32 個 token 才保留，而且兩個 view 都保留的題才進訓練。兩份分別保留 328 與 311 筆推理，對應 156 與 142 題；老師在這些保留的推理中，選到正確候選的有 328/328 與 310/311。
5. 訓練目標：學生在自己的輸入下，產生老師那段推理與最後的選擇。

請直接看 **Figure 6 左半部**，原文 caption：*"Overview of distillation and advice injection. Left. We distill the reasoning of a teacher that has seen the supported candidate into a student that sees only the question. …"* 意思是：左半是把「看過正確候選的老師」的推理，蒸餾給「只看到題目的學生」；右半是評測時把學生的判斷寫成建議，由固定的 executor 完成任務（見 2.6）。

&#91;embedded content: 蒸餾的兩個階段 · 階段一 5 個方塊、階段二 3 個方塊\]

階段一：老師看到答案寫出推理，學生在老師寫的每個位置預測下一個字，兩邊分布的差異就是損失。階段二：學生改用自己寫的推理，只在最後的 A／B 選擇位置，對標準答案訓練。

**為什麼蒸餾「推理」，而不是直接學標籤。** 每一題只有一個二選一的標籤，沒有中間推理。論文的理由是：只用標籤微調，模型會背答案而沒有學到判斷。底層道理（一般知識，不是論文內容）：每個學生只用約 195 題訓練，模型卻有 270 億個參數，損失只算在一個答案 token 上時，最省力的做法是記住這題的表面特徵對應哪個答案。推理讓每題多出幾百個要擬合的 token，模型更難只靠背表面特徵降低損失。論文沒有附「只學標籤」的對照實驗，這是論文給的理由。

**損失函數：forward KL。** KL 散度衡量兩個機率分布差多少，兩個分布完全一樣時為 0，差越多越大。在老師寫出的推理的每一個位置 t，兩邊讀同一段前文，各自預測下一個 token，損失是：

```latex
\mathcal{L}_t = \sum_{v} p_T(v \mid c_T, y_{<t}) \, \log \frac{p_T(v \mid c_T, y_{<t})}{p_S(v \mid c_S, y_{<t})}
```

- t：推理中的第幾個位置。
- v：下一個可能的 token。
- y\_{\<t}：這個位置之前已經寫出的推理內容，由老師的輸出取樣而來。
- c\_T、c\_S：老師的輸入（題目 + demonstration）與學生的輸入（只有題目）。
- p\_T、p\_S：老師、學生在這個位置，對每個 v 給的機率。

白話：兩邊讀同一段推理的前半，各自猜下一個字，差越多，損失越大，訓練就把學生的猜法拉向老師。自編例子：某位置只看三個 token，老師的機率是 0.7、0.2、0.1，學生是 0.4、0.4、0.2，損失 = 0.7 ln(0.7/0.4) + 0.2 ln(0.2/0.4) + 0.1 ln(0.1/0.2) ≈ 0.392 − 0.139 − 0.069 = 0.184；學生和老師一模一樣時為 0。

實作上為了省算力有幾個截斷與設定：推理位置只在一小批 token 上算並把其餘合成一格、最後的選擇位置只比 A 與 B、長推理最多抽 512 個位置，細節見【概念 3】。為什麼這個 KL 要在「老師寫的文字」上算，見【概念 4】。截斷時取誰的前 K 名，見【概念 5】。

**第二階段：校準（Appendix G.1）。** 蒸餾完之後，論文多加了一個小步驟。蒸餾時，學生的最終選擇是接在「老師寫的推理」後面學的；但實際考試時，學生接的是「自己寫的推理」。校準就是讓學生在自己的推理後面也能選對：

1. 學生對每道訓練題（A、B 兩種順序各一次）自己寫出推理。
2. 只在最後選擇的位置，用 cross-entropy 對標準答案訓練，推理部分不動。
3. 設定：學習率 1e-5（蒸餾的十分之一）、1 個 epoch、softmax temperature 2.0（讓機率分布變平，避免被推向極端自信），兩份分別用 306 與 320 個 view。

cross-entropy 衡量模型給正確答案多少機率：正確答案是 A 時，模型給 A 的機率 0.55，損失 −ln 0.55 ≈ 0.60；給 0.90，損失 −ln 0.90 ≈ 0.11。為什麼需要這一步，論文沒有解釋，上面「訓練與考試接的推理不同」是推論。校準這一步直接用了標準答案，正文 Section 5.1 沒提它，只在附錄 G.1 寫到；論文也沒有報告校準前後的準確率差異。

**洩漏控制（輕描淡寫，附一個疑慮）。** 要防的事：老師的輸出是看過 demonstration 才寫出來的，如果輸出裡混了「只有看過答案才寫得出來」的內容，學生被訓練去寫這些內容，就會學成「假裝有依據，然後猜」。論文的做法稱為結構性控制：選擇限定成 A 或 B，老師的輸出到最終答案就結束，所以輸出裡沒有任何一段是照抄 demonstration 的文字。這個控制屬於第一階段（蒸餾），第二階段（校準）用的是學生自己寫的推理，沒有這個風險。

疑慮：結構性控制只擋了答案欄位。推理那段仍是自由生成的文字，老師可以用自己的話轉述 demonstration 的內容，例如「既有測試會直接呼叫這個 helper」，這種轉述不算照抄，控制擋不到；論文也沒有報告這方面的檢查數據。學生學到的有多少是真判斷，要看 held-out 的結果（見 3.3）。

### 2.6 端到端：把學生的判斷寫成建議交給 executor

學生不親自寫程式，只在每個岔路口給一則建議；另一個固定的 agent（executor）讀完建議再去做任務，看成功率有沒有提高。

**流程（Section 5.3、Appendix H）。**

1. 每個 held-out 任務事先已有幾個岔路口（41 個任務共 98 個），岔路口與兩個候選的文字，是 2.2 的流程從這些任務的舊執行挖出來的。
2. 學生對每個岔路口選一個候選。建議由「沒有訓練過這個任務的那個學生」產生（兩份 fold 各訓練一個學生）。
3. 每個岔路口寫成一則建議筆記：情境、要避開的候選、要採用的候選。
4. 所有筆記放在 executor 的第一則訊息裡、問題描述之前。
5. executor 獨立完成整個任務。
6. 用官方 SWE-bench Pro 的測試判定 patch 是否被接受，這就是成功。

**學生真正決定的只有一件事。** 建議的文字（情境、候選描述）是照模板組出來的，來自 generator 在 2.2 寫好的內容；學生只決定「哪個候選標成要避開、哪個標成要採用」，也就是每個岔路口一個二選一。選擇的規則：把學生對兩種順序下 A、B 兩個答案 token 的 log-odds 加總，取總和偏向的那個候選。

**建議整體的結構（Appendix H 模板，摘要）：**

```markdown
# Task-specific pitfall notes (from prior runs on this exact task)
固定開頭：這些是其他次執行的紀錄，不是你這次修改的證據；
         提交前必須自己跑相關測試或自己建一個檢查，看過實際輸出才能提交。

## Decision trap {n} [{parallel|detour}] (step {fork step})
### Situation where prior runs diverged   -> 岔路口的情境
### Known trap (this route produced a FAILING patch) -> 要避開的候選
### Route that avoided the trap in a prior run       -> 要採用的候選
固定結尾：選這條路線不等於驗證，行動後要自己產生證據。
```

**executor。** SWE-agent 1.1.0，模型是 Qwen3.6-27B（沒有蒸餾過，關閉 thinking，temperature 0.7），每次執行最多 75 次模型呼叫、每個指令 600 秒、總共 4,800 秒，在該任務的官方 SWE-bench Pro 容器中執行。41 個任務涵蓋 11 個 repository。

三種設定、結果與解讀見 3.4。

### 3.5 3.3 與 3.4 的差別：有沒有 executor

兩個實驗用的是同一批學生，但問的是不同的問題：

|  | 3.3 蒸餾遷移 | 3.4 端到端 |
| --- | --- | --- |
| 做的事 | 學生直接回答 Taste-Bench 的 A/B 題 | 學生的選擇寫成建議，交給 executor 去修 bug |
| 有 executor 嗎 | 沒有 | 有（Qwen3.6-27B 跑在 SWE-agent 上） |
| 衡量什麼 | 選對岔路口的比例（30.0% → 47.9%） | 任務成功率（14.6% → 33.7%） |
| 用到的測試資料 | 沒見過的那份 390 題工程題 | 41 個 held-out SWE-bench Pro 任務 |

白話：3.3 問「學生會不會選」，3.4 問「學生選完，有沒有讓別人做得更好」。3.4 每個任務的建議，都是由沒有訓練過該任務的那一個學生寫的，所以兩個實驗在「學生沒見過這個任務」這點上是一致的。

## 四、整體評價

這篇論文的價值集中在「造題的方法」；蒸餾與端到端的結果，目前只能當作方向性的正面訊號。

### 值得肯定的

1. **用既有軌跡的結果當免費標籤。** 同一任務的多次嘗試在中途分歧，最終結果就是答案，不需要專家標註，題庫還會隨著 agent 系統產出的軌跡一起長大。這個想法簡單、可搬、站得住。
2. **兩種造題法互補，而且分開統計。** parallel 抓 agent 沒發現的錯，detour 抓 agent 自己改正的錯。讀者看得到兩者的難度差異（繞路工程題最難，平均 35.9%），不是被混成一個平均數。
3. **標籤品質有人工驗證。** 兩位審查員與自動標籤的一致率 98.8%。這是看過結果之後的判斷，驗證的是標籤與紀錄對得上，但至少排除了標籤明顯標錯的疑慮。

### 一個閱讀時提出的疑慮：端到端實驗的部署缺口

端到端實驗用的岔路口與候選，是事先從同一任務的舊執行挖出來的（見 2.6）。論文原文也說，建議在新的一次執行開始前就已準備好。所以這個實驗測的是「有了現成的候選對，建議有沒有用」，不是「agent 遇到新任務時，自己判斷」。

整條流程拆開來看，論文測了哪些步驟：

| 步驟 | 論文有測嗎 |
| --- | --- |
| 學生對一道已經寫好的 A/B 題做選擇 | 有（沒見過的任務上 47.9%） |
| 偵測「現在是不是岔路口」 | 沒測 |
| 自己列出兩個措辭平行的候選 | 沒測 |
| 把選擇寫成建議交給 executor | 有 |

新任務沒有舊執行，所以「找岔路口、寫候選」這兩步在實際使用時要由 agent 自己完成，而這兩步論文都沒驗證。（推論：真實的候選不會像 Taste-Bench 那樣被整理成乾淨的平行措辭，這兩步各自也會出錯。）另外，這 41 個任務都是「至少挖出一個岔路口」的任務，等於只挑了確實有決策分歧的任務。

因此，33.7% 能證明的是「建議品質夠好時，executor 會受益」，不是「這套方法能在新任務上直接提升成功率」。

### 判斷：研究價值與工程價值

研究上，這篇的新意不高：用結果標註中途決策，是 process reward 這條線（用後續 rollout 的結果評每一步）的延伸；蒸餾部分是 context distillation 加上 SDPO 的變體。新的是把這些東西套到 agent 長任務的岔路口，並且給出一套可複製的造題流程。

工程上，價值集中在造題那一塊。如果手上有同一個任務的多次執行紀錄與結果，這套「挖岔路口、寫平行候選、再過濾」的流程，可以直接拿來參考，當成評測 agent 決策能力的資料來源。蒸餾與建議注入這一塊，目前只能當方向性的訊號：它顯示「把看過結果的判斷內化」是可行的方向，但還沒有證明能部署在新任務上。

## 五、值得帶走的東西

分兩類：第一類是這篇論文本身的貢獻，很少；第二類是讀這篇論文的過程中學到、脫離它也成立的觀念，通常才是真正的收穫。兩類都按耐久度排序。

### 第一類：這篇論文本身的貢獻

只有一項值得帶走：**造題配方**，也就是怎麼從 agent 已經跑過的軌跡，免費造出「決策品質」的評測題。

**為什麼這個配方成立。** 單一軌跡的結果混了判斷、執行品質與環境，看不出是不是判斷造成的。但同一個任務的兩次嘗試，如果在中途分歧之前完全相同，結果的差異就主要來自分歧點的那個決定，所以「誰的結果好」可以當成「這個決定好不好」的標籤。這個推論不依賴特定模型，也不依賴特定領域，所以耐久。

**需要的原料。** (1) 同一個任務的多次執行紀錄；(2) 每次執行一個可信的結果訊號（測試通過與否、評分）；(3) 一個能讀完整軌跡的 generator 模型。

**流程（偽代碼，對應 2.2、2.3）。**

```python
def build_taste_questions(runs_by_task, generator, judges):
    candidates = []
    for task, runs in runs_by_task.items():
        # 來源 A：平行軌跡 -- 同任務、一成一敗配成一對
        for good, bad in pair_opposite_outcomes(runs):
            candidates.append(generator.find_fork(task, good, bad))
        # 來源 B：繞路軌跡 -- 單次執行中「選 X -> 碰壁 -> 改選 Y -> 成功」
        for run in runs:
            candidates.append(generator.find_detour(task, run))

    # 第 1 道：generator 依 rubric 自己丟掉證據不乾淨的候選（大半被丟）
    qs = [c for c in candidates if c is not None and c.passes_rubric]

    # 第 2 道：太簡單的丟掉 -- 只看兩個候選的措辭，若所有裁判都答對，就沒測到判斷
    qs = [q for q in qs
          if not all(j.choose(q.cands) == q.label for j in judges)]

    # 第 3 道：無法判定的丟掉 -- 看完整紀錄，只要有裁判不同意標籤就丟
    qs = [q for q in qs
          if all(j.choose(q.cands, full_record=q.record) == q.label for j in judges)]
    return qs
```

**實務上要預期的產出率。** 論文從 4,657 個候選只留下 502 題（10.8%），所以要準備大約十倍的候選量。裁判不能包含 generator 本身。

**造題時最容易犯的錯，generator 的規則已經寫出對策（2.2）：** 結果差異其實來自打錯字、當機或運氣；較好的方向只有看到失敗之後才說得出來；兩個候選有一個是稻草人；措辭洩漏了答案。

### 第二類：脫離論文也成立的東西

#### 觀念一：二選一的評測要對調順序考兩次

**問題。** LLM 做二選一時有 position bias（位置偏誤）：傾向選第一個或第二個，跟內容無關。如果只考一次，一個永遠回答「A」的模型，在 A、B 各半的題庫上會得到 50%，而這個 50% 完全不代表它有判斷力。偏誤只有部分的模型也一樣，分數裡混了「碰巧順序對自己有利」的成分。

**做法。** 每題考兩次，第二次把兩個選項的順序完全對調，兩次都答對才算對。

```python
def strict_accuracy(model, questions):
    correct = 0
    for q in questions:
        a1 = model(q.task, q.prefix, first=q.cand_x, second=q.cand_y)  # 順序一
        a2 = model(q.task, q.prefix, first=q.cand_y, second=q.cand_x)  # 順序二（完全反過來）
        ok1 = (a1 == slot_of(q.label, order=1))
        ok2 = (a2 == slot_of(q.label, order=2))
        correct += (ok1 and ok2)     # 兩次都對才算
    return correct / len(questions)
```

**這會改變的事：**

- 隨機基準從 50% 變成 25%（每次 1/2，兩次都對 1/2 × 1/2）。
- 永遠選同一個位置的模型得 0%，而不是 50%。
- 答案會隨順序翻轉的題，不算作有品味。

**用論文的數字看效果。** GPT-5.6 Sol 在 502 題上：兩次都對 292、只對第一次 25、只對第二次 29、兩次都錯 156。其中 25 + 29 = 54 題（10.8%）的答案會隨順序改變，單考一次這些題會有一半被算成答對，嚴格計分把它們全部排除。嚴格準確率是 292 / 502 = 58.2%。

**代價與取捨。** 推論成本加倍，分數會比習慣的數字低；可以另外報告「兩次作答各自計分」的較寬鬆版本，兩個數字的差距本身就反映模型對位置的敏感度。任何兩兩比較的 LLM 評審（pairwise judge、A/B 偏好評測）都可以套用。

#### 觀念二：forward KL 截斷時，保留「老師」機率最高的前 K 名比較自然

**背景。** 蒸餾時，學生要靠近老師的下一個 token 機率分布。詞表有十幾萬個 token，逐一算 KL 太貴，所以實作會截斷：只保留一部分 token，其餘合併成一格「其他」。問題是：保留誰的前 K 名？

**關鍵事實：forward KL 是以老師的機率加權的。**

```latex
D_{KL}(p_T \,\|\, p_S) = \sum_{v} p_T(v) \log \frac{p_T(v)}{p_S(v)}
```

每一項都乘上 p\_T(v)。老師給的機率很小的 token，貢獻幾乎是 0，可以安全地捨棄；老師給的機率高的 token，才是損失的主要來源。（一般知識：reverse KL 是以學生的機率加權，那種情況下保留學生的前 K 名才是自然的做法。）

**論文的做法與它的缺口。** 論文取的是學生的前 100 名，加上一格「其他」。如果老師想要的 token 不在學生的前 100 名（學生給它很低的機率），這個 token 就被併進「其他」，學生只被告知「榜外該多給一點機率」，不知道是哪個 token。這個缺口的大小，用自編例子看：

| token | 學生 p\_S | 老師 p\_T |
| --- | --- | --- |
| 甲 | 0.5 | 0.2 |
| 乙 | 0.3 | 0.1 |
| 丁 | 0.01 | 0.6 |
| 其他 | 0.19 | 0.1 |

- 用學生的前 2 名（甲、乙）分格，丁被併進「其他」（學生 0.20、老師 0.70）：KL ≈ 0.2 ln(0.2/0.5) + 0.1 ln(0.1/0.3) + 0.7 ln(0.7/0.2) ≈ 0.58。
- 用老師的前 3 名（丁、甲、乙）分格，丁自己一格：KL ≈ 0.6 ln(0.6/0.01) + 0.2 ln(0.2/0.5) + 0.1 ln(0.1/0.3) + 0.1 ln(0.1/0.19) ≈ 2.10。因為這個例子的 token 已經全部列出，2.10 就是不截斷的完整 KL。

也就是說，用學生的前 K 名分格，在老師最在意的 token 上，把損失低估了 3.6 倍；而且梯度指向的是整個「其他」，不是丁。（推論：梯度會把所有榜外 token 依各自目前的機率比例一起抬高，老師想要的 token 本來機率就小，被抬高的幅度也小，所以學得慢。）

**判斷規則（我們的判斷，論文沒有對照實驗）。** 截斷時，保留「加權那一方」的高機率項：

| KL 的方向 | 加權的分布 | 截斷時保留誰的前 K 名 |
| --- | --- | --- |
| forward KL（以老師為目標） | p\_T | 老師的前 K 名 |
| reverse KL | p\_S | 學生的前 K 名 |
| 不確定、想保險 |  | 兩邊前 K 名的聯集，再加一格「其他」 |

論文取學生前 100 名的原因沒有交代；一個合理的猜測是，訓練時學生的 logits 本來就在手上，直接取它的前 100 名實作最簡單。這個猜測是推論，不是論文寫的。逐步的推導見【概念 5】，KL 的基本定義與截斷細節見【概念 3】。

## 概念詳解

以下五段是最容易混淆、也最容易忘的觀念。每一段都寫成脫離這篇論文也能獨立閱讀。

### 【概念 1】parallel／detour 是題目的來源，也決定標籤怎麼來

**結論：parallel 與 detour 不只是「樣本從哪裡來」，它們同時決定了「這題的答案是怎麼得到的」。**

從 agent 軌跡造「決策品質」的評測題，有兩種原料：

- **Parallel（平行軌跡）。** 原料是同一個任務的兩次獨立嘗試，一次成功、一次失敗，兩次在中途走向不同方向。標籤來自兩條分支最終結果的比較：結果較好的那條，它的方向就是答案。這種做法有真正的對照：兩條分支在岔路口之前完全相同。
- **Detour（繞路軌跡）。** 原料是同一次嘗試裡 agent 自己的走錯與改正：選了方向 X、碰壁、改走方向 Y、成功。標籤來自這一次執行的經過：被放棄的方向產生了可觀察的失敗，改正的方向完成了任務，所以改正的方向是答案。這種做法沒有平行的另一條分支。

兩者抓到的錯誤不同：parallel 抓的是 agent 一路沒發現的錯誤（兩次嘗試都走到底，結果不同）；detour 抓的是 agent 後來自己發現並改正的錯誤。

**在 Taste-Bench 裡的比例與難度。** 502 題中，parallel 有 172 題（工程 124 + 研究 48），detour 有 330 題（工程 266 + 研究 64）。論文把兩種分開統計，因為難度差很多。14 個模型的平均準確率：平行工程 58.1%、平行研究 50.9%、繞路研究 50.8%、繞路工程 35.9%。構造方式（parallel／detour）造成的差距，比領域（工程／研究）造成的差距更大；繞路工程題最難。

**為什麼難度差這麼多（推論）。** parallel 測的是「兩條分支裡誰的方向比較好」，兩條路都是 agent 真的走完的；detour 測的是「能不能比當時行動的 agent 更早看出這個方向會失敗」，這需要預見後果，而不是比較兩個結果。

**可遷移的觀念。** 任何從日誌挖評測題的做法，都會碰到同一個選擇：用「兩次不同的執行」構成反事實對照，還是用「一次執行裡的自我修正」？前者標籤更可靠，後者資料量更大、也更貼近「事後諸葛」的風險。

### 【概念 2】怎麼讀人工審查的一致率

**結論：論文報了兩組不同的比較。人和自動標籤很像（98.8%），人和人也很像（98.6%，κ = 0.973），兩者都成立。**

用一個比喻：兩位老師拿同一份考卷，對照標準答案批改。

**設定。** 兩位審查員各自看 100 道題。每題先選自己會選哪個方向；再看後續過程與結果的摘要，回答「哪個決策比較好」，選項是 A、B、或「兩者差不多／選擇無法解釋結果差異」。分析只用第二階段的回答，而且排除沒有明確 A/B 偏好的回答。

**比較 1：人 vs 標籤。** 每位審查員的明確 A/B 判斷，各自拿去跟自動標籤比對：

|  | 有明確 A/B 的判斷數 | 與標籤一致 |
| --- | --- | --- |
| 審查員 1 | 87 | 86（98.9%） |
| 審查員 2 | 85 | 84（98.8%） |
| 合計 | 172 | 170（98.8%） |

白話：兩位審查員幾乎每一題的選擇，都和自動標籤一樣。

**比較 2：人 vs 人。** 這次不看標籤，只看兩位審查員彼此。兩人都有明確 A/B 選擇的題只有 74 題，其中 73 題兩人選的一樣（98.6%）。

**為什麼分母是 172 和 74，不是同一個數字？** 172 是「判斷的次數」（87 + 85），也就是每位審查員保留下來的判斷加總。每位審查員都有些題回答「兩者差不多」而被排除。要比較兩個人，必須是兩人在同一題都有明確選擇，所以只剩 74 題。

**κ 是什麼。** Cohen's kappa 回答的還是比較 2 的問題：兩位評分者的一致程度，並扣掉「碰巧選一樣」的部分。選項只有 A、B 時，兩人亂猜也有大約 50% 會一樣，所以 κ 比單純的一致率更嚴格。

```latex
\kappa = \frac{p_o - p_e}{1 - p_e}
```

- p\_o：實際觀察到的一致率。
- p\_e：如果兩人各自隨機選，預期會碰巧一致的比例。
- 分母 1 − p\_e：扣掉碰巧一致之後，最多還能多出多少。
- κ = 1 代表完全一致，κ = 0 代表跟亂猜一樣。

驗算：p\_o = 73 / 74 ≈ 0.986。A、B 大致各半時 p\_e ≈ 0.5，所以 κ ≈ (0.986 − 0.5) / (1 − 0.5) ≈ 0.973，和論文報的一致。

**這組數字驗證了什麼、沒驗證什麼。** 審查員是看過結果之後才判斷的（第二階段），所以 98.8% 驗證的是「自動標籤和記錄下來的結果對得上」，等於一致性檢查。它沒有驗證「這個決策真的是造成結果差異的原因」，也沒有驗證「這一題在決策當下真的答得出來」。另外，審查員第一階段（看到結果之前）的選擇，等於人類在這個任務上的準確率，可以拿來跟模型比較；論文正文沒有報告這個數字。

**可遷移的觀念。** 用 LLM 自動產生標籤的資料集，品質檢查要把「人對標籤」和「人對人」兩件事分開報告：前者回答標籤是否可信，後者回答這個任務本身有沒有清楚的答案。

### 【概念 3】forward KL 在實作時怎麼截斷

**結論：KL 要對詞表裡每個 token 加總，太貴，所以實作時只在一小批 token 上算，其餘的合成一格「其他」，機率總和仍是 1，沒有被丟掉。**

**背景（一般知識）。** 語言模型在每個位置，要對詞表裡每一個 token（常見是十幾萬個）都給一個機率。第一次的損失公式（見 2.5）要對所有 v 加總：

```latex
\mathcal{L}_t = \sum_{v} p_T(v) \log \frac{p_T(v)}{p_S(v)}
```

- p\_T(v)、p\_S(v)：老師、學生在這個位置給 token v 的機率。
- 加總範圍：整個詞表。

對每個位置、每個訓練 view 都算一次，記憶體與計算量都很大，所以論文做了下面這些簡化（Appendix G.1）：

**1. 推理位置：前 100 名加一格「其他」。**

1. 取學生機率最高的 100 個 token。
2. 其他幾萬個 token 的機率全部加起來，當作第 101 格「其他」。
3. 在這 101 格上算 KL。

這樣算得便宜，機率總和也還是 1。論文原文只說「student 的前 100 名加一格剩餘機率」，沒有說老師那一邊怎麼處理。KL 是逐格比較「老師給這一格多少、學生給這一格多少」，兩邊的格子必須一樣才比得了，所以合理的做法是：老師的分布也在同樣這 100 個 token 上讀出機率，剩下的也加總成「其他」。這是推論，不是論文明講的。

**2. 最後的選擇位置：只比 A 和 B。** 模型最後輸出 `{"answer":"A"}`，在 A／B 這個位置只有兩格。自編例子：老師 P(A) = 0.95、P(B) = 0.05，學生 P(A) = 0.55、P(B) = 0.45。

損失 = 0.95 ln(0.95/0.55) + 0.05 ln(0.05/0.45) ≈ 0.52 − 0.11 = 0.41。

**3. 總損失。** 推理位置的 KL 與選擇位置的 KL 各乘以 1，再相加。

**4. 長推理要抽樣。** 老師的推理最長可到 3,072 個 token，全部位置都算太吃記憶體，所以平均挑最多 512 個位置來算。

**一個完整的小例子（自編，三個 token）。** 某位置老師的機率是 0.7、0.2、0.1，學生是 0.4、0.4、0.2：

| token | 老師 p\_T | 學生 p\_S | p\_T ln(p\_T / p\_S) |
| --- | --- | --- | --- |
| 甲 | 0.7 | 0.4 | 0.7 × ln 1.75 ≈ 0.392 |
| 乙 | 0.2 | 0.4 | 0.2 × ln 0.5 ≈ −0.139 |
| 丙 | 0.1 | 0.2 | 0.1 × ln 0.5 ≈ −0.069 |
| 合計 | 1.0 | 1.0 | ≈ 0.184 |

學生如果跟老師一模一樣，結果是 0。

**為什麼不算「對的數字」而要截斷也能接受。** forward KL 以老師的機率加權（見【概念 5】），老師機率很小的 token 貢獻幾乎是 0，所以只要保留的格子涵蓋了老師真正在意的 token，截斷損失得不多。問題出在「保留誰的前 100 名」，這是【概念 5】的主題。

### 【概念 4】KL 要在誰寫的文字上算

**結論：「學生要模仿誰」和「在誰寫的那段文字上比較」是兩件不同的事。學生模仿的對象永遠是老師；論文選擇用老師寫的文字當比較的現場。**

**先釐清 KL 需要什麼。** KL 要先有一段已經寫好的文字。在這段文字的每個位置，兩個模型各自讀同一段前文，預測下一個 token，再比較兩個預測差多少。所以必須先決定：拿誰寫的文字來比？

**兩件事混在一起的常見說法：「因為要學老師，所以以老師為主。」** 這句話只對了一半：

1. **模仿誰？** 一直是老師。公式裡每一項都乘上老師的機率 p\_T，所以無論用哪段文字，學生都在靠近老師。
2. **用誰寫的文字當現場？** 這才是問題所在，答案有兩種做法。

**做法 1（論文）：用老師寫的文字。** 自編例子，老師看過 demonstration，寫道：「保持 helper 的預設輸出不變，既有測試才不會壞，所以選 A。」

- 寫到「既有測試會壞」這個關鍵洞見的位置：老師已知答案，預測機率高；學生沒看過答案，機率低。差距大，損失大，學生被推著去學「該想到這一點」。
- 寫到「所以選」的位置：老師預測 A 是 0.95，學生只有 0.55，同樣差距大。

用老師的文字，等於一路帶著學生走過老師的思路，每一步問：「換你，下一個字會寫什麼？」

**做法 2：用學生自己寫的文字。** 學生不知道答案，寫出來的比較籠統，例如「兩個方案都合理，B 比較完整……」。這段文字裡，老師和學生對大多數位置的預測差不多，損失很小。真正有差別的那些關鍵洞見，學生根本沒寫出來，所以沒有任何位置可以拿來比較。

**論文的理由，翻成白話：** 兩邊的輸入只差在 demonstration，真正預測不同的 token，只出現在老師的輸出裡。學生自己的樣本很少產生這些 token，在學生的文字上算 KL，就抓不到老師的偏好。簡單說：學生想不到的洞見，不會出現在它自己的文字裡，也就沒有東西可以教它。

**對應的一般知識。**

- 這個做法接近一般監督式微調的 teacher forcing：把「正確的前文」餵給模型，只看它預測下一個字準不準。
- 在學生自己的取樣上算 KL，是 on-policy distillation（論文參考文獻 \[51\]）的標準做法。論文刻意不照那樣做，並且把理由寫在 Appendix G.1。論文沒有提供改用學生文字的對照實驗。

**可遷移的觀念。** 蒸餾時如果老師與學生的差異來自「老師多看到的資訊」，就要在老師的軌跡上比較，因為只有在老師的軌跡上，那些資訊的影響才會顯現；在學生自己的軌跡上，學生永遠走不到那裡。

### 【概念 5】截斷時取誰的前 K 名

**結論：兩邊分格必須一樣；論文用「學生的前 100 名」決定分格，但從 forward KL 的數學來看，用「老師的前 K 名」更自然，因為損失主要由老師機率高的 token 決定。論文沒有交代這個選擇的理由，也沒有對照實驗。**

**問題 1：老師和學生取的前 100 名，要一樣嗎？** 要。KL 是逐格比較，兩邊的格子不一樣就比不了。論文原文說的是「top 100 tokens of the student，加上一格剩餘機率」。做法是：

1. 看學生在這個位置的機率，挑出前 100 名 token。
2. 老師的分布也在這 100 個 token 上讀出機率。
3. 兩邊各自把其餘 token 的機率加總成第 101 格。
4. 在這 101 格上算 KL。

第 2、3 步論文沒有明講，是推論，但邏輯上必須如此。

**問題 2：為什麼不用老師的前 100 名？** 直覺是：這樣學生馬上就知道要提升哪些 token 的機率。這個直覺有道理，論文沒有說明為什麼選學生的前 100 名。

- **用學生的前 K 名分格的缺口：** 老師想要的 token 如果學生給它很低的機率，它就掉出學生的前 K 名，被併進「其他」。這一格的損失只告訴學生「榜外的整體該多給一些機率」，沒有指出是哪個 token。（推論：梯度會依各 token 目前的機率比例，把整個榜外一起抬高；老師想要的 token 本來機率就小，被抬高的幅度也小，所以很慢。）
- **用老師的前 K 名分格：** 老師想要的 token 自己獨立一格，這一格的損失很大，梯度直接指向「把它抬高」。
- **數學上也一致：** forward KL 的每一項都乘上老師的機率 p\_T，老師機率小的 token 對損失貢獻很小，可以安全捨棄；要省算力，最自然的做法是保留老師機率高的 token。保留學生機率高的 token，是 reverse KL（以學生機率加權）的自然做法。

**數字例子。** 見第五章「觀念二」的表格：同一組分布，用學生前 2 名分格，KL ≈ 0.58；用老師的前 3 名分格，KL ≈ 2.10。因為那個例子的 token 全部列出，2.10 就是不截斷的完整 KL，學生前 K 名的做法在老師最在意的 token 上把損失低估了約 3.6 倍。

**論文可能的理由（猜測）。** 訓練時學生的 logits 本來就在手上，直接取它的前 100 名實作最簡單。論文沒有報告改用老師前 100 名的對照。

**可遷移的判斷規則。** 截斷或抽樣時，保留「加權那一方」的高機率項：forward KL 取老師的前 K 名，reverse KL 取學生的前 K 名，不確定時取兩邊前 K 名的聯集再加一格「其他」。
