# SKILL.state：用顯式執行狀態取代對話歷史的 Agent Runtime

**論文**：*SKILL.state: Scalable Long-Horizon Agent Skills*
**作者**：Sanket Badhe, Priyanka Tiwari, Jonghyun Chung（Google LLC / Purdue University）
**來源**：arXiv:2608.26263v2 [cs.AI]，2026 年 8 月 28 日

---

## 30 秒版本

現在幾乎所有 LLM agent runtime（ReAct 這類）都是「每走一步，就把這一步的觀察、推理、動作往後疊加」的對話式做法，導致 prompt 長度隨執行步數呈平方成長（O(T²)），長任務會又貴又慢，還會被過期的舊資訊干擾判斷。

本論文提出 SKILL.state：**每一步只餵模型「任務指令 + 當下的結構化狀態 + 最新觀察」這三樣東西，模型的推理過程用完即丟，只把「狀態該怎麼修改」的結果保留下來**。這讓每一步的 prompt 大小跟第幾步無關（O(1)），總消耗隨步數線性成長（O(T)）。

**判決**：工程／成本價值高、證據紮實（尤其 token 節省，實測 T=200 時省下 41 倍）；研究價值中等偏低，核心概念（結構化狀態、丟棄歷史）在 MemGPT、LangGraph、Dialogue State Tracking 裡都已存在，這篇的貢獻主要是把它系統化並給出複雜度證明。準確率提升的證據比 token 節省的證據弱很多，而且**不是在所有環境下都成立**——換成關聯密集的環境或弱模型，優勢會打平甚至倒輸。

## 一、這篇論文想解決的問題

現在的 agent runtime 幾乎都採用「對話式執行模型」：每一步都把「任務指令」+「到目前為止累積的所有觀察、推理、動作」整包塞給 LLM，做完一步，就把這一步的內容再往後疊加一段。

這個做法有兩個具體問題：

1. **Prompt 長度隨執行步數增長，token 成本與延遲跟著漲**——執行越久，context 裡塞的東西越多。
2. **舊資訊「賴著不走」，模型得自己分辨哪些還有效**——早期的觀察結果、已經走過的推理過程，即使已經過期，還是留在 context 裡。模型每一步都要重新判斷「這段舊文字現在還算數嗎」，這件事本身就是額外負擔，也容易出錯：如果世界狀態已經被外部事件改變了，但舊的觀察紀錄還壓在上面，模型可能還是照舊資訊做判斷。

加了記憶系統（摘要、檢索）也沒有真正解決這兩個問題，因為這些方法本質上還是「把過去的文字歷史重新整理一遍再餵回去」，模型的決策仍然建立在「重建過去發生了什麼」，而不是「直接讀取現在世界長什麼樣子」——執行的邏輯本質沒變，只是換了一種壓縮歷史的方式。

論文真正瞄準的問題是：**能不能把「現在的世界狀態」變成一個獨立於歷史文字之外、可以直接讀取的東西**，讓模型不用每次都從一堆文字裡重建現況。

## 二、核心方法

### 2.1 每一步的輸入與輸出

每一步，模型只會看到三樣東西：

```
A_t = (P, Σ_t, O_t)
```

- **P**：procedural specification，任務的固定指令（例如「你是倉儲管理員，可用動作是 Store/Ship/Move/Wait」）。整個執行過程中都不變。
- **Σ_t**：第 t 步當下的「結構化執行狀態」，一個 JSON 字典，記錄目前世界長什麼樣子（例如「shelf_42 放著 item_12」）。
- **O_t**：這一步環境傳來的最新觀察（例如「Customer ordered item_12」）。

模型看到這三樣東西後，輸出三個東西：

```
(R_t, ΔΣ_t, a_t)
```

- **R_t**：推理過程（chain-of-thought）。用完立刻丟掉，**永遠不會出現在下一步的 prompt 裡**。
- **ΔΣ_t**：狀態的「差異」，一個 JSON 字典，描述這一步要對狀態做哪些修改。
- **a_t**：要執行的動作。

狀態更新公式：

```
Σ_(t+1) = Σ_t ⊕ ΔΣ_t
```

**⊕** 是論文定義的「字典合併運算子，帶 null 刪除語意」：
- ΔΣ_t 裡有的 key，直接覆蓋 Σ_t 裡同名 key 的值
- 某個 key 的值被設成 `null`，代表把這個 key 從狀態裡整個刪掉
- ΔΣ_t 沒提到的 key，維持原樣不動

### 2.2 執行迴圈全貌

```
[1] 收到觀察 O_t
     ↓
[2] 組成 prompt = (P, Σ_t, O_t)   ← 大小跟第幾步無關
     ↓
[3] LLM 輸出 (R_t, ΔΣ_t, a_t)
     ↓
[4] Runtime 驗證 ΔΣ_t 是否合法（格式檢查）
     ↓ 合法                         ↓ 不合法
[5] Σ_(t+1) = Σ_t ⊕ ΔΣ_t      回滾，要求模型重新輸出
     ↓
[6] 執行動作 a_t，R_t 永久丟棄
     ↓
[7] 環境回傳新觀察 O_(t+1) → 回到 [1]
```

對照傳統做法（ReAct 式），prompt 是不斷往後疊加的：

```
傳統做法：
  第1步 prompt: [P] + [O_1]
  第2步 prompt: [P] + [O_1, R_1, a_1] + [O_2]
  第3步 prompt: [P] + [O_1,R_1,a_1] + [O_2,R_2,a_2] + [O_3]
  ...越疊越長

SKILL.state：
  第1步 prompt: [P] + [Σ_1] + [O_1]
  第2步 prompt: [P] + [Σ_2] + [O_2]
  第3步 prompt: [P] + [Σ_3] + [O_3]
  ...大小大致固定（Σ 可能隨任務複雜度緩慢變化，但跟「走了幾步」無關）
```

### 2.3 具體數值範例（取自論文 Appendix B.3）

情境：倉儲環境，item_12 目前放在 shelf_42。

**收到觀察：**
```
O_t = "Customer ordered item_12."
```

**模型內部推理（R_t，這段之後會被丟掉）：**
> 顧客訂購了 item_12，我需要出貨。查看目前狀態，item_12 在 shelf_42。我要下 Ship 動作，並把狀態裡 shelf_42 的紀錄清掉。

**模型實際輸出：**
```json
{
  "state_patch": { "inventory": { "shelf_42": null } },
  "action": "Ship item_12 shelf_42"
}
```

**套用 ⊕ 之前的狀態：**
```
Σ_t.inventory = { shelf_42: "item_12", shelf_43: "item_9", ... }
```

**套用之後：**
```
Σ_(t+1).inventory.shelf_42 = null      ← 被刪除／清空
Σ_(t+1).inventory.shelf_43 = "item_9"  ← 沒被提到，維持原樣
```

**環境執行完動作後回傳新觀察：**
```
O_(t+1) = "Success: Shipped item_12 from shelf_42."
```

下一輪 prompt 是 `(P, Σ_(t+1), O_(t+1))`——注意 R_t（推理過程）完全沒有出現，上一步的 O_t 也沒有出現。模型下一輪看到的只有「現在的狀態」+「最新的觀察」。

### 2.4 Schema 是 per-domain 設計，不是 per-task

同一個 domain 裡的所有任務共用同一份 schema，只設計一次。例如 InterCode CTF benchmark 裡 100 個完全不同的挑戰題目（逆向工程、鑑識、密碼學、二進位漏洞利用），全部共用同一組固定的 5 個欄位：

```
discovered_flags     已經找到的 flag
tested_hypotheses    已經試過的假設／指令
active_files         目前在操作的檔案
working_dir          目前工作目錄
cmd_summary          指令執行摘要
```

好處：工程上省事，不用每個任務重新設計狀態格式，也讓不同任務可以共用同一套 runtime 程式碼。

> ⚠️ **限制**：這個做法的前提是「這個 domain 事先就知道該追蹤哪些欄位」。如果一個 domain 沒辦法事先固定 schema、必須邊執行邊發現該追蹤什麼，這套做法就不適用——這是論文自己在 Limitations 承認的第一個失效情境（見第六節）。

### 2.5 驗證機制與它的盲區

Runtime 在套用 ΔΣ_t 之前，會先做格式驗證：檢查是不是合法 JSON、是否符合預期的 key 結構。如果驗證失敗，會觸發「回滾重試」——狀態退回上一步，要求模型重新輸出。這個機制確保**格式錯誤**的輸出不會污染狀態。

> ⚠️ **這個機制擋得住「格式不合法」，但擋不住「格式合法、但語意錯誤」的輸出**——例如模型合法地輸出了一個會誤刪重要資訊的 patch，這種 patch 格式上完全沒問題，驗證機制抓不到，只能算完全「成功」地套用一次錯誤更新。
>
> 更關鍵的是：**因為舊狀態已經不在 context 裡了，一旦錯誤的 patch 被合法套用，就沒有「回頭看歷史文字」自我修正的機會**。這是整個架構相對於保留完整歷史的做法，結構性更脆弱的地方。論文自己的實驗數據（第六節 Error Taxonomy）顯示，小模型 68% 的失敗案例正是這種「語意上合法但錯誤的更新被無感套用」。

## ❓ 延伸提問：平方 vs 線性的成長速度，具體怎麼算出來的？

論文用 T 代表總執行步數，證明兩種做法的總 token 消耗量級不同：

**傳統做法**：第 t 步的 prompt 長度 `|C_t| = O(t)`——跟 t 成正比。把所有步驟的 prompt 長度加總：

```
Σ(t=1 to T) |C_t| = O(T²)
```

**SKILL.state**：第 t 步的 prompt 長度 `|P_t| = O(|P| + |Σ| + |O|)`——跟 t 無關，大致是常數。加總 T 步：

```
Σ(t=1 to T) |P_t| = O(T)
```

**用具體數字驗證直覺**——假設走 10 步，每一步的「單位長度」簡化成 1, 2, 3, ..., 10（傳統做法）vs 1, 1, ..., 1（SKILL.state）：

```
傳統做法：1 + 2 + ... + 10 = (1+10)×10/2 = 55   ← 等差數列求和，量級是 T²
SKILL.state：1 + 1 + ... + 1（10次） = 1×10 = 10  ← 量級是 T
```

這正是 O(T²) 對 O(T) 差距的來源：傳統做法的每一步長度隨 t 線性增加，把這些「線性增加的量」再加總一次，結果就變成平方量級；SKILL.state 每一步長度大致固定，加總後自然只跟 T 成正比。

> 📌 **小提醒**：這裡的「1 單位」是簡化說法。SKILL.state 每一步的實際大小是 `|P| + |Σ| + |O|`，這個量不是完全釘死的常數——狀態 Σ 可能隨任務複雜度緩慢變大（例如關聯密集的環境裡，狀態本身會隨 PR、分支數量增加而變胖）。但關鍵是：**它的變化跟「已經走了幾步 t」無關**，只跟「當下世界有多複雜」有關，這也是為什麼稱為 O(1) per-step、O(T) 總和，而不是嚴格意義上「每步剛好等於某個固定常數」。

**實測數字驗證**（Table 1，見第五節）：T 從 100 加倍到 200 時，Stateful baseline 的總 token 消耗成長了約 4.7 倍（接近理論預期的 4 倍 = 2²），SKILL.state 只成長約 1.9 倍（接近理論預期的 2 倍 = 2¹）。實測趨勢跟數學推導基本吻合。

## 三、實驗設計

### 3.1 三個測試環境

**SkillExecBench**（論文自建的合成 benchmark）：控制型診斷測試台，用決定性的世界轉換規則，把「執行機制本身」跟「開放式啟發式搜尋」分開測。兩個子環境：

- **倉儲管理**：500 個獨立、互不重疊的貨架，動作只有 Store/Ship/Move/Wait。測試模型能否在長執行過程中維持大量互不干擾的狀態變數。
- **軟體版本庫**：有深度巢狀關聯的 Git 分支、commit、PR、CI 狀態圖，動作包括 CherryPick、Merge、RunTests、CreateRelease、Rollback。特色是「密集依賴關係」——單一動作（如合併 PR）會連帶影響目標分支跟其他相依 PR，測試模型在互相糾纏的關聯圖上做結構化推理的能力。

**InterCode CTF**（Yang et al., 2023，公開 benchmark）：100 道 Linux bash 的 Capture-The-Flag 挑戰，涵蓋逆向工程、鑑識、密碼學、二進位漏洞利用。Agent 在 Docker 容器裡執行 bash 指令，反覆測試假設找出隱藏 flag。

**Sierra τ-Bench**（Yao et al., 2024，公開 benchmark）：測試工具-agent-使用者三方互動的企業客服場景（零售、航空兩個領域），agent 要跟模擬使用者對話、透過工具呼叫查詢 SQLite 資料庫，並在商業政策限制下執行交易性動作。

### 3.2 評估指標

- **Task Accuracy / Success Rate**：SkillExecBench 是連續分數（成功動作數 ÷ 總事件數）；InterCode CTF 是二元 pass@1；τ-Bench 用官方評分器檢查資料庫最終狀態。
- **Average Prompt Size**：每次呼叫 LLM 的平均 token 用量。
- **Total Token Cost**：整個執行過程累積的 token 總量。

### 3.3 Baseline 陣容

**主要對照組（架構層面）**：
```
Prompt (ReAct)      → 每步觀察/推理/動作全部往後疊加，最原始做法
Memory (Summary)    → 保留最近 3 輪原文 + 定期更新的自然語言摘要
Stateful (LangGraph)→ 有結構化 state block，但「同時」還保留完整滾動對話紀錄
```
其中 **Stateful** 是最關鍵的對照組——它跟 SKILL.state 一樣有結構化狀態，唯一差異是「狀態 + 完整歷史並存」vs「只有狀態，歷史全丟」。Stateful vs SKILL.state 這組比較，才是真正驗證「丟棄歷史」這個決定有沒有價值的關鍵對照。

**預算對齊控制組（排除「贏只是因為短」這個混淆變因）**：
```
Truncated (Sliding Window) → 只留最近幾輪，硬卡 token 上限
Summary-capped             → 自然語言摘要，嚴格限制摘要本身的 token 上限
ReAct + LLMLingua          → 用小模型做困惑度壓縮，硬壓到目標 token 數
```

**模型**：Gemini-3-Flash（proprietary）、Gemma-4-31B-it、Qwen-3-8B-it（open-weight）。溫度 0.0，合成實驗跑 5 個隨機種子，T≥50 時做 paired t-test（論文聲稱 p<0.01）。

## ❓ 延伸提問：這篇論文的「long horizon」宣稱，證據真的夠紮實嗎？

論文在合成環境（SkillExecBench）裡刻意把 horizon 拉到 T=10 到 T=200，是明確的「長度掃描」設計。但翻遍 InterCode CTF 跟 τ-Bench 那兩節，**論文完全沒有報告這兩個公開 benchmark 裡，一個任務平均要走幾步才能完成**。如果這些任務平均只需要 10-20 步就結束，那麼「公開驗證」根本沒有真正測試到 SKILL.state 宣稱最擅長的長距離場景——唯一真正壓力測試過「long horizon」的，就只剩自己設計、自己控制的合成環境。

此外，業界確實存在專門設計來測試長距離、真實世界 agent 能力的公開 benchmark，這篇論文一個都沒用，包括：

- **SWE-bench**：真實 GitHub issue 修復任務，往往需要數十到上百輪工具呼叫（值得注意的是，論文自己的「軟體版本庫」合成環境本質上就是在模仿 SWE-bench 這類任務，卻選擇自己造一個簡化版，而不是直接採用真實的 SWE-bench）
- **WebArena / Mind2Web**：長距離網頁導航任務
- **GAIA**：需要多步驟工具串接推理的通用助理任務
- **OSWorld**：真實作業系統操作任務

論文沒有解釋為什麼沒有採用這些更有代表性的 long-horizon benchmark。

**結論**：「long horizon 假設在真實世界真的 work」這個宣稱，證據力比表面上看起來薄——最有說服力的長距離數字全部來自自己設計、自己控制的合成環境。

### 4.1 Table 1 — Warehouse Long-Horizon Scaling

> **原文 caption**：Warehouse Management Long-Horizon Scaling using Gemini-3-Flash. Baseline runtimes suffer O(T²) context accumulation, whereas SKILL.state maintains a bounded O(1) prompt footprint (Mean ± SD across 5 seeds).

```
                T=10 準確率    T=200 準確率    T=200 總Token
Stateful         1.00           0.88            5,041,164
SKILL.state      1.00           0.94            122,384
```

- **短任務（T=10）沒有準確率優勢**，主要 baseline（Memory、Stateful）跟 SKILL.state 都是 1.00，打平。優勢只在長任務才浮現，而且差距不算壓倒性（T=200 時 0.94 vs 0.88，差 6 個百分點）。
- **真正壓倒性的是 token 節省**：T=200 時差了 41 倍。這篇論文最硬的證據是「省成本」，不是「更準」。
- baseline 準確率隨 T 增加而下降、標準差放大（Prompt runtime 從 T=10 的 0.90±0.02 跌到 T=200 的 0.74±0.14），SKILL.state 相對穩定——更精確的講法是「baseline 會隨執行時間拉長而退化，SKILL.state 不太退化」，而非「SKILL.state 準確率大幅領先」。

```
SKILL.state      54.2%    387k           58.3%    3.47M         32.4%    2.88M
```

- 這是全篇最有說服力的準確率提升證據，因為是在別人設計的真實任務上：三個獨立任務都贏（CTF +7.8pt、Retail +6.6pt、Airline +4.3pt，均對比最強的 baseline）。
- **異常值需留意**：Memory baseline 在 τ-Bench Retail 上崩得很慘（29.9%，比 Prompt 的 48.2% 還低近 20 個百分點），可能是摘要式記憶把交易細節搞丟了，論文沒有討論這個異常值。這代表 Retail 這欄的比較基準不穩定，SKILL.state 贏的是「表現最好的 baseline」還是「表現最差的 baseline」差距很大，解讀時要留意對照組是誰。
- 這張表無法回答「long horizon 假設在真實世界成立」這個問題（見上方 ❓ 提問），它證明的是「整體上比較好」，範圍比摘要暗示的窄。

### 4.3 Table 6 — 軟體版本庫環境（關鍵反例）

> **原文 caption**：Software Repository Long-Horizon Execution Scaling using Gemini-3-Flash. Baseline runtimes suffer catastrophic O(N²) context collapse, whereas SKILL.state maintains an O(1) prompt footprint.

```
T=10   Stateful 1.00±0.00     SKILL.state 1.00±0.00   （打平）
T=25   Stateful 0.94±0.03     SKILL.state 0.88±0.08   （SKILL.state 反而輸 6pt）
T=50   Stateful 0.74±0.08     SKILL.state 0.86±0.04   （SKILL.state 贏回來）
T=100  Stateful 0.63±0.10     SKILL.state 0.78±0.08   （SKILL.state 贏 15pt）
```

> ⚠️ **這是全篇最重要的反例**。T=25 這個點，SKILL.state（0.88）**輸給** Stateful（0.94），直接跟論文摘要「SKILL.state improves task accuracy... across diverse datasets」以及正文「matches or exceeds baseline accuracy across all horizons」這句話矛盾——「across all horizons」這句話只在 Warehouse 環境成立，換到 Software Repository 環境就有反例，論文正文完全沒有提到這個反例。
>
> SKILL.state 在這張表的標準差也偏大（±0.08），代表結果不算穩定。這跟「軟體版本庫」環境的特性有關——它的設計特色是「密集依賴關係，單一動作可能連帶影響多個分支」。這類強關聯的狀態，一旦某次 patch 更新沒有正確捕捉到連帶影響（例如合併 PR 卻漏更新相依分支的狀態），錯誤可能一路延續到後面步驟，因為沒有原始歷史文字可以回頭核對——這正好呼應第 2.5 節提到的驗證機制盲區，T=25 這個反例很可能就是這個風險在實際發生。
>
> **結論**：「準確率全面提升」這個宣稱在真實／複雜關聯的任務上不是穩定成立的，會因環境的關聯密度而有反例；真正跨所有環境都穩定成立的優勢，只有 token 節省。

### 4.4 其他實驗（簡述）

- **Table 2（雜訊魯棒性，T=50）**：高雜訊環境下，Prompt baseline 準確率從 0.68 掉到 0.53，SKILL.state 全程維持 0.97-1.00。結論可預期——雜訊不會被寫進 state patch，自然不影響後續決策，屬於架構設計的直接推論，不算意外發現。
- **Table 3（狀態恢復）**：外部環境悄悄改變世界狀態時，history-based baseline 需要 5-8 步才能從錯誤的舊認知中恢復，SKILL.state 需要 0 步。這個結果同樣接近同義反覆——SKILL.state 定義上不保留歷史文字，「被舊觀察蓋過新事實」這件事在架構設計上本來就不可能發生，只要修正性的觀察能成功寫進 patch，恢復步數邏輯上必然是 0。
- **Table 5（Budget-matched control，T=100，見下方摘要）**：把所有做法的 token 預算硬性對齊到 SKILL.state 的水準（~1,800 tokens）後比較：

```
Truncated (Sliding Window)  0.18
ReAct + LLMLingua           0.22
Summary-capped              0.52
SKILL.state (Structured)    0.94
```

  這是全篇最紮實的實驗，因為它排除了「贏只是因為 prompt 比較短」這個混淆變因——在同樣的 token 預算下，統計式壓縮（LLMLingua）跟簡單截斷都會把語意上關鍵的資訊一起壓爛掉，SKILL.state 的結構化狀態能完整保留關鍵的關聯資訊。

## 五、Error Taxonomy 與 Limitations

### 5.1 小模型的失敗模式（Gemma-4-31B, T=100, 準確率僅 0.42）

```
1. Premature State Overwrite/Deletion   68%   合併時不小心漏掉既有 key，等於誤刪
2. Schema Comprehension / Type 錯誤      20%   巢狀 list/dict 搞混
3. JSON 語法/格式錯誤                    12%   漏逗號、括號沒對齊
```

論文結論：小模型失敗的根源是「結構化輸出的遵從度」，不是「推理能力不足」。第 1 類（68%）正是「語意上合法、但錯誤的 patch 被套用且無法回頭校正」這個架構性風險的直接證據（見 2.5 節），跟 Table 6 的 T=25 反例本質上是同一個問題的不同表現形式。

### 5.2 論文承認的三種架構假設失效情境

整套設計依賴一個前提：**「執行狀態可以成為未來執行的充分統計量」**——過去發生的一切，只要在當下就被正確寫進狀態裡，就不需要保留原始文字。這個前提在三種情境下會失效：

1. **Schema 沒辦法事先固定**——必須邊執行邊發現該追蹤什麼欄位。
2. **某個早期觀察，當下沒被判斷為重要，後來才發現有關**——因為沒寫進狀態，事後也找不回來了。這是三者中最現實、最容易在生產環境踩到的一項——整個架構最根本的賭注，是賭模型在**當下**就能做出正確的取捨判斷，一旦賭錯，沒有回頭路。
3. **任務本身的目標就是「歷史軌跡」本身**——例如稽核、debug 溯源、解釋過去做了什麼決策。這種任務下，丟棄歷史直接跟任務目標衝突。

另外兩個附帶限制：多 agent 場景下共享狀態的同時寫入衝突，論文只說「可以自然擴展」但沒有實作或測試；grammar-constrained decoding 可以消除上表第 3 類的純語法錯誤，但解決不了第 1 類語意錯誤。

## ❓ 延伸提問：實務上，什麼時候該選 ReAct、什麼時候該選 SKILL.state？

一個常見的直覺是：「保留過去的動作紀錄比較有容錯空間，對強模型來說應該是利大於弊」。這個直覺需要拆成兩種不同意義的「容錯」：

- **意義一「事後可追溯、可除錯」**——保留歷史確實佔優勢，出錯後還能回頭檢查原始資料。SKILL.state 一旦資訊被丟棄就真的回不去了（對應 5.2 節第 2 點限制）。
- **意義二「模型在長距離任務中的準確率會不會因保留歷史而更穩」**——**Table 1 的實測數字反駁了這個直覺**，即使用論文測過最強的模型（Gemini-3-Flash），保留完整歷史的 Prompt(ReAct) 從 T=10 的 0.90±0.02 一路跌到 T=200 的 0.74±0.14，準確率下滑、標準差還放大 7 倍。這不是模型推理能力不夠，而是長 context 裡的資訊即使模型「看得到」，也不代表會可靠地「用得到」（lost-in-the-middle 現象，見下方第六節）——這個弱點換成更強的前沿模型也不會消失，只是程度可能緩和。所以「強模型 + 保留歷史 = 利大於弊」這個推論，在短中距離任務成立，但在長距離任務上被實測數據推翻。

**決策框架（六個軸線）**：

| 軸線 | 傾向 ReAct（保留歷史） | 傾向 SKILL.state（丟棄歷史） |
|---|---|---|
| ① 相關性何時能判斷 | 事後才發現某觀察有用（debug、探索式研究） | 當下就能判斷「這筆該不該記」（倉儲、資料庫狀態這類） |
| ② 軌跡本身是不是產出物 | 是（稽核、合規、解釋過程） | 否（只要最終狀態/結果對） |
| ③ 狀態的關聯密度 | 密集互相依賴（Git 圖、連鎖財務計算）——patch 一旦出錯，後果會無聲擴散、且無法回頭比對原文 | 稀疏獨立（像 500 個互不相關的貨架）——patch 錯誤的影響範圍被限制住 |
| ④ 預期執行長度 | 短～中（<25 步左右）：兩者準確率打平，用 ReAct 更簡單，不用多蓋一層 schema/validate 基礎設施 | 長（100+ 步）：歷史型準確率會退化且變異數放大，狀態型維持穩定 |
| ⑤ 模型能力 | 弱模型：合法但語意錯誤的 patch 被無感套用是重大風險 | 強模型能降低這個風險，但沒有證據顯示前沿模型完全免疫，只是沒測過 |
| ⑥ 對成本/延遲的敏感度 | 不敏感（少量呼叫、預算充足） | 敏感（高頻呼叫、要上生產環境，O(T²) 成本會爆表） |

**簡短判斷規則**：先問「這個 domain 的狀態，我能不能在事情發生的當下就決定該不該記」——如果能（結構清楚、關聯稀疏、任務夠長），選 SKILL.state；如果不能，或需要稽核軌跡，或狀態關聯密集，優先考慮 ReAct 或「狀態 + 有限歷史」的混合做法。

**一個中間選項值得注意**：Table 1、Table 6 裡的 **Stateful (LangGraph-style)** baseline——「結構化狀態 + 完整對話歷史同時保留」，不是純 ReAct，也不是 SKILL.state 那種「只留狀態」。這個做法在 Table 6（軟體版本庫）T=25 時甚至贏過 SKILL.state（0.94 vs 0.88）。如果不完全確定「當下就能正確判斷什麼該記」這個假設成不成立，「狀態 + 有限窗口的近期歷史」這種混合做法，可能比論文兩個極端選項都更務實——用結構化狀態處理有信心的部分，同時保留一小段滾動歷史當安全網，萬一 schema 漏掉了什麼，近期歷史還能補救。成本介於兩者之間，不是 O(1)，但也不是純線性疊加到底。

## 六、值得帶走的東西

### 這篇論文本身的貢獻

1. **把「結構化狀態 + 丟棄歷史」這個做法系統化，並給出複雜度證明（O(T) vs O(T²)）**——這是論文最扎實的部分，但核心概念（Dialogue State Tracking、MemGPT、LangGraph 的 state block）都已存在，論文的貢獻是「證明 + 系統化衡量」，不是提出新概念。
2. **Budget-matched control（Table 5）這個實驗設計本身**——證明贏的是「結構化」而非單純「變短」，這個實驗方法論比論文的核心主張更值得記住。

### 讀這篇論文過程中學到、脫離它也成立的東西（這才是真正的收穫）

1. **「準確率提升」vs「成本降低」是兩個獨立的宣稱**，論文常把它們包裝成同一個賣點，但證據力不對等。遇到任何宣稱「又快又準」的論文，習慣把兩個宣稱拆開分別檢查證據強度，通常其中一個會明顯強於另一個（這篇是成本的證據強得多）。
2. **判斷一個架構該用「保留歷史」還是「壓縮/丟棄狀態」，關鍵問題是「相關性能不能在資訊出現的當下就被正確判斷」**，不是「模型夠不夠強」。這是一個可以帶到未來任何「要不要保留原始資料 vs 只留摘要/結構化萃取」場景的通用判斷規則，不限於 agent 設計。
3. **檢查一篇論文的「across all X」這類全稱宣稱時，去找有沒有跨資料集/跨環境的反例**（像 Table 6 的 T=25）——全稱宣稱通常只在最有利的那個環境成立，附錄或次要表格反而常藏著誠實的反例。
4. **Lost-in-the-middle 現象**（Liu et al., 2024，本論文引用來解釋長 context 準確率退化的原因）——模型技術上「看得到」長 context 裡的資訊，不代表「用得到」，跟模型強弱是兩個獨立的維度，值得日後單獨深入了解。
5. **Dialogue State Tracking（DST）跟這篇論文的差異**——DST 是「狀態 + 完整對話歷史並存」，這篇是「只留狀態」。任何「要不要維護結構化狀態」的系統設計，都可以先問「歷史要不要跟狀態並存」這個子問題，而不是把「有沒有結構化狀態」當成唯一的分類維度。
6. **驗證機制（validate）能擋語法錯誤，擋不住語意錯誤**——這是這篇論文自己的實驗（68% 錯誤來自語意合法但錯誤的 patch）暴露出來、但論文沒有明講其架構性含義的發現。任何「用 runtime 驗證 LLM 輸出再套用」的設計，都要清楚意識到 validate 只能擋格式層面的錯，擋不住「格式對、但內容錯」這類錯誤——這是一個可遷移到任何「LLM 產生結構化輸出、程式碼自動套用」場景的提醒。
7. **架構設計如果消除了「回頭核對原始資料」這條路，就等於把賭注全押在「當下的判斷一定要對」上**——這個 trade-off 不只是這篇論文的特例，任何為了效率而丟棄原始資料、只留摘要/萃取結果的系統，都在做同一種賭注。
