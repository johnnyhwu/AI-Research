# Naive Prompt Optimization (NPO) 論文筆記

**論文資訊**：Yuan Chang, Xiaoqi Chen (Purdue University), *Naive Prompt Optimization: Rethinking the Need for Complex Prompt Search*, arXiv:2608.27266v1 [cs.AI], 27 Aug 2026.

---

## 30 秒版本

Prompt optimization（自動優化 prompt 的技術）近年的方法越做越複雜——維護多個候選版本、做搜索、做 Pareto 篩選（GEPA 就是代表）。這篇論文問：如果給 teacher model（負責改寫 prompt 的模型）看更豐富的回饋資訊（完整執行過程 + 每題分數，而不只是一個總分），再加上一個夠強的 teacher，是不是就可以完全不做搜索、只維護「一條路線」的 prompt 修訂，也能達到差不多甚至更好的效果？

他們提出的方法叫 **NPO（Naive Prompt Optimization）**：每一輪都執行目前版本的 prompt、收集結果，把「最近幾輪」的完整結果丟給 teacher model，讓它直接改寫出下一版 prompt，如此重複。實驗顯示：teacher 夠強時，NPO 能用比 GEPA 更少的執行次數打平甚至勝出；但這個比較本身有一個沒處理乾淨的漏洞（下面會細講），所以「贏在架構簡單」還是「贏在回饋資訊給得多」無法從論文中確定地拆開。

**研究貢獻本身接近零**——方法是既有技術（OPRO）的小幅修改。但論文裡「怎麼做公平的方法比較」這套實驗設計（配對隨機種子、約束解碼）做得紮實，是這份筆記真正想留下來的東西，篇幅上也會以此為重。

## 一、這篇論文想解決的問題

### 1.1 什麼是 automatic prompt optimization

如果你有一個「student model」（實際要拿去執行任務的模型），有兩種方式可以讓它表現更好：

1. **調整模型權重**：例如 RLHF、PPO、GRPO 這類強化學習方法，直接更新模型參數。
2. **調整 prompt（指令文字）**：模型權重完全不動，只是換一段更好的指令。

第二種方式的好處是**輕量、可攜**：不需要為每個任務或每個使用者訓練並維護一份專屬權重，只要換一段文字，就能部署到任何透過標準 API 存取的第三方模型上。Automatic prompt optimization 研究的就是「怎麼自動找到那段更好的指令文字」。

### 1.2 這個領域最近的方法越來越複雜

論文列出幾個代表性方法的演進：

- **OPRO**：把 LLM 當作優化器，根據「之前試過的 prompt 版本 + 對應的分數」，提出下一個新版本。
- **ProTeGi**：結合「文字梯度」的概念與 beam search（同時追蹤多條候選路線）。
- **MIPRO**：用模型生成候選 + 貝氏優化（Bayesian optimization，一種用機率模型猜測「下一個該嘗試的設定」的搜索方法）。
- **GEPA**：維護一整個候選 prompt 的「池」（pool），透過反思（reflection）產生新候選，並用 Pareto-based selection（保留在多個評估指標上都沒有被其他候選全面超越的那些候選）決定要留下哪些。

這些方法有個共同點：都在**同時維護多個候選版本**，並用某種機制決定該往哪個方向修改。

### 1.3 這些方法背後的隱含假設

會加上這些「多候選 + 搜索」機制，背後通常假設：如果只走一條路線（一次只有一個 prompt 版本，改壞了也回不去），很容易卡進局部最優——某一步修壞了就一路壞下去，浪費掉有限的執行次數（rollout）預算。維護多個候選、保留表現好的分支，是為了不把所有籌碼押在一條可能走偏的路線上。

### 1.4 NPO 想問的問題

如果每次修訂時，餵給 teacher model 的回饋夠豐富——不是只有「上一版 + 一個總分」，而是完整的執行過程與逐題分數——再加上 teacher model 本身夠強，那麼「只走一條路線、不做搜索」是否就足夠好，讓那些搜索機制的邊際效益趨近於零？

這是這篇論文的立論起點：**不是提出新演算法，而是質疑既有複雜度是否必要**。論文摘要的原文用詞是「stronger teacher reasoning can partially substitute for optimizer-side search complexity」——注意是「partially substitute」（部分取代），不是「完全不需要」，這是一個有條件的主張，不是斷言式結論。

## 二、NPO 方法本身

### 2.1 整體邏輯（一句話）

每一輪：用目前的 prompt 跑一批任務 → 收集這批任務的執行過程與分數 → 把「最近幾輪」的執行過程與分數一起丟給 teacher model → teacher 產生下一版 prompt。重複固定輪數。

### 2.2 Algorithm 1 逐符號拆解

原文 **Algorithm 1**（標題：*Naive Prompt Optimization with Sliding-Window Rollout Feedback*，論文 p.3）：

| 符號 | 意思 |
|---|---|
| P(i) | 第 i 輪的 prompt 版本，i 從 0 開始 |
| D | 完整的任務資料集（例如所有訓練問題） |
| N | 每輪抽樣的 minibatch 大小（例如一次跑 50 題） |
| Bi | 第 i 輪從 D 抽出的 N 題任務 |
| Ri | 第 i 輪跑完後收集到的：每題的完整執行過程（rollout trace）+ 每題的分數（reward） |
| W | sliding window 大小——teacher 這次能看到「過去幾輪」的資料範圍 |
| T | teacher model（負責改寫 prompt 的模型） |
| Y | 總共執行的輪數 |

核心步驟，用純文字符號表示（原文公式）：

```
sliding-window feedback = {R_j}，其中 j 從 max(0, i-W+1) 到 i

P(i+1) = T( P(i), {R_j}，j 從 max(0, i-W+1) 到 i )
```

白話講：teacher 拿到「目前這版 prompt」加上「最近 W 輪（含這一輪）的所有執行結果」，改寫出下一版 prompt。`max(0, i-W+1)` 這個寫法是處理「輪數還不夠 W 輪」的邊界情況——例如 i=0 時，往前推 W-1 輪會變成負數，這時候就從 0 開始算，不會出錯。

**除了單題資料，teacher 實際上還會看到更多東西**：論文原文明講（2.1 節）teacher 收到的是「the prompts, corresponding rollout traces, and rewards」——注意是複數的 prompts。也就是說，如果 window 涵蓋 2 輪，teacher 拿到的完整輸入是：

- 這 2 個版本的 **prompt 文字本身**
- 這 2 個版本各自的 **平均分數**
- 這 2 輪、每輪 N 題，總共 2×N 筆的 **(題目, 執行過程, 模型輸出, 單題分數)**

這一點很重要：如果 teacher 只看到單題結果，它只能判斷「這題錯在哪」；但因為它同時看得到「連續兩輪的平均分數變化」，它才有機會判斷「上一次的修改到底有沒有效」——這是 sliding window 設計想達成的效果（但下面〈批次抽樣的隱藏問題〉會說明這個效果其實沒有被保證）。

### 2.3 用論文自己的例子跑一次（Figure 1）

**Figure 1**（原文 caption：*"Overview of the Naive Prompt Optimization (NPO) workflow."*）給了具體示範。假設 minibatch 裡有一題是「What is the capital of France?」：

- **P(1)**（第 1 版 prompt）：`Given the fields 'question', 'summary_1', produce the fields 'query'.`
- 用 P(1) 跑這題，模型輸出是 "Berlin"，Reward = 0.0（答錯）
- 整批 minibatch 跑完，平均分數 P(1) = 0.56
- Teacher 看到「P(1) 的文字 + 一堆包含錯誤答案的執行紀錄」，判斷問題出在 prompt 沒講清楚「要給最終答案」，改寫出：
- **P(2)**：`Given the fields 'question' and 'summary_1', produce the field 'query'. Your goal is to provide the concise final answer.`

### 2.4 Sliding Window 的視覺化（W=2 時）

**Figure 2**（原文 caption：*"GEPA evolves candidate prompts in a pool, while NPO follows a simple lineage."*）右半邊畫出滑動窗格。用文字重新表示：

```
輪次:        0      1      2      3      4      5
分數 P(i):  0.25   0.68   0.69   0.60   0.65   0.73

Window 1 = {輪0}         -> 產生 P(1)
Window 2 = {輪0, 輪1}    -> 產生 P(2)
Window 3 = {輪1, 輪2}    -> 產生 P(3)
Window 4 = {輪2, 輪3}    -> 產生 P(4)
Window 5 = {輪3, 輪4}    -> 產生 P(5)
```

每個 window 只涵蓋「最近兩輪」的資料，輪次往前推進，window 也跟著往前滑動，且窗格之間會重疊（例如 Window 2 和 Window 3 都包含輪1）——這讓 teacher 修訂時，既能看到最新結果，也保有一點更早的脈絡。

對照 Figure 2 左半邊的 GEPA：GEPA 是一棵樹，每個節點是一個候選 prompt，可以從樹上任何表現好的節點分支出新候選；NPO 完全是一條線，P(0)→P(1)→P(2)→…，沒有分支，只有「往前看幾步」的差異。

### 2.5 與 OPRO 的差異

論文原文（2.1 節）：NPO 使用的「LLM 當迭代式 prompt 優化器」這個手法最早由 OPRO 提出；差異在於 OPRO 只把「之前評估過的 prompt + 對應的純量分數」給 teacher 看，而 NPO 給的是「完整的執行過程 + 逐題分數」。這是論文對 OPRO 差異的完整說明，原文沒有進一步展開細節。

### 2.6 NPO 方法：批次抽樣的隱藏問題 [C4]

Algorithm 1 第 2 行寫的是「Sample minibatch Bi of size N from D」——也就是**每一輪都重新從整個資料集裡隨機抽樣**一批新的 N 題，不是固定用同一批題目。

這件事對 sliding window 的設計意圖造成一個問題：teacher 之所以能看到「連續兩輪的平均分數」，原本的用意是讓它判斷「上一次的修改到底有沒有效」。但如果 P(i-1) 的分數是在批次 A（例如某一組 40 題）上算出來的，P(i) 的分數是在批次 B（另一組完全不同的 40 題）上算出來的，這兩個分數的差異裡，就同時混雜了「prompt 有沒有變好」跟「這批題目剛好比較難或比較簡單」兩種原因。Teacher 沒有辦法單從這兩個數字判斷差異到底來自哪一個原因。

**論文對這件事沒有明確處理**：論文 2.4 節確實有「shared pseudorandomness」（配對隨機種子）這個機制，但那是用來確保「NPO、GEPA、GRPO 這三種方法之間」的比較公平（見〈概念一〉），並沒有被用來處理「NPO 自己內部、連續輪次的 minibatch 是否一致」這個問題。Algorithm 1 的原文寫法就是逐輪重新抽樣，論文沒有進一步說明是否對這些批次做過任何控制。

*以下是我的推論，論文沒有寫：* 一個可能稍微緩解問題的因素是，每輪的分數是 N=40~50 題的平均值而非單題分數，樣本數夠大時，批次難度的隨機波動理論上會被平均掉一部分。但這只是「緩解」不是「解決」——尤其像 IFBench 這種任務，不同題目對應的約束類型難度差異可能很大，就算平均 40 題，批次組成不同仍可能造成分數有系統性落差而非單純隨機雜訊。論文完全沒有討論或做敏感度分析。

## 三、對照方法：GEPA 與 GRPO（簡述）

這一節沒有深入拆解演算法細節，只記錄理解結果所需的最低限度背景。

**GEPA**（2.2 節）：維護一個候選 prompt 的池。從池中抽出一個「父代」prompt，用一批反思資料（reflection minibatch）修訂它；修訂後的版本只有在「對這批反思資料有改善」時才會被接受。被接受的修訂會在驗證集上評估，加入候選池，之後用這個驗證表現做 Pareto-based 的父代篩選（保留沒有被其他候選全面超越的版本）。論文使用標準 GEPA 流程（不含 GEPA-merge 變體）。

**GRPO**（2.3 節）：作為「權重層級」的 RL 對照基準。對每一組執行結果（rollout group），把獎勵減去該組平均值、除以標準差，得到相對優勢，用於更新一個 LoRA（低秩適應）adapter，主幹權重與 prompt 都保持固定。在雙人遊戲環境中，訓練中的一方對戰一個固定、未訓練過的基礎模型，只有訓練中一方的 LoRA 參數會更新；並且刻意讓訓練中一方在一半的隨機化回合中先手、另一半後手，避免先後手造成的獎勵分布差異汙染訓練訊號。

## 四、實驗方法論設計（本篇論文工程價值最高的部分）

### 概念一：配對隨機種子（Shared Pseudorandomness）[C1]

**要解決的問題**：比較 NPO、GEPA、GRPO 三種方法時，如果每個方法各自在「隨機生成」的環境上執行（例如 Minesweeper 每次隨機佈雷、位置都不同），那麼最後分數的差異可能不是「方法本身比較強」造成的，而是「剛好抽到比較簡單的關卡」造成的。這是一個典型的干擾變因——想比較的是方法優劣，卻混進了環境難度的隨機波動。

**機制**：針對每個環境，先用一組固定的隨機種子生成一批環境實例，讓 NPO、GEPA、GRPO **共用同一組種子序列**。也就是說，NPO 執行的第 135 次 rollout，跟 GEPA 執行的第 135 次 rollout，起始盤面完全一樣（同樣的地雷位置、同樣的已知數字），只有各自的 prompt / policy 不同，導致後續動作不同。

**為什麼這個設計成立（類比統計學的配對設計 paired design）**：這跟統計實驗裡的「配對比較」（例如 paired t-test，或醫學實驗裡「同一批受試者服藥前後比較」）邏輯一致——核心精神是「把會造成雜訊的變因鎖定成相同」，讓組間差異只反映真正想測的那個變因。這裡鎖定的變因是「環境實例的隨機性」，想測的變因是「optimization 方法的好壞」。不鎖定隨機種子時，比較的是「獨立樣本」（unpaired），組間變異會被環境難度的隨機波動稀釋，需要更多樣本才能看出真正差異；鎖定種子後等於做了「配對」，雜訊被大幅消除，統計檢定力明顯提高。

**論文的具體示範（Figure 3）**：**Figure 3**（原文 caption：*"We use shared pseudo-randomness to reduce environment-induced noise when comparing."*）並排展示 "Rollouts #135, NPO" 與 "Rollouts #135, GEPA"：兩邊的 Minesweeper 盤面（地雷位置、已知數字）完全相同（圖中用骰子圖示標示「shared seed」），差異只出現在 prompt 不同，導致模型做出不同判斷（NPO 選了 [3 1]，GEPA 選了 [0 2]）。

*注：這不是這篇論文原創的技巧。* 用固定種子做配對比較是實驗設計裡行之有年的通用手法，在 RL / bandit 研究中很常見。論文只是把它套用到「比較不同 prompt optimizer」的場景，屬於工程紀律的展現，不是方法論創新——但正因如此，這個技巧的可遷移價值反而更高，值得用在任何自己設計的 A/B 比較實驗中。

### 概念二：Constrained Decoding 完整機制 [C2]

**要解決的問題**：論文（2.4 節）提到前期實驗發現，格式錯誤（模型輸出的動作字串不符合環境要求）佔了失敗案例中不小的比例。如果 A 方法的失敗大多來自「格式寫錯」而非「決策真的比較差」，把這些失敗算進最終分數，就等於錯誤地懲罰了 A。他們要把「決策品質」跟「格式遵循能力」分開，只評測前者。

**第一步：怎麼「遮蔽」不合法的 token**

模型每一步生成下一個 token 時，原本會對詞彙表裡所有 token 都算出一個機率。Constrained decoding 做的事：把不合法的 token 機率設成 0，只留下合法的那幾個，重新正規化成一個機率分布。

用一個簡單數字示範：假設某一步，原始機率是：

```
A: 0.4    B: 0.3    C: 0.1    D: 0.1    E: 0.1
```

但這一步只有 A 和 B 合法。做法：把 C、D、E 設成 0，剩下 A=0.4、B=0.3，相加是 0.7，重新除以 0.7：

```
A: 0.4/0.7 ≈ 0.571    B: 0.3/0.7 ≈ 0.429
```

論文公式（原文用 softmax 形式表示，這裡用純文字符號寫出，等價於上面的計算）：

```
q(t | s) = exp(z_t(s)) / Σ[u∈A(s)] exp(z_u(s))，t 屬於 A(s)
```

其中 s 代表目前已生成的前綴字串，A(s) 代表在這個前綴之後，合法的下一個 token 集合，z_t(s) 是模型對 token t 的原始分數（logit）。

**第二步：為什麼需要一棵「樹」**

單一步驟的遮蔽只解決了「這一步要選哪個 token」，但完整的動作字串（例如 `[3,4]`）通常要好幾個 token 才能拼完，而且**每一步「合法的 token 有哪些」，會隨著前面已經打出來的內容而改變**。

舉例：假設環境只允許兩個合法動作 `[3,4]` 和 `[2,5]`。一開始合法的第一個 token 只有 `[`；打完 `[` 之後，合法的下一步變成 `3` 或 `2`；如果選了 `3`，下一步只剩 `,`；再來只剩 `4`，最後只剩 `]`。「合法 token 集合」在每一步都不同，且取決於前面已經打了什麼。

這正是需要**字首樹（prefix trie）**的原因——樹的每個節點代表「目前已生成的前綴」，從節點出發能走的邊，就是「合法的下一個 token」。走到葉節點，就代表湊出一個完整合法動作。用箭頭表示這個 2 動作範例的樹狀結構：

```
根節點(尚未生成)
  --[--> "["
           --3--> "[3" --,--> "[3," --4--> "[3,4" --]--> "[3,4]" (葉節點)
           --2--> "[2" --,--> "[2," --5--> "[2,5" --]--> "[2,5]" (葉節點)
```

**第三步：把遮蔽跟樹接起來，逐步往下走**

在樹上每一個節點都重複同樣的事：看這個節點下有哪些合法子節點 → 對這些合法選項的原始分數做遮蔽+重新正規化 → 依機率選一個、走到對應子節點 → 重複直到走到葉節點。

用上面的 2 動作範例走一次，並算出 `[3,4]` 的完整機率：

- **根節點**：合法下一步只有 `[` 一個選項，機率鎖定為 1（原文明講：只有一個合法延續的節點，強制轉移機率為 1）。
- **`[` 節點**：合法下一步有 `3`、`2` 兩個真正的分岔點。假設遮蔽+正規化後算出 q(3|[)=0.6、q(2|[)=0.4。
- **`[3` 節點**：合法下一步只有 `,`，機率鎖定為 1。
- **`[3,` 節點、`[3,4` 節點**：後面的 `4` 和 `]` 也都是唯一合法選項，機率同樣鎖定為 1。

把整條路徑的機率連乘：

```
P([3,4]) = q([|根) × q(3|[) × q(,|[3) × q(4|[3,) × q(]|[3,4)
         = 1 × 0.6 × 1 × 1 × 1
         = 0.6
```

關鍵效果：除了「選 3 還是選 2」這個真正的分岔點之外，其他每一步都是唯一選項（機率鎖定為 1），所以整條路徑的機率幾乎完全由「真正的決策分岔點」決定——**格式相關的 token（`[`、`,`、`]`）完全不影響最終機率**。

**額外的邊界情況（推理預算用完）**：如果模型在推理 token 用完前，都還沒生成結束推理的標記，論文不會直接把它算成失敗（因為那樣會把「決策品質差」跟「不知道自己快沒 token 額度」混在一起算）。而是在額度快用完前，強制插入結束推理的標記，再用一小段保留的動作預算，逼模型仍要從合法動作裡選一個。

*注：關於 Figure 11 的說明——* 論文 **Figure 11**（原文 caption：*"Token-prefix trie used for constrained decoding over the set of legitimate action strings. At each node, next-token probabilities are renormalized over the valid outgoing edges that lead to legitimate actions."*）用一個具體的 4 動作範例（`[3,4]`、`[3,1]`、`[2,5]`、`[4,5]`）畫出帶數字的字首樹。但這張圖經 PDF 文字擷取後，邊標籤與分支的對應關係無法可靠還原（部分數字加總對不上 1，無法確定是擷取錯位還是對應關係讀錯）。**因此上面〈第三步〉裡使用的具體數字（0.6、0.4）是我自己設定的示範數字，不是論文原圖的數字**，只是借用相同的樹狀結構做說明。若需要精確數值，需回頭查閱原始 PDF 的 Figure 11。

Constrained decoding 這套技術本身不是這篇論文原創——locally constrained decoding／"local product of experts" 有既有文獻（論文引用 [9]），grammar-constrained 生成在業界也很常見（論文引用了 lm-format-enforcer [3]，這類工具如 Outlines 也是基於同樣的原理）。論文是把既有工具套用在「消除跨方法比較的格式雜訊」這個場景。

### 概念三：Local vs Global 兩種機率算法 [C3]

論文提到計算「葉節點（完整動作）機率」有兩種方式，這篇論文選用其中一種，另一種只是拿來對照說明。

**定義**

- **Local**（這篇論文採用）：每走到樹上一個節點，就先遮蔽不合法 token、對合法選項重新正規化，再往下走一步——就是〈概念二〉第三步描述的逐步流程。
- **Global**：不在中途做任何遮蔽或正規化，讓模型用原本自由生成時的機率，把整條路徑的每一步機率直接連乘；等所有合法動作（葉節點）的乘積都算完後，最後才在這些葉節點之間做一次正規化。

**Global 的具體流程（拆成五步）**

Global 需要用到「teacher forcing」這個技巧：正常生成是模型自己一個 token 接一個 token生成；teacher forcing 則是**強制**塞給模型一段指定好的內容，只問模型「如果前面是這段內容，你對下一個 token 的機率分布長怎樣」，藉此算出「模型生成出某段固定文字」的機率，即使模型自己從未真的生成過這段話。

1. 先窮舉所有合法的完整動作字串（例如 `[3,4]`、`[2,5]`）——這也是為什麼 Global 只適用在動作集合有限、可窮舉的場景，如果合法輸出是開放式自然語言就做不到。
2. 對每個候選字串，用 teacher forcing 依序問模型「原始、未被遮蔽過」的逐步機率（例如對 `[3,4]` 依序問 p("["）、p("3"|"["）、p(","|"[3"）、p("4"|"[3,"）、p("]"|"[3,4"）……）。
3. 把這些機率連乘，得到這個候選的「原始分數」。
4. 對其他候選重複同樣流程。
5. 把所有候選的原始分數放在一起做正規化，再從中採樣或選出最終動作。

**用一組自建的數字，比較 Local 與 Global 的結果差異**（同樣是示範用數字，不是論文原圖數字）：

假設模型原本（自由生成、未遮蔽）對每一步的原始機率是：

```
路徑 [3,4]：
  P("[")          = 0.05
  P("3" | "[")    = 0.02
  P("," | "[3")   = 0.90
  P("4" | "[3,")  = 0.015
  P("]" | "[3,4") = 0.85

路徑 [2,5]：
  P("[")          = 0.05
  P("2" | "[")    = 0.015
  P("," | "[2")   = 0.88
  P("5" | "[2,")  = 0.01
  P("]" | "[2,5") = 0.65
```

（`0.85` 與 `0.65` 這兩個「該不該收尾打 `]`」的信心值差異，純粹是模型 tokenizer 或訓練資料造成的巧合，跟「該選哪個動作」這個真正的決策完全無關——這正是問題所在。）

**Global 算法**（直接連乘，最後才正規化）：

```
路徑[3,4] 連乘 = 0.05 × 0.02 × 0.90 × 0.015 × 0.85 ≈ 0.0000115
路徑[2,5] 連乘 = 0.05 × 0.015 × 0.88 × 0.01 × 0.65 ≈ 0.0000043

P([3,4]) = 0.0000115 / (0.0000115+0.0000043) ≈ 0.73
P([2,5]) = 0.0000043 / (0.0000115+0.0000043) ≈ 0.27
```

**Local 算法**（每個節點先遮蔽再正規化）：只有 `[` 節點是真正的分岔點：

```
q(3|[) = 0.02/(0.02+0.015) ≈ 0.571
q(2|[) = 0.015/(0.02+0.015) ≈ 0.429
```

其他節點都只有一個合法選項，機率鎖定為 1，所以：

```
P([3,4]) = 1 × 0.571 × 1 × 1 × 1 = 0.571
P([2,5]) = 1 × 0.429 × 1 × 1 × 1 = 0.429
```

**兩者並列比較**：

```
              [3,4]   [2,5]
Global:       0.73    0.27
Local:        0.571   0.429
```

Global 算出的 0.73 vs 0.27 差距這麼大，有很大一部分其實是被 `]` 這個 token 的原始信心值（0.85 vs 0.65）拉出來的，而這個信心值差異只是格式收尾時的雜訊，跟「該選哪個動作」的真正決策無關。Local 因為把「別無選擇」的節點直接鎖定成 1，結果只剩真正的決策分岔點在決定最終機率，更貼近「模型真正想選哪個動作」的訊號。

**為什麼論文選 Local**：為了確保比較不同 optimization 方法時，看到的機率差異反映的是「決策品質」，而不是「格式收尾 token 剛好比較幸運」。

**Global 的優勢在哪裡（以下是計算機科學／機率論的一般知識，不是論文內容，論文完全沒有討論這個角度）**：

Global 算出來的機率，剛好等於用貝氏定理算出來的條件機率。想像完全不做任何限制，讓模型自由生成，如果生成出不合法動作就丟掉重來（這叫拒絕採樣，rejection sampling），一直重複直到抽到合法動作為止。這個過程最終收斂到的機率分布，用貝氏定理寫出來正好是：

```
P(某合法動作 | 這個動作合法) = P(該動作，原始未遮蔽機率) / Σ(所有合法動作的原始未遮蔽機率)
```

這正是 Global 算法的公式本身。換句話說，**Global 是「不斷重新生成、丟掉不合法結果，直到抽中合法動作為止」這整個過程最終會收斂到的機率分布**，完整保留了模型對每個合法選項「原本真正的相對信心」，沒有被人為扭曲過。而 Local 每走到一個節點就先局部正規化，等於是**主動抹掉**了模型對格式收尾等 token 的部分原始信心資訊——不是巧合誤差，是這個算法設計上必然發生的系統性偏移，用這個代價換取「一次生成就完成、不用窮舉候選」的運算效率。

**兩者取捨整理**：

| | Local | Global |
|---|---|---|
| 運算量 | 低（一次自迴歸生成即可） | 高（每個候選都要跑一次 teacher forcing 評分） |
| 是否等於模型原始信心的真實條件分布 | 不是，會被格式 token 等雜訊系統性扭曲 | 是，數學上等價於拒絕採樣得到的分布 |
| 適合場景 | 想要的是「決策品質」，格式雜訊是想主動消除的東西（本篇論文的情境） | 想要精確得知模型對每個選項的真實相對信心，例如做模型校準度（calibration）分析 |
| 是否保證輸出合法 | 保證（兩者都只在合法動作集合內選擇/採樣） | 保證 |

值得強調：Local / Global 從來不是「要不要保證格式合規」的取捨——兩者都 100% 保證輸出合法（合法動作清單本身就是有限、事先窮舉好的集合），差別只在於「合法選項之間的機率該怎麼分配」。

## 五、主要結果

### 5.1 執行效率（Figure 4）

**Figure 4**（原文 caption：*"Performance of NPO and GEPA on IFBench and HotpotQA under different teacher models, showing NPO's advantage with stronger teachers."*）比較 NPO 與 GEPA 在 IFBench、HotpotQA 兩個任務上、換用不同 teacher（Qwen3-8B、DeepSeek-V4-Flash、GPT-5.5）時的表現。

- NPO 換成更強的 teacher 時表現明顯提升：teacher 換成 GPT-5.5 時，NPO 收斂最快、最終分數最高，兩個任務都能用比 GEPA 更少的執行次數（rollout）達到同等或更好的表現。
- GEPA 換 teacher 影響較小：GEPA+GPT-5.5 跟 GEPA+Qwen3-8B（自己當自己的 teacher）表現大致持平。

**重要限制（承接第二節〈批次抽樣的隱藏問題〉之外的另一個混淆變因）**：NPO 使用的 reflection minibatch 大小是 50（IFBench）/ 40（HotpotQA），而 GEPA 使用原論文預設的 3——差了 10~15 倍。雖然兩者最終「總 rollout 預算」相近（NPO 3,500/6,800，GEPA 3,593/6,871），但這代表 NPO 每次修訂看到的回饋資訊量遠比 GEPA 豐富。論文完全沒有做「把 GEPA 的 minibatch 也調到 50 重跑一次」這樣的乾淨對照，因此「NPO 比 GEPA 更有效率」這個結論裡，混雜了「單一路線 vs pool 搜索架構誰比較好」與「每次修訂看到的回饋資訊量誰比較多」兩個變因，論文沒有拆開驗證，無法從中判斷 NPO 的優勢究竟來自何者。

### 5.2 跨模型 Prompt 遷移（Figure 5）

**Figure 5**（原文 caption：*"Performance improvements when prompts learned by NPO are transferred verbatim to different student models, within and across model families."*）測試把在小模型（Qwen3-8B、Llama-3.1-8B）上優化好的 prompt，原封不動套用到更大的模型上（不重新優化）。

- 同 family 內的遷移效果最強、大多穩定為正（例如 Qwen3-8B 優化好的 prompt 套到 Qwen3-14B、Qwen3-32B）。
- 跨 family 遷移（例如套到 Llama 系列）也大多正向，但幅度較小、變異較大。
- 少數例外是負值（例如 IFBench+GEPA 遷移到某些模型出現 -0.07、-0.002），但屬於少數情況，不是普遍現象。
- 這一節證明的是 prompt optimization 相對於權重層級 RL 的一個實際優勢——不需重新訓練就能遷移；但 NPO 和 GEPA 在這一點上表現相近，這不是 NPO 獨有的優勢。

### 5.3 與 GRPO 的比較（Figure 6）

**Figure 6**（原文 caption：*"Performance improvement under different optimization methods for 22 TextArena games."*）在 22 個 TextArena 遊戲環境中，控制相同的 rollout 預算，比較 NPO、GEPA、GRPO。

- 沒有全面贏家：NPO 與 GEPA 表現大致相當，沒有誰系統性地比較好；GRPO 在部分「prompt optimization 較無力」的任務上明顯更強（例如 2048 遊戲 GRPO 提升 +6.9，遠超 NPO 的 +0.22 與 GEPA 的 +0.90）。
- 部分雙人策略遊戲（如 Chess、ConnectFour、Crusade）三種方法表現都不佳、甚至出現負值，顯示這類任務可能本質上不太適合這三種方法中的任何一種。
- 論文明確指出：這個結果跟過去文獻常見的「GEPA 系統性優於 RL」印象不同——這裡沒有觀察到 GEPA 全面勝過 GRPO 的現象。

### 5.4 是否有評估答案洩漏（簡述）

論文額外檢查了一件事：因為 NPO 搭配強 teacher 時常產生比 GEPA 長很多的 prompt，他們擔心這些 prompt 是否不小心「背」進了訓練或驗證集的正確答案，導致分數提升只是資料污染而非真實能力提升。**Figure 7**（原文 caption：*"Measuring gold-answer leakage into optimized prompts (HotpotQA)."*）顯示：優化後的 prompt 跟訓練集答案的重疊度會隨迭代自然上升（這符合預期，因為 prompt optimization 本來就該從訓練範例中萃取有用資訊），但跟驗證集答案的重疊度幾乎沒有增加，人工檢查也確認少量重疊只是訓練跟驗證題目剛好共享同一個答案，不是直接洩漏驗證題目本身。結論：觀測到的效能提升不太可能是評估答案洩漏造成的。

## 六、值得帶走的東西（按耐久度排序）

### 這篇論文本身的貢獻（偏低）

- 核心方法（用 sliding-window 回饋取代 pool-based 搜索）是 OPRO 的漸進式修改，不是新機制。
- 核心賣點「NPO 用更少 rollout 打平/贏過 GEPA」這個結論，因為 reflection minibatch 大小沒對齊（NPO 50 對 GEPA 3）而混雜了兩個變因，論文自己沒有拆開驗證——這個結論可信，但「贏在哪」無法確定歸因。
- 比較站得住腳的貢獻反而是修正性的：推翻了「GEPA 系統性優於 RL（GRPO）」這個過去文獻的印象，誠實展示三種方法各有勝負、沒有全面贏家。這種「打臉過度宣稱」的價值，通常比正面宣稱更可信。
- Gold-answer leakage 檢查算是這篇論文對自己實驗誠信度的把關，屬於附加分，不是核心貢獻。

一句話：**這篇論文的貢獻接近一份「乾淨的 ablation/baseline 研究」，方法論創新趨近於零，真正的價值在下面這三點。**

### 脫離這篇論文也成立的東西（真正該帶走的）

1. **配對隨機種子做公平比較（shared pseudorandomness）**：跟統計上的配對設計（paired design）同一個邏輯——把會製造雜訊的變因鎖死成相同，才能讓組間差異乾淨反映真正想測的變因。以後要比較任何兩套系統或流程（不限 AI），這個原則都適用。

2. **Constrained decoding 的完整機制**：字首樹（prefix trie）+ 逐節點遮蔽/重新正規化，是 Outlines 這類約束生成工具的底層邏輯——不只是「知道有這個功能」，而是具體知道它逐 token 怎麼運作。

3. **Local vs Global 的取捨規則（本篇筆記技術含量最高的部分）**：
   - Local：運算量低、一次生成完成，但系統性地抹掉格式 token 的原始信心，只保留真正的決策分岔點——適合只在乎「決策品質」、想主動消除格式雜訊的場景。
   - Global：數學上等價於拒絕採樣（rejection sampling）得到的真實條件機率，忠實保留模型原始信心，但運算量高（每個候選都要跑一次 teacher forcing）——適合需要精確得知模型真實相對信心的場景，例如模型校準度分析。
   - 背後更通用的觀念：**拒絕採樣與條件機率的等價關係**，這在機率論與 MCMC（馬可夫鏈蒙地卡羅）方法中是通用工具，不只用在 constrained decoding 這一個場景。
