# Resource2Skill：從人類製作資源蒸餾可執行技能

> arXiv 2606.29538v4，Microsoft Research，2026 年 5 月初版 / 7 月修訂
> 作者：Yijia Fan, Zonglin Di, Zimo Wen 等（Microsoft Research / UC Santa Cruz / 上海交大）

---

## 30 秒版本

**問題**：software agent（做 PPT、Excel、網頁、3D 場景這類「創作型」任務的 agent）缺乏程序性知識——不知道該用哪個工具模式、怎麼分解任務、失敗了怎麼救。現有技能庫大多是人工寫的、純文字的，或從 agent 自己的操作記錄裡挖出來的，唯獨「教學影片」這種人類最自然的學習素材幾乎沒被用上。

**做法**：把教學影片、程式碼庫、文章、參考成品這四種資源，用一個 vision-capable LM 蒸餾成結構化的「技能」條目（文字說明＋視覺縮圖＋可執行程式碼＋metadata），組織成一個階層式的 Skill Wiki。Agent 執行任務時，先用詞法檢索縮小候選範圍，再讓 LM 從候選裡挑幾個技能來用；技能庫涵蓋不到的地方，同一套蒸餾流程可以即時上線去補。

**結果**：7 個領域、4 個模型上，平均比不給技能庫的 agent 高 11.9 個百分點，也贏過 Claude Code / Codex 這兩個現成 harness。

**判斷**：
- **研究價值：低**。核心檢索與選擇機制不是新方法，是既有 RAG 元件的組合。唯一算得上發現的是「影片是不可替代的資訊來源」，但這組實驗沒控制資源數量，說服力打折。
- **工程價值：中低，且有明顯缺口**。系統骨架（schema、驗收 gate、MCP 介面）值得參考，但論文對「怎麼從原始資料蒸餾成技能」這個最關鍵的技術細節寫得極度單薄，你沒辦法照抄出一套完整流程。
- **這篇論文真正的價值，不在論文本身的貢獻，而在於它用大規模實驗驗證了幾個你原本可能就會有的直覺**——技能庫規模有飽和點、純向量檢索不一定比詞法檢索好、驗證程式碼可執行性時要分層處理而不是二元丟棄。這幾點在下面「值得帶走的東西」一節有完整說明，是這份筆記真正該精讀的部分。

## 一、問題設定

Software agent 要完成的任務（做投影片、算 Excel、搭 3D 場景……）成功與否，往往不是靠事實知識，而是靠「程序性知識」：怎麼分解目標、用哪個工具模式、中間該檢查什麼狀態、出錯了怎麼救。

現有的技能庫來源大致三種：人工手寫、agent 自己操作記錄裡累積出來的、從文字/程式碼資源裡挖出來的。這篇論文指出一個被忽略的來源：**教學影片**。影片能傳遞的東西——操作的時間順序、每一步的視覺效果、難以言傳的設計選擇——文字很難完整承載；但把影片直接塞進 agent 的 context 又太貴太冗長。論文要解決的核心問題就是：**怎麼把影片這類高維度多模態資源，自動蒸餾成 agent 可以高效檢索、執行的技能，同時不丟失影片獨有的資訊**。

## 二、核心方法

### 技能的資料結構

每個技能是一個四元組加 metadata：

```
s = (p, x_text, x_visual, x_code, m)
```

| 符號 | 意義 |
|---|---|
| p | 技能在該領域分類樹（taxonomy）裡的路徑，例如 blender/lighting/jewelry |
| x_text | 名稱、機制、適用條件、輸入、預期效果 |
| x_visual | 縮圖、截圖、渲染預覽、圖表（可為空） |
| x_code | 可執行或可改寫的程式碼片段（可為空，此時是「純參考型」技能） |
| m | metadata：分類、標籤、來源類型、驗證狀態，用於篩選、稽核、追溯 |

**【概念 A】為什麼視覺要是一等公民**：一般常見的技能庫格式（例如 Anthropic 的 Agent Skills 規範：`SKILL.md` + `scripts/` + `references/` + `assets/`）裡，圖片、範例通常只是丟進泛用的 `assets/` 資料夾，跟其他附件沒有 schema 上的區別。Resource2Skill 把 `x_visual` 明確寫進技能定義的核心 tuple，是因為論文的中心論點就是「視覺/時序資訊不能被文字取代」——這個論點後面在資源來源的 ablation（Table 3）裡有被驗證。如果你的技能庫格式沒有把視覺當一等公民對待，設計上等於預先假設了視覺資訊不重要，這個假設不一定站得住腳。

一個實務上的細節：`x_visual` 是「用到才解析」的——縮圖只是路徑引用，只有 agent 主動要求視覺模態時才會被載入成圖片，不計入文字 token 預算。這代表擁有視覺內容不必然拉高每次呼叫的 token 成本。

### 技能存放格式對照（與 Anthropic Agent Skills 的差異）

如果你的組織採用 Anthropic 的 Agent Skills 標準（`SKILL.md` 內含 YAML frontmatter + 指令，外加 `scripts/`、`references/`、`assets/`），跟 Resource2Skill 的格式不是同一套邏輯，轉換時要注意：

| 能直接搬 | 會斷掉的部分 |
|---|---|
| x_code → scripts/ | x_visual 的「用到才解析、不進文字 token 預算」機制——Anthropic 標準沒有這個區分，你得自己在 orchestration 層重建 |
| x_text → SKILL.md 內文 | 階層分類樹 + 兩段式檢索（下面會講）——Anthropic 標準是讓 Claude 自己讀每個技能的 description 判斷相關性，是完全不同的檢索邏輯 |
| meta.json → SKILL.md 的 YAML frontmatter | exec_ok 驗收 gate——不是檔案格式的一部分，是 Resource2Skill 自己的 pipeline 步驟，換了格式這道驗證不會自動存在 |

論文自己（Related Work）也點名比較過：Anthropic Agent Skills 是「人工撰寫、沒有自動化獲取機制」的技能庫，Resource2Skill 的賣點正是自動蒸餾＋影片來源＋階層分類，兩者是不同設計哲學下的產物，不是誰取代誰的關係。

### 四階段 Pipeline

```
[1. 資源蒐集]        [2. 蒸餾 f_θ]           [3. 五道驗收 gate A_D]    [4. 存入階層式 Wiki]
影片/程式碼庫         →  一次 vision LM 呼叫   →  完整性/來源/去重/       →  按分類路徑存放
/文章/參考成品            + 確定性前後處理           模態一致/可執行性

                    [執行:agent 檢索+組合技能]  ←────┘
                    ├─ MetaBrowse 兩段式選技能
                    ├─ apply（透過 MCP 執行到 domain）
                    └─ render（把成品轉成 judge 看得懂的格式）
                            │
                    候選池篩不出堪用技能時
                            ↓
                    即時觸發同一套 (f_θ, A_D) 補洞
                    （online pool，不併回 offline wiki）
```

**第 2 步（蒸餾 f_θ）**：本質是一次 vision-capable LM 呼叫，加上確定性前處理（影片抽關鍵幀、程式碼庫用 AST 抓區塊、文章切段落）與後處理（正規化、算 SHA1 技能 ID）。論文強調這一步**不是**訓練過的模型，就是 prompt engineering 加結構化輸出。

> **這裡論文沒有講清楚的地方（誠實記錄，不是我幫忙補完）**：「key-frame sampling」怎麼取樣完全沒說明——固定間隔？場景切換偵測？跟旁白對齊？論文自己在引言主張影片的價值在於視覺效果與時間順序，但很多這類資訊其實是老師在旁白裡口頭講出來的，pipeline 描述裡卻完全沒提到語音轉文字（ASR）這一步，是否真的完全沒用到語音、還是有做只是沒寫，論文文字本身無法判定。此外 prompt template 內容從未公開、沒有蒸餾品質的人工抽查數字、一支影片如何切分成多個技能的邏輯也沒有交代。如果你想把這套流程套用到自己的資料上，這一段（也是全篇技術含量最高、最該講清楚的部分）幾乎沒有可以照抄的東西，需要自己從零設計。

**第 3 步（五道驗收 gate）**：全部是確定性規則檢查，**不是** LLM-as-judge。每一道各自檢驗 tuple 裡不同的元素：

| Gate | 檢驗對象 | 檢查什麼 |
|---|---|---|
| Completeness（完整性） | m + x_text | frontmatter 必填欄位、x_text 最短長度、至少一個模態非空 |
| Provenance（來源） | m | source_path 是否指向 connector manifest 裡真實記錄過的資源 |
| Deduplication（去重） | m | SHA1(domain, source_path, node_index) 當技能 ID，撞到既有 ID 就併入既有條目 |
| Modality consistency（模態一致） | m vs x_visual/x_code | 宣稱有的模態，硬碟上是否真的存在對應檔案 |
| Structural executability（可執行性） | x_code | sandbox 實際跑一次程式碼，能不能執行、有沒有產出非平凡結果 |

**【概念 B】驗收 gate 該怎麼分層設計**：這五道 gate 裡最值得記住的設計是 executability 沒過的處理方式——**不是直接丟棄，而是降級成「reference-only」**。程式碼沒驗證過，agent 就不會直接執行它（避免在 live 環境跑未驗證的程式碼有風險），但 `x_text`／`x_visual` 描述的原理跟效果仍然可用，agent 可以照著這些描述自己重寫程式碼。這個設計把「這段程式碼可信嗎」和「這個知識有價值嗎」拆成兩個獨立判斷，而不是用單一二元開關（合格/丟棄）粗暴地處理——如果你要幫自己的技能庫（例如 Anthropic Skills 格式裡的 `scripts/`）加驗證機制，這是一個成本不高、值得直接套用的思路：對每個技能的 script 跑一次輕量 smoke test，通過的照常執行，沒通過的在 SKILL.md 裡註明「僅供參考」，讓 agent 退回自己讀說明重寫程式碼，而不是整個技能被丟棄或帶著不可靠的程式碼硬跑。

> 補充提醒：論文的驗證是離線建庫時做一次、結果寫死進 metadata。如果你的情境是內部工具版本持續迭代，這個驗證結果會過期，需要自己考慮要不要定期重跑，這是論文情境（相對穩定的公開教學資源）跟企業內部場景一個實質的差異。

> 另外五道 gate 裡有個盲點：Modality consistency 只檢查「檔案存不存在」，不檢查 `x_visual` 的**內容品質**（圖片是否真的相關、清晰）——沒有任何一道 gate 在把關這件事。

**執行階段**：`apply` 是唯一的執行動作，透過 MCP 把選中的技能程式碼送進真正在跑的 domain 軟體（例如 Blender headless）執行，背後接一份「capabilities manifest」，不支援的操作會回傳結構化的「做不到」訊息而非直接報錯。`render` 則是把 domain 軟體實際產出的東西轉成 judge 看得懂的格式（截圖、渲染圖、音檔）——judge 全程**只看 render 出來的成品，不看原始檔案或程式碼**，所以就算程式碼邏輯正確，只要渲染結果視覺上不理想，分數還是會被扣。

**Online acquisition**：當第一階段檢索（下面會講）篩不出堪用候選時，同一套 `(f_θ, A_D)` 會被即時呼叫，去搜資源、蒸餾、驗收，結果存進一個獨立的「online pool」，**不會**併回離線 wiki——這是刻意的實驗控制，避免線上搜尋讓離線庫越用越大、混淆其他實驗對照。量化效果上（Table 2）：在標準任務集上開啟線上補洞幾乎沒差（+0.7pp），但在專門設計來測「離線庫覆蓋不到」的任務集上，同樣 100 個線上技能能把分數從 41.2% 拉到 62.8%（+21.6pp）——論文的結論是線上搜尋是「補洞用」，不是「日常加分用」。

### 技能檢索與選擇：MetaBrowse 兩段式

**第一階段（詞法篩選，縮小候選池）**：

```
CK(q) = TopK[ s ∈ ΣD ] of BM25( q, name(s) ⊕ tags(s) ⊕ applicability(s) ⊕ p(s) )
```

符號說明：`q` 是使用者的任務需求，`ΣD` 是該領域完整技能庫，`⊕` 是字串串接（把技能的名稱、標籤、適用條件、**分類路徑 p(s)** 全部接起來當一份文件跟 q 比對），K 在論文設定裡是 20。

關鍵設計：把分類路徑 p(s) 也塞進比對文字裡，讓「技能在分類樹上的位置」直接影響詞法分數，論文原話是希望讓技能庫「favour skills sitting in topically relevant subtrees」，而不是把整個 wiki 當一堆散裝技能做全庫比對。舉例：query 是「render a jewelry ring with dramatic lighting」，一個路徑是 `blender/lighting/jewelry-macro` 的技能，光是路徑裡的 "lighting"、"jewelry" 就會跟 query 有詞頻重疊、貢獻分數；路徑是 `blender/geometry/procedural-terrain` 的技能則幾乎沒有重疊，連進候選池的機會都低。

**第二階段（LM 選子集）**：

```
S(q) = π_φ( q, {Φ(s) : s ∈ CK(q)} )
```

`π_φ` 是語言模型本身（不是專門訓練過的選擇器），`Φ(s)` 是技能 s 依目前設定暴露的內容（metadata 加上開放的 text/visual/code 視圖），實際選出的技能數量 n=5。這一步是「選子集」不是「排序取 top-n」——LM 可以選 0 個技能，讓 agent 退回自己寫程式碼，這跟一般推薦系統的 top-K 排序不同，選擇器有「全部拒絕」的權力。

**【概念 E】檢索策略：一個反直覺結果**：論文比較了六種選技能的策略（固定技能庫、agent、judge、候選預算），結果純向量檢索（Embed）反而是表現最差的策略之一（60.0%），比純 BM25（66.0%）還差，論文兩段式的 hierarchy-then-LM 方法拿到最高分（68.9%）。這個結果值得記住：**別預設 dense retrieval 天生比 lexical retrieval 好**——技能跟任務之間的「適配度」有時候不是純語意相似度能抓到的，需要一層額外的判斷（不管是 LM 還是規則）去把關組合性、互補性。

## 三、主結果與一個關鍵盲點

### Table 1（Main comparison, overall score）主要數字（GPT-5.4 backbone）

| 系統 | Web | Excel | Reaper | PPT | Blender | CAD | UE5 | 平均 |
|---|---|---|---|---|---|---|---|---|
| w Skills | 82.4 | 76.4 | 77.3 | 64.8 | 44.1 | 55.7 | 67.3 | 66.9 |
| w/o Skills | 68.7 | 58.6 | 73.2 | 55.4 | 29.5 | 48.7 | 29.1 | 51.9 |
| ClaudeCode-H | 81.6 | 69.2 | 75.8 | 61.6 | 36.7 | 53.3 | 35.7 | 59.1 |
| Codex-H | 79.8 | 70.4 | 76.1 | 62.3 | 35.9 | 53.0 | 36.3 | 59.1 |

跨 28 個 model-domain cell，w Skills 全數贏過 w/o Skills，配對 Wilcoxon 檢定在抽樣的 9 個 cell 全部 p < 10⁻³（多數 p < 10⁻⁸），統計上站得住腳。w Skills 也在 26/28 cell 贏過兩個 harness 裡較強的那個，UE5 領域增益最大（+30～40pp）——論文解讀是 free-form code agent 很難靠 UE5 Python API 從零組出及格場景，常直接掉到最低品質門檻以下算 0 分。

### 【概念 C】主結果的一個關鍵盲點

`ClaudeCode-H`、`Codex-H` 兩個對照組，論文原文（Appendix C）明講完全沒有掛載 Skill Wiki、也不能上網搜尋（Codex-H 甚至被設定成 `web search to cached`，連即時瀏覽都關掉），是純粹用通用 harness 硬做。也就是說 Table 1 比的其實是「有技能庫」vs「完全沒有技能庫、也不准自己去找」——**贏的到底是 Resource2Skill 這套 pipeline 設計本身，還是單純『有沒有技能庫』這個更粗的變因，論文的實驗設計拆不開**。

論文另外有一組實驗（Section 4.4.1，`Flat` vs `Our Wiki` vs `w/o Skills`）某種程度上局部回應了這個問題：`Flat` 條件是把技能內容做成純文字、無結構的扁平清單（拿掉分類瀏覽、metadata 篩選、視覺、程式碼），結果 `Flat` 已經比 `w/o Skills` 高出一大截，`Our Wiki`（完整階層式多模態）只比 `Flat` 再多贏 2.5～8.2pp。這代表：**技能庫的「組織形式」（階層多模態 vs 扁平文字）貢獻沒有想像中大，大部分增益來自『有沒有技能庫』這個更粗的變因**。

但要注意：`Flat` 條件裡的技能內容，仍然是用 Resource2Skill 自己的蒸餾方法產生的，只是呈現形式改了。也就是說論文測了「組織形式的貢獻」，但完全沒測「蒸餾方法本身的品質貢獻」——換一個更陽春的蒸餾方式（甚至人工寫的技能庫），最終效果會不會一樣好，這個問題從頭到尾沒被觸碰，也是這篇論文在方法論上最大的validity 缺口。

## 四、Ablation：資源來源混合（全篇最紮實的實驗）

### Table 3（Ablation: resource-source mix）

拿掉影片，平均分從 68.9% 掉到 59.4%（掉近 10 個百分點）；**只用影片**（不含其他三種）反而還贏過「其他三種來源加起來但不含影片」7.4 個百分點——影片單獨的貢獻比其他三種來源加起來還大。下降最兇的是 Excel（-14.2pp）跟 Web（-11.5pp），論文的解讀是這些領域的操作順序、畫面變化，文字難以完整承載。

這是一組控制得比較乾淨的實驗（只換一個變因：資源來源，其他全部固定），是全篇最能站得住腳的發現。

> **一個論文沒處理、但值得懷疑的地方**：影片來源蒐集到的技能數量，有沒有跟其他三種來源打平了才比？如果教學影片本來就比文章/程式碼庫容易找到大量高品質內容，那「影片贏」有可能部分只是「資料量比較多」贏的，不完全是「影片這個模態本質上資訊量更高」贏的。論文沒有控制資源數量這個變因，這是一個合理的質疑，但論文本身沒有給出可以驗證或反駁的證據。

## 五、技能庫規模：報酬遞減（Section 4.3.1）

固定 agent、judge、brief、wiki 介面，讓技能庫大小從 0 一路長到完整規模，測 5 個核心領域：

- 表現隨技能庫變大**單調上升**，大約在 **200 個技能左右飽和**
- 0→200 這段吃掉大部分增益（Reaper 只漲 +3.1pp，Excel 漲最多 +14.2pp）
- 200 之後曲線變平，400→Full 每個領域最多再漲 +0.8pp

各領域完整規模（Full）的最終分數：Web 82.4、Excel 76.4、Reaper 77.3、PPT 64.8、Blender 44.1。

### 【概念 D】可遷移的觀念

**存在飽和點、早期報酬遞減**這件事本身是可遷移的判斷框架：不需要一開始就想著蒐集海量資源、蒸餾出上千個技能才能上線，先求覆蓋核心常見操作的技能（論文的數字是「前 200 個」），性價比遠高於持續擴充長尾。但「200」這個具體數字**不能直接套用**到你自己的情境——這是這篇論文 7 個特定軟體創作領域、用他們自己的分類方式量出來的數字，換到不同性質的資料（例如企業內部知識），飽和點會落在哪裡完全未知，只能借用「存在報酬遞減」這個定性觀念,不能借用具體數字。

## 七、值得帶走的東西（按耐久度排序）

### 這篇論文本身的貢獻
- 幾乎接近零。核心檢索與選擇機制是既有元件的組合，不是新方法；唯一算得上發現的「影片不可替代」（Table 3），控制變因不夠乾淨（資源數量未控制），說服力有限。
- 論文的骨架（schema、五道驗收 gate、MCP 執行介面）作為系統設計的參考範例有一定價值，但最關鍵的「怎麼蒸餾」技術細節寫得極度單薄，無法直接照抄。

### 讀這篇論文過程中學到、脫離它也成立的東西（這才是主要收穫）

1. **技能庫的組織形式（Table 3的資源多樣性、Table 4 的多模態、階層分類）貢獻有限，比不上「有沒有技能庫」這個更粗的變因** —— 評估任何「A 系統 vs B 系統」的比較時，先問清楚兩者除了你關心的那個變因之外，是不是還有別的東西沒被控制住。這篇論文的 Table 1 就是一個活教材：ClaudeCode-H / Codex-H 完全沒有技能庫，這個對照本身就沒有回答「Resource2Skill 設計得好不好」這個問題。

2. **技能庫規模存在飽和點，早期報酬遞減** —— 建自己的技能庫時，優先覆蓋核心常見場景，不要一開始就追求大而全的覆蓋率。具體飽和的技能數量因情境而異，不能照搬論文的數字。

3. **純向量檢索不一定比詞法/結構化檢索好** —— 技能跟任務之間的適配度，有時候需要額外一層判斷（LM 或規則）才能抓到，別預設 embedding-based retrieval 天生更聰明。

4. **驗證機制要分層設計，不要二元丟棄** —— 「這段程式碼可信嗎」跟「這個知識本身有沒有價值」是兩個獨立的判斷。程式碼驗證沒過，不代表整個技能條目沒用，可以降級成「參考用」而保留其說明與範例，讓 agent 自己重新產生程式碼。這個思路可以直接套用到任何技能庫（包含 Anthropic Agent Skills 格式）裡的 `scripts/` 驗證機制上：跑一個輕量 smoke test，通過的照常用，沒通過的在說明檔裡標註「僅供參考」。
