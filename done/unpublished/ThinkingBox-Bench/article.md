# ThinkingBox：評估 agent 要看資料庫最後變成什麼，還要重複跑才知道穩不穩

**來源**：[ThinkingBox 與 ThinkingBox-Bench](https://arxiv.org/abs/2608.19741)（arXiv 2026/08）

## 前言

一個客服 agent 回覆「已幫您延期」，對話正常結束，工具呼叫也沒報錯。看起來辦好了，但資料庫裡可能多了一筆違反公司政策的紀錄。這篇論文要解決的就是這種「看起來成功、其實失敗」的評估盲點。

作者做了兩件事。第一是 ThinkingBox，一個沙盒：agent 跟模擬使用者對話、呼叫隔離的工具，結束後拿資料庫終態跟標準答案逐條比對，全部通過才算成功。第二是 ThinkingBox-Bench，507 個商業流程任務（零售、訂房、保險、銀行內部 IT、顧問公司 IT/HR），每題重複跑 20 次。結果最高的是 Claude Opus 5，pass@1 約 66.5%；但同一個模型「至少成功一次」和「次次成功」的差距可以非常大，例如 Kimi-K3 是 93.89% 對 17.60%。單次成功不等於可靠。

這篇文章依序講問題、方法、實驗結果、解讀限制，最後整理兩個脫離這篇論文也成立的判斷。文中標（推論）的是本文作者的推測，標（自編）的是為了說明而自己舉的例子，標（一般知識）的是論文以外的背景說明，其餘都是論文內容。

## 問題：只看回覆和 tool call 為什麼不夠

很多 agent 評估只看兩樣東西：最後的回覆，以及 tool call（agent 呼叫外部工具的動作）。這種評估抓不到「看起來把事辦完、資料庫卻被改錯」的失敗。

真實的商業工作，例如改訂房、退款、更新理賠、轉派內部請求，都有多輪對話、政策限制和後端副作用。成敗取決於資料庫最後變成什麼樣，不是 agent 說了什麼。

### 一個具體例子：保單延期

這是論文附錄 D.4 的 Case 4：

1. 使用者問：保單逾期 7 天，能延期嗎？
2. agent 查到這個客戶近 12 個月已有 2 次分期安排，而這個客戶等級的上限就是 2 次。
3. agent 還是呼叫了延期工具，次數變成 3。
4. agent 回覆「已延期」，結束對話。

同一段過程，用兩種方式評估，結論完全相反：

| 評估方式 | 看到什麼 | 判定 |
| --- | --- | --- |
| 只看回覆與 tool call | 正常結束、有呼叫寫入工具、沒報錯 | 看起來成功 |
| 比對資料庫終態 | 多出第 3 次分期安排，違反上限 | 失敗（標準答案是拒絕） |

差別只在看「過程的樣子」還是看「世界最後變成什麼」。這篇論文主張後者才算數。

### 要做成自動化測試，得處理四件事

要把這類工作變成能自動驗證的測試，需要同時處理四個挑戰（推論：論文沒有明列這份清單，是本文作者依論文 Introduction 與第 3 節整理的）：

- **C1 對的做法不只一種**：同一件事可以用不同步驟完成。
- **C2 使用者資訊不完整**：使用者不會一開始就把所有細節講完。
- **C3 每次嘗試互不干擾**：重複跑的時候，前一次不能影響後一次。
- **C4 單次成功不等於可靠**：跑一次成功，不代表每次都會成功。

每個挑戰在方法裡對應哪個設計，整理在〈四個挑戰各對應哪個設計〉。

## ThinkingBox 的做法

三個重點：沙盒讓 agent 跟模擬使用者對話、呼叫隔離的工具；每個任務由五個元素定義；判定只比對資料庫終態與副作用。

### 沙盒怎麼運作

沙盒裡有四個角色，每次嘗試都從同一個初始世界重新開始：

| 角色 | 做什麼 |
| --- | --- |
| 模擬使用者 | 由另一個 LLM 扮演，有固定目標，只在被問到時才透露細節 |
| LLM agent | 被測對象，決定要回話還是呼叫工具 |
| 隔離的工具 session | 透過 MCP 提供的工具，背後接這個任務專屬的資料庫 |
| Orchestrator（協調者） | 負責重置、轉送訊息、執行工具、記錄整段過程 |

MCP（Model Context Protocol）是讓 agent 用統一格式呼叫外部工具的協定（一般知識）；論文本身只說這些工具「MCP 相容」。

只有 agent 能呼叫會改資料的工具，使用者只負責說話。所以論文把模擬使用者當成環境的一部分，而不是第二個決策者。

一次嘗試大致分成五步，其中第 3 步會來回很多輪（推論：各步內容是本文作者依角色表、任務組成與判定方式整理的）：

1. **重置**：資料庫回到初始狀態，開一個新的隔離 session。
2. **開場**：模擬使用者送出固定的開場請求。
3. **來回對話與工具呼叫**：agent 可以追問使用者，也可以呼叫工具；這一步會重複多輪。
4. **結束**：對話正常結束。
5. **判定**：抽出這次實際改了什麼，逐條檢查（細節在〈怎麼判定成功〉）。

第 1 步的重置是 C3 的關鍵：兩次嘗試不能共用資料庫列、快取或副作用，否則重複跑出來的數字不可信。第 3 步的來回是 C2 的關鍵：agent 會追問，模擬使用者才會把藏著的資訊說出來。

### 一個任務由哪些東西組成

白話講，一個任務 = 起始世界 + 使用者想要什麼 + 可用工具 + 使用者的行為規則 + 一份 agent 看不到的檢查清單。論文式 1 寫成：

$$
x = (b_0,\ g,\ \mathcal{T},\ \mathcal{U},\ \mathcal{C})
$$

- $b_0$：初始後端狀態，也就是資料庫一開始的樣子。
- $g$：使用者目標，包含固定的開場請求，以及「被問到才會透露」的事實。
- $\mathcal{T}$：agent 可用的工具集合。
- $\mathcal{U}$：模擬使用者的行為規則（合作、不編造資訊）。
- $\mathcal{C}$：$m$ 條隱藏的可執行檢查，agent 和使用者都看不到。

題目、世界、工具、使用者規則全都固定，唯一會變的是 agent 怎麼做。

拿論文附錄 E.2 的零售會員升級任務來對照：

| 元素 | 這個任務裡是什麼 |
| --- | --- |
| $b_0$ | 客戶 CUS-40030，等級 standard，沒有有效會籍 |
| $g$ | 開場：「我想升級 TechHome Plus，要免運與回饋點數」。藏著的事實：姓名、email |
| $\mathcal{T}$ | 查客戶、查會籍、開 ticket、更新會籍等工具 |
| $\mathcal{U}$ | 只能用 $g$ 裡的事實回答，不能編造 |
| $\mathcal{C}$ | 論文沒說明這題的具體檢查；從通過的軌跡看，應該是會籍變成 plus、ticket 狀態正確（推論） |

### 怎麼判定成功

任務跑完後，不看 agent 做了哪些步驟，只比對資料庫最後的樣子和標準答案。流程分兩步：先抽出這次實際改了什麼，再逐條檢查，全部通過才算 1。

**第一步：抽出副作用**（論文式 3）

$$
e = \Delta_x(s_0,\ s_T,\ \rho)
$$

- $s_0$：起始狀態。
- $s_T$：結束時的狀態。
- $\rho$：整段對話與工具紀錄。
- $\Delta_x$：這個任務專屬的抽取器。
- $e$：實際發生的改動清單。

概念上就是拿起點和終點的資料庫相減，得到這次到底改了什麼。

**第二步：所有檢查相乘**（論文式 4）

$$
V(x,\rho) = \prod_{i=1}^{m} c_i(s_T,\ e,\ \rho),\qquad c_i \in \{0,1\}
$$

- $c_i$：第 $i$ 條檢查，通過是 1，不通過是 0。
- $m$：這個任務的檢查條數。

相乘的意思是：每條都過，$V$ 才是 1；任何一條沒過，整題就是 0。因為比對的是標準終態，不同的操作順序只要結果相同都算對（這就處理了 C1）。檢查能抓三種錯：

- **值不對**：例如會籍等級寫錯（自編）。
- **該有的沒有**：例如下面 Case 1 少掉的那一列存取權限。
- **多出不該有的**：例如重複紀錄，或改到無關的資料。

看一個實際失敗的例子，論文附錄 D.4 的 Case 1，存取權限升級。標準流程是：撤銷舊的 read only 指派、授予並驗證 write non-PII only、建一張 ticket 記錄。結果：

| 檢查 | 標準答案 | 實際 |
| --- | --- | --- |
| Okta 存取列數 | 13 | 12，缺 write non-PII only 那一列 |
| Zendesk ticket 數 | 6 | 5 |

兩項都不符，所以 $V = 0$。有趣的是，agent 在回覆裡宣稱已經更新了存取權限；但判定看的是資料列，不是 agent 怎麼說。這題的 $m$ 是多少、這兩項是否各算一條 $c_i$，論文沒說（推論：各算一條）。

### Benchmark 怎麼建

作者把五個領域的客服與營運流程做成 507 個可執行任務。建構分三步：

1. 設計流程模板：訂單變更與退款、訂房修改、理賠更新、帳戶支援、內部 IT/HR 請求，全部使用合成資料。
2. 把模板做成具體任務：起始資料庫、工具、使用者設定、政策文件、檢查。
3. 在沙盒裡實際跑過一遍，再過濾。

過濾會剔除這幾類任務：工具壞掉、起始狀態自相矛盾、目標含糊、結果無法驗證、檢查依賴 tool call 順序，以及對話不會正常結束的。留下來的每題都「能跑、能重置、有明確標準答案」，而且至少有一種可行的完成方式。

| --- | --- | --- | --- | --- | --- |
| 任務數 | 98 | 104 | 100 | 104 | 101 |
| 工具數（寫／讀） | 16 / 17 | 10 / 28 | 14 / 19 | 13 / 19 | 13 / 14 |
| 政策文件字數 | 945 | 3,684 | 2,471 | 3,392 | 1,747 |

從表 1 可以看到，Booking 的政策文件最長（3,684 字）、每題平均動作數最多（8.8）；Retail 這兩項都最少（945 字、4.4）。

〈要做成自動化測試，得處理四件事〉列的四個挑戰，在方法裡各有對應：

| 挑戰 | 對應設計 | 在哪一節 |
| --- | --- | --- |

## 實驗結果

同樣 507 題，每個模型各跑 20 次，比較三件事：單次成功、至少成功一次、次次成功，彼此差多少。下面的表 2、表 3 都只節錄論文完整排行榜中的幾個模型。

### 排行榜與領域差異

各模型的單次成功率（pass@1）差距很大，而且沒有哪個模型在每個領域都最強。

先講分母：每個模型跑 507 題 × 20 次，共 10,140 次嘗試，pass@1 就是其中成功的比例。各領域欄的分母則是該領域題數 × 20。

| 模型 | Retail | Auto | Booking | Bank | Consulting | 平均 |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 80.71 | 65.80 | 49.95 | 70.62 | 66.19 | 66.50 |
| GPT-5.4 | 76.33 | 62.65 | 68.12 | 65.34 | 54.60 | 65.36 |
| Kimi-K3 | 82.24 | 50.80 | 61.83 | 41.35 | 51.63 | 57.37 |
| Claude Opus 4.6 | 68.62 | 8.30 | 21.11 | 35.67 | 27.82 | 32.09 |
*表 2 — 各領域 pass@1（%，節錄），每題重複 20 次後微平均。欄名沿用論文原文：Auto、Bank 和表 1 的領域名稱不同，論文節錄中沒有明說兩者怎麼對應。（來源：原始論文 Table 4。）*

從表 2 能讀出幾件事：

- **前兩名分不出高下**：Opus 5 的 66.50 對 GPT-5.4 的 65.36，在誤差範圍內。
- **各領域冠軍不同**：Retail 是 Kimi-K3，Booking 是 GPT-5.4，其餘三個領域是 Opus 5。
- **同一模型跨領域落差很大**：Opus 4.6 在 Retail 有 68.62，在 Auto 只有 8.30。
- **領域難度不一**：論文的模型裡有一部分經過 RL（強化學習）訓練；排除這些之後的 14 個模型，領域平均以 Retail 最高（58.81），Auto 最低（33.18）。

### 發現與可靠：pass@k 和 pass^k

同一題跑 20 次，「至少成功一次」和「次次都成功」差很多，而後者才是能放心把工作交給 agent 的程度。這對應 C4。

兩個指標的定義：

- **pass@k**：跑 $k$ 次，至少成功一次的機率。回答「有沒有能力做到」。
- **pass^k**：跑 $k$ 次，全部成功的機率。回答「能不能穩定做到」。

這套可靠度評估的做法是沿用 τ-bench（Yao et al., 2024）。

舉個數字感受一下（自編）：一題跑 20 次，成功 14 次。那麼 pass@1 = 14/20 = 0.7；pass@20 = 1，因為至少成功過一次；pass^20 約是 $0.7^{20} \approx 0.0008$，連續 20 次全對幾乎不可能。同一題，三個指標可以從 1 一路掉到接近 0。

*圖 1 — 論文的總覽圖。右半部（B）顯示：在 507 題、每題 20 次嘗試下，pass@20 遠高於 pass@1，20 次全成功則遠低於 pass@1。（來源：原始論文 Figure 1。）*

| 模型 | pass@1 | pass@20 | pass^20 | 從沒成功的題數 | 20 次全成功的題數 |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 66.50 | 79.09 | 47.53 | 106 | 241 |
| GPT-5.4 | 65.36 | 91.12 | 30.62 | 45 | 128 |
| GPT-6 Astra | 58.31 | 71.01 | 46.89 | 147 | 231 |
| Kimi-K3 | 57.37 | 93.89 | 17.60 | 31 | 68 |
| Qwen3.8-27B | 51.70 | 89.35 | 10.93 | 54 | 38 |
*表 3 — 重複跑 20 次的「發現」與「可靠」指標（%，節錄）。（來源：原始論文 Table 15。）*

表 3 裡最值得看的是三種不同的型態：

- **Kimi-K3：碰得到，但不穩。** pass@20 全場最高（93.89%），pass^20 只有 17.60%。多試幾次幾乎每題都碰得到成功，但很少穩定成功。論文把這個落差叫做 discovery–reliability gap。
- **GPT-6 Astra：成功的很穩，但範圍窄。** 在論文完整排行榜上 pass@1 排第五，pass^20 卻排第二。它會的題目做得很穩，但有 147 題從來沒成功過。
- **Opus 5：最穩，但碰得到的範圍也較窄。** pass^20 最高（47.53%），pass@20 只有 79.09%。

只看 pass@1，看不出「穩」和「碰運氣」的差別。

## 解讀這些數字時要注意的地方

- **分數量的是後端結果，不是溝通品質。** 507 題裡有 477 題只檢查後端終態，不看最終回覆；只有 30 題（Booking 和 Bank 各 15 題）另外加了回覆檢查。也就是說，agent 把狀態改對、卻對使用者講錯話，大多數題目照樣算通過。
- **只測結果唯一的任務。** 每題只有一個標準終態，有多個合理結果的流程在建構時就排除了。這個基準測的是政策明確、結果唯一的工作，不涵蓋需要判斷取捨的情境。
- **抽取器的實作沒有說明。** $\Delta_x$ 怎麼從起點和終點的資料庫算出改動，論文沒有交代。
- **Retail 分數高的原因只是推測。** 論文推測 Retail 最高是因為模型熟悉標準電商流程，但沒有實驗驗證。

## 值得帶走的兩個判斷

這兩點脫離這篇論文也成立，設計自己的 agent 評測時可以直接用。

### 比對終態，不比對過程

評估 agent 要看「世界最後變成什麼」，而不是看它說了什麼、呼叫了什麼。

為什麼成立：回覆和 tool call 只是「agent 宣稱做了什麼」，資料庫才是「實際發生了什麼」，兩者可以脫鉤。〈一個具體例子：保單延期〉就是例子：正常結束、有寫入、沒報錯，資料庫卻違反了上限。

怎麼用：先定義「正確的終態」，也就是該有哪些紀錄、哪些資料不能動，再用它來判定。不要要求 agent 照一條固定步驟走。

### pass@k 與 pass^k 要分開量

「有沒有能力做到」（pass@k）和「能不能穩定做到」（pass^k）是兩個問題，定義見〈發現與可靠：pass@k 和 pass^k〉。

為什麼成立：表 3 的 Kimi-K3 與 GPT-6 Astra 正好是兩種相反的型態，而 pass@1 把它們都藏起來了。

怎麼用：要把 agent 放進有後果的流程（改資料、退款）時，看 pass^k；只想知道能力上限，或系統本身有重試機制時，看 pass@k。

---

## 結論

- ThinkingBox 把「agent 有沒有把事辦完」改成比對資料庫終態：抽出副作用、逐條檢查、全過才算成功，不同的操作路徑只要終態一致都算對。
- ThinkingBox-Bench 有 507 個商業流程任務、五個領域，每題重複跑 20 次。Claude Opus 5 的 pass@1 最高（66.50%），但和 GPT-5.4 在誤差範圍內；各領域冠軍也不同。
- 「至少成功一次」和「次次成功」可以差很遠，Kimi-K3 是 93.89% 對 17.60%。單次成功不等於可靠。
- 分數主要反映後端結果，不反映對使用者說了什麼；而且只涵蓋結果唯一的任務。
