# ThinkingBox 與 ThinkingBox-Bench 論文筆記

Oct 26, 2026 · @Johnny Wu

## 三十秒版本

這篇論文([arXiv:2608.19741](https://arxiv.org/abs/2608.19741))把「agent 有沒有把事辦完」改成比對資料庫終態來判定。沙盒讓 agent 與模擬使用者對話、呼叫隔離的工具,結束後把後端狀態與標準答案逐條檢查,全部通過才算成功。作者據此建了 507 個商業流程任務(零售、訂房、保險、銀行內部 IT、顧問公司 IT/HR),每題重複跑 20 次。結果顯示 Claude Opus 5 的 pass@1 最高,約 66.5%;同一模型的「至少成功一次」(pass@20)與「次次成功」(pass^20)差距很大,例如 Kimi-K3 是 93.89% 對 17.60%。單次成功不等於可靠。

## 怎麼讀與索引

主軸:評估 agent 要比對「世界最後變成什麼」,並且重複跑才看得出穩不穩。主線每一節回答一個問題,本筆記沒有獨立的概念詳解段。

- **1 問題**:為什麼只看回覆或 tool call 不夠
- **2 方法**:沙盒怎麼運作、任務由什麼組成、怎麼判定成功、基準怎麼建
- **3 實驗**:各模型的成績,以及「至少成功一次」與「次次成功」的差距
- **4 值得帶走**:兩個脫離這篇論文也成立的判斷

## 1 問題

只看回覆或 tool call(agent 呼叫外部工具的動作)的評估,抓不到「看起來把事辦完、資料庫卻被改錯」的失敗。真實商業工作(改訂房、退款、更新理賠、轉派內部請求)有多輪對話、政策限制與後端副作用,成敗取決於資料庫最後變成什麼樣。

要把這類工作變成可自動驗證的測試,需要同時處理四件事:對的做法不只一種、使用者資訊不完整、每次嘗試互不干擾、單次成功不等於可靠。論文沒有明列這份清單,這是依 Introduction 與第 3 節整理,屬推論;各項對應的設計見第 2 章結尾的對照表。

### 例子:保單延期(論文附錄 D.4 Case 4)

1. 使用者:保單逾期 7 天,能延期嗎?
2. agent 查到近 12 個月已有 2 次分期安排,這個客戶等級的上限就是 2 次。
3. agent 仍呼叫延期工具,次數變成 3。
4. agent 回覆「已延期」並結束。

| 評估方式 | 看到什麼 | 判定 |
| --- | --- | --- |
| 只看回覆與 tool call | 正常結束、有呼叫寫入工具、沒報錯 | 看起來成功 |
| 比對資料庫終態 | 多出第 3 次分期安排,違反上限 | 失敗(標準答案是拒絕) |

兩種評估看的是同一段過程,差別只在看「過程的樣子」還是看「世界最後變成什麼」。這篇論文主張後者才算數。

## 2 方法

沙盒讓 agent 與模擬使用者對話、呼叫隔離的工具;每個任務由五個元素定義;判定只比對資料庫終態與副作用。

### 2.1 沙盒怎麼運作

沙盒讓 agent 跟一個會回話的模擬使用者對話,呼叫的是隔離的工具,每次嘗試都從同一個初始世界重新開始。

| 角色 | 做什麼 |
| --- | --- |
| 模擬使用者 | 由另一個 LLM 扮演,有固定目標,只在被問到時才透露細節 |
| LLM agent | 被測對象,決定回話還是呼叫工具 |
| 隔離的工具 session | 透過 MCP 暴露的工具,背後接這個任務專屬的資料庫 |
| Orchestrator(協調者) | 負責重置、轉送訊息、執行工具、記錄整段過程 |

MCP(Model Context Protocol)是讓 agent 以統一格式呼叫外部工具的協定(一般知識,不是論文內容);論文只說工具「MCP 相容」。只有 agent 能呼叫會改資料的工具,使用者只負責說話,所以論文把使用者視為環境的一部分,而不是第二個決策者。

&#91;embedded content: 一次嘗試的流程 · 5 步,第 3 步可來回多輪\]

步驟 1 的重置是 C3 的關鍵:兩次嘗試不能共用資料庫列、快取或副作用,否則重複跑出來的數字不可信。步驟 3 的來回是 C2 的關鍵:agent 能追問,模擬使用者才會把藏著的資訊說出來。

### 2.2 一個任務由哪些東西組成

一個任務 = 起始世界 + 使用者想要什麼 + 可用工具 + 使用者的行為規則 + 一份 agent 看不到的檢查清單(論文式 1)。

```latex
x = (b_0,\ g,\ \mathcal{T},\ \mathcal{U},\ \mathcal{C})
```

- b0:初始後端狀態,也就是資料庫一開始的樣子
- g:使用者目標,包含固定的開場請求,以及「被問到才會透露」的事實
- T:agent 可用的工具集合
- U:模擬使用者的行為規則(合作、不編造資訊)
- C:m 條隱藏的可執行檢查,agent 與使用者都看不到

題目、世界、工具、使用者規則都固定,唯一不固定的是 agent 怎麼做。

例子:論文附錄 E.2 的零售會員升級任務。

| 元素 | 這個任務裡是什麼 |
| --- | --- |
| b0 | 客戶 CUS-40030,等級 standard,沒有有效會籍 |
| g | 開場:「我想升級 TechHome Plus,要免運與回饋點數」。藏著的事實:姓名、email |
| T | 查客戶、查會籍、開 ticket、更新會籍等工具 |
| U | 只能用 g 裡的事實回答,不能編造 |
| C | 論文未說明這題的具體檢查;從通過的軌跡推論:會籍變 plus、ticket 狀態正確 |

### 2.3 怎麼判定成功

任務跑完後,不看 agent 做了哪些步驟,只比對資料庫最後變成什麼樣與標準答案,所有檢查都過才算成功。分兩步:先抽出這次實際改了什麼,再逐條檢查、全過才算 1。

**抽出副作用**(論文式 3)

```latex
e = \Delta_x(s_0,\ s_T,\ \rho)
```

- s0:起始狀態
- sT:結束時的狀態
- ρ:整段對話與工具紀錄
- Δx:這個任務專屬的抽取器
- e:實際發生的改動清單

拿起點與終點的資料庫相減,得到這次到底改了什麼。抽取器怎麼實作,論文未說明。

**所有檢查相乘**(論文式 4)

```latex
V(x,\rho) = \prod_{i=1}^{m} c_i(s_T,\ e,\ \rho),\qquad c_i \in \{0,1\}
```

- c\_i:第 i 條檢查,過是 1,不過是 0
- m:這個任務的檢查條數

每條都過,V 才是 1;任何一條不過,整題就是 0。因為比對的是標準終態,不同的操作順序只要結果相同都算對。檢查能抓三種錯:值不對、該有的沒有、多出不該有的(例如重複紀錄或改到無關資料)。

例子:論文附錄 D.4 Case 1,存取權限升級。標準流程是撤銷舊的 read only 指派、授予並驗證 write non-PII only、建 ticket 記錄。

| 檢查 | 標準答案 | 實際 |
| --- | --- | --- |
| Okta 存取列數 | 13 | 12,缺 write non-PII only 那一列 |
| Zendesk ticket 數 | 6 | 5 |

兩項都不符,所以 V = 0。agent 在回覆中宣稱已更新存取,但判定看的是資料列。這題的 m 是多少、兩項是否各算一條 c\_i,論文未說明(推論:各算一條)。

### 2.4 Benchmark 怎麼建

作者把五個領域的客服與營運流程做成 507 個可執行任務,每個任務都要通過「能跑、能重置、有明確標準答案」的檢查才保留。

1. 設計流程模板(訂單變更與退款、訂房修改、理賠更新、帳戶支援、內部 IT/HR 請求),全部使用合成資料。
2. 把模板做成具體任務:起始資料庫、工具、使用者設定、政策文件、檢查。
3. 在沙盒實際跑過一遍並過濾。

過濾會剔除:工具壞掉、起始狀態自相矛盾、目標含糊、結果無法驗證、檢查依賴 tool call 順序,以及對話不會正常結束的任務。留下的每題至少有一種可行的完成方式。

|  | Retail | Booking | Insurance | Neobank | Consulting |
| --- | --- | --- | --- | --- | --- |
| 任務數 | 98 | 104 | 100 | 104 | 101 |
| 工具數(寫 / 讀) | 16 / 17 | 10 / 28 | 14 / 19 | 13 / 19 | 13 / 14 |

每題只有一個標準終態(附錄 A、B.5 到 B.6):路徑可以不同,終態必須一致。有多個合理結果的流程在建構時就被排除,所以這個基準測的是政策明確、結果唯一的任務。

## 3 實驗

同樣的 507 題,每個模型各跑 20 次,比較「單次成功」「至少成功一次」「次次成功」三者差多少。

### 3.1 排行榜與領域差異

各模型每次嘗試的成功率差很大,而且沒有哪個模型在每個領域都最強。

pass@1 的分母:每個模型跑 507 題 × 20 次,共 10,140 次嘗試,pass@1 是其中成功的比例。領域欄的分母是該領域題數 × 20。

論文 Table 4:*THINKINGBOX-BENCH pass@1 (%) by domain, micro-averaged over repeated N = 20 trials per task.*(節錄,單位 %)

| 模型 | Retail | Auto | Booking | Bank | Consulting | 平均 |
| --- | --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 80.71 | 65.80 | 49.95 | 70.62 | 66.19 | 66.50 |
| GPT-5.4 | 76.33 | 62.65 | 68.12 | 65.34 | 54.60 | 65.36 |
| Kimi-K3 | 82.24 | 50.80 | 61.83 | 41.35 | 51.63 | 57.37 |
| Claude Opus 4.6 | 68.62 | 8.30 | 21.11 | 35.67 | 27.82 | 32.09 |

- 總分第一、二名(Opus 5 的 66.50 對 GPT-5.4 的 65.36)在誤差範圍內分不出高下。
- 各領域最高分不同:Retail 是 Kimi-K3,Booking 是 GPT-5.4,其餘三個是 Opus 5。
- 同一個模型在不同領域可以差很多:Opus 4.6 在 Retail 是 68.62,在 Auto 只有 8.30。
- 14 個非 RL 模型的領域平均,Retail 最高(58.81),Auto 最低(33.18)。論文推測 Retail 高是因為模型熟悉標準電商流程,論文未驗證。

**解讀限制:** 507 題中有 477 題只檢查後端終態,不看最終回覆;只有 30 題(Booking 與 Bank 各 15)另加回覆檢查。agent 狀態改對、卻對使用者講錯,仍算通過。這些分數量的是後端結果對不對,不是溝通品質。

### 3.2 發現 vs 可靠

同一題跑 20 次,「至少成功一次」和「次次都成功」差很多,後者才是能放心交給 agent 的程度。這對應 C4。

- **pass@k:** 跑 k 次,至少成功一次的機率。回答「有沒有能力做到」。
- **pass^k:** 跑 k 次,全部成功的機率。回答「能不能穩定做到」。

論文沿用 τ-bench 的可靠度評估做法(Yao et al., 2024)。

自編例子:一題跑 20 次,成功 14 次。pass@1 = 14/20 = 0.7;pass@20 = 1(至少成功過一次);pass^20 ≈ 0.7^20 ≈ 0.0008,連續 20 次全對幾乎不可能。

論文 Figure 1(B):*Across 507 tasks and 20 attempts per task, pass@20 is much higher than pass@1, while all-20 success is much lower.* 下表節錄自論文 Table 15(單位 %)。

| 模型 | pass@1 | pass@20 | pass^20 | 從沒成功的題數 | 20 次全成功的題數 |
| --- | --- | --- | --- | --- | --- |
| Claude Opus 5 | 66.50 | 79.09 | 47.53 | 106 | 241 |
| GPT-5.4 | 65.36 | 91.12 | 30.62 | 45 | 128 |
| GPT-6 Astra | 58.31 | 71.01 | 46.89 | 147 | 231 |
| Kimi-K3 | 57.37 | 93.89 | 17.60 | 31 | 68 |
| Qwen3.8-27B | 51.70 | 89.35 | 10.93 | 54 | 38 |

- Kimi-K3 的 pass@20 全場最高,pass^20 只有 17.60%。多試幾次幾乎每題都碰得到成功,但很少穩定。論文把這個落差稱為 discovery–reliability gap。
- GPT-6 Astra 的 pass@1 排第五,pass^20 排第二。它成功的題目成功得很穩,但有 147 題從沒成功。
- Opus 5 的 pass^20 最高,pass@20 只有 79.09%:穩,但碰得到的題目範圍較窄。
- 結論:只看 pass@1,看不出「穩」與「碰運氣」的差別。

## 4 值得帶走

兩個脫離這篇論文也成立的判斷。

### 4.1 比對終態,不比對過程

評估 agent 要看「世界最後變成什麼」,不是看它說了什麼、呼叫了什麼。

為什麼成立:回覆和 tool call 只是「agent 宣稱做了什麼」,資料庫才是「實際發生了什麼」,兩者可以脫鉤。第 1 章的保單延期就是例子:正常結束、有寫入、沒報錯,資料庫卻違反了上限。

怎麼用:設計自己的 agent 評測時,先定義「正確的終態」(該有哪些紀錄、哪些不能動),再用它判定,不要要求 agent 照一條固定步驟走。

### 4.2 pass@k 與 pass^k 要分開量

「有沒有能力做到」和「能不能穩定做到」是兩個問題,pass@1 看不出差別。

| 指標 | 回答的問題 | 定義 |
| --- | --- | --- |
| pass@k | 有沒有能力 | 跑 k 次,至少成功一次 |
| pass^k | 穩不穩 | 跑 k 次,全部成功 |

為什麼成立:3.2 的表中,Kimi-K3 多試幾次幾乎每題都碰得到成功,但很少穩定;GPT-6 Astra 的 pass@1 排第五,pass^20 卻排第二。只看 pass@1,這兩種差別都看不出來。

怎麼用:要把 agent 放進有後果的流程(改資料、退款)時,看 pass^k;只想知道能力上限、或搭配重試機制時,看 pass@k。
