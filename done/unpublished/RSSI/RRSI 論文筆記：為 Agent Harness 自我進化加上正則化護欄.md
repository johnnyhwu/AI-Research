# RRSI 論文筆記：為 Agent Harness 自我進化加上正則化護欄

Sep 30, 2026 · @YHHW

## 三十秒版本

這篇論文的貢獻是一個好的問題定義，加上一組合理但沒有被拆開驗證的工程護欄：讓 LLM 自動改 agent 的 harness 很容易過擬合，RRSI 用一整包規則把這件事管住。

論文：*RRSI: Regularized Recursive Self-Improvement of Agent Harnesses*，Google Cloud AI Research，arXiv 2609.24972v2（2026 年 9 月）。

- 問題：agent 的能力很大程度取決於包在模型外面的 harness（提示詞、控制流程、工具介面、記憶、context 管理）。近期做法是讓另一個 LLM 自動修改 harness，用任務分數當回饋，反覆迭代。但每一輪都用同一批有限的題目評分，進化用的題目分數會一路上升，換到沒看過的 benchmark，進步卻縮水甚至消失。
- 方法（RRSI）：不限制 harness 能改什麼，改為管「怎麼提出修改」和「哪些修改可以被留下」。提案端有三個零件：A 每個候選最多綁幾個修改（逐輪遞減）、B 把每次修改的結果記成歷史交給 proposer、C 進度停滯時去試沒碰過的元件類別。篩選端有：D 評分前先審查有沒有寫死題目資訊、E 分數不能低於歷史最高分減去雜訊帶、F 多花的 token 要用分數進步來換、G 沒有貢獻的元件列為刪除目標，另外 engineering 領域有一道額外的 guard，最後在倖存的候選裡挑分數最高的。
- 最乾淨的證據：agentic 任務的 Table 2。沒有任何正則化的進化，進化用題目 92.8 分、沒看過的三個 benchmark 平均 40.3、每次試驗 3.80M tokens；RRSI 是 90.5、43.6、2.42M。進化用題目少拿 2.3 分，沒看過的題目多拿 3.3 分，token 省 36%。
- 判斷：研究價值偏低，工程參考價值中等偏上。護欄的設計原則（進化與驗證分開、先量評分雜訊、成本用分數換、每個修改留紀錄）脫離這篇論文也成立，值得直接借用。
- 最大的三個保留：所有數字都沒有變異數；「泛化」只是同一類任務之間換題，沒有測跨領域；沒有任何單一零件的 ablation，只有「整組拿掉」。

## 一、論文想解決的問題

讓 LLM 自動改進 agent 的 harness，看起來是一個穩定進步的迴圈，但它有一個結構性的缺陷：每一輪的決策都在重複使用同一批有限的題目，所以進步可能只是在背這批題目。

### 1.1 背景：agent、harness 與「進化」

**Agent** 在這篇論文裡被拆成兩塊：一個固定不動的 backbone 模型（權重完全不改），加上包在外面的 **harness**。Harness 指模型以外的所有東西：

- system prompt 與任務 prompt
- 控制流程：什麼時候該規劃、行動、反思或停止
- 工具介面與工具說明
- 記憶與 skill 檔案
- context management：每一步要讓模型看到什麼

同一個模型，harness 設計得好不好，決定它會不會先讀檔案再編輯、指令失敗後能不能復原、context 會不會塞爆、最後有沒有把結果寫進交付物。過去這些都靠工程師人工檢視失敗紀錄再手動調整，進度受限於工程師一天能讀多少紀錄。

**Harness evolution（harness 進化）** 是把這個人工迴圈自動化：讓另一個 LLM（稱為 proposer）讀失敗紀錄、提出修改，再用任務分數挑選。因為每一輪都是用「目前的系統」產生的回饋去改善「下一版系統」，論文把它稱為 agent 系統層級的 **RSI（recursive self-improvement，遞迴式自我改善）**，只是改的是 harness，不是模型權重。

一輪進化的流程如下（論文 Section 2）：

1. 目前的 harness H\_t 在 **evolve set**（進化用題目集）上執行。
2. 產生 trajectories（每題一次完整的執行紀錄），整理成 feedback F\_t。
3. proposer LLM 根據 F\_t 產生幾個候選 harness。
4. 候選們在同一個 evolve set 上重新評分。
5. 在「候選加上原本的 H\_t」裡挑分數最高的，成為下一輪的 H\_{t+1}，回到第 1 步。

&#91;embedded content: harness 進化迴圈 · 5 個步驟\]

圖中有顏色的步驟 1 與 4 都在同一批 evolve set 上評分，而第 3 步提案又依據第 1 步的結果，所以每一輪都在「看過」這批題目；右側箭頭表示第 5 步選出的 H\_(t+1) 成為下一輪的起點。

用式子寫（論文 Eq. 2）：

```latex
\mathcal{H}_t \sim P_0(\cdot \mid H_t, \mathcal{F}_t), \qquad H_{t+1} = \arg\max_{H' \in \mathcal{H}_t \cup \{H_t\}} \hat{S}(H';\, \mathcal{D}_{\text{evolve}})
```

- H\_t：第 t 輪在位的 harness。
- 𝓗\_t（式中的花體 H）：這一輪 proposer 產生的候選集合。
- P\_0：沒有任何限制的提案分布，也就是 proposer LLM 想怎麼改就怎麼改。
- F\_t：這一輪的失敗回饋（概念五詳細講它是什麼）。
- Ŝ：實測的分數。帽子表示只跑了有限次，有隨機雜訊。
- argmax：找出讓後面的值最大的那個候選，回傳的是候選本身，不是分數。

注意 argmax 的範圍包含 H\_t 自己：如果沒有任何候選比現在的好，H\_t 留任，這一輪什麼都不改。

### 1.2 核心問題：適應性過擬合

上面第 1 到 4 步一直重複使用同一個 evolve set，而且下一輪要改什麼，取決於前幾輪在同一批題目上量到的結果。這在統計上叫 adaptive data reuse（適應性資料重用）：這批題目不再是獨立的檢驗資料，而是被搜尋過程一步步「看過」的資料。結果是 evolve set 的分數一直漲，換到沒看過的任務，進步大幅縮水，甚至比什麼都沒改的原始 harness（論文記作 H\_0）還差。原理見〈概念一〉。

請直接翻到 **Figure 1**（a），caption 開頭是：*"Evolution overfits on the split it is scored on whereas RRSI generalizes the improvements. (a) Gains on the evolve split against gains out of distribution for the agentic workspace benchmark."* 橫軸是在 evolve 題目上的相對進步，縱軸是在沒看過的 benchmark（OOD）上的相對進步。圖上標了一條「1:1 transfer」的對角線，代表進步能完整搬過去；四個既有方法（Meta-Harness、AHE、TTHE、HarnessX）都落在線的下方，有的縱軸是負的（標示 "gain does not transfer"），只有 RRSI 落在上方。

### 1.3 三個造成過擬合的行為

論文歸納出三個互相耦合的行為，合起來把「evolve 分數」和「換題目後的分數」之間的差距越拉越大。這三個行為正好對應後面的護欄：

| 行為 | 白話 | 自編例子 | 對應的護欄 |
| --- | --- | --- | --- |
| benchmark-specific fitting（針對特定 benchmark 的擬合） | 修改內容直接記住了這批題目的特徵 | 某題失敗是因為公司名稱格式不對，proposer 就在 prompt 裡加一句「遇到 Acme 公司的報表要用 YY 格式」。evolve 分數上升，換一批題目完全派不上用場 | D（leakage screening） |
| noise chasing（追逐雜訊） | 選中的候選只是這次評分運氣好 | 4 個候選真實實力都是 90.0，各自量到 89.7、90.4、89.9、90.1，挑最高的 90.4，看起來進步 0.4，其實一分都沒進步 | E（分數底線）、雜訊帶 δ |
| complexity accumulation（複雜度累積） | 越改越肥，分數靠多花運算換來，不是靠更好的機制 | Table 2 裡沒有任何正則化的進化：evolve 分數最高，token 卻是原始 harness 的 2.4 倍 | F（成本規則）、G（結構剪枝） |

兩個提醒。第一，這三個行為在概念上分得很清楚，實務上很可能同時發生在同一個修改上（推論：例如一個寫死題目特徵的修改，同時也讓 prompt 變長）。第二，論文只用一小段文字介紹這三個行為，沒有各自做實驗量出它們各佔多少，Table 2 的 ablation 是把整組正則化一起拿掉。

### 1.4 後面會用到的名詞

- **evolve set**：進化過程中被反覆用來評分的題目集。
- **ID held-out（in-distribution held-out）**：同一個 benchmark 裡，進化時沒用到的題目。
- **OOD（out-of-distribution）**：進化時完全沒看過的 benchmark。
- **policy**：實際執行任務的那個模型。論文主實驗的 policy 固定為 Claude Opus 4.8。
- **trajectory**：agent 執行一題任務的完整紀錄，包含每一步的推理、工具呼叫與結果。

## 二、方法總覽

RRSI 完全不縮小 harness 能改的範圍，它只管兩件事：proposer 怎麼提出修改（提案端），以及哪些量到的進步可以變成永久狀態（篩選端）。

### 2.1 用 code review 的流程來理解

把 harness 想成一個 repo，把每一輪進化想成一次 PR 流程：

- 「不限制可修改範圍」：repo 裡任何檔案都可以動，prompt、工具、記憶、控制流程、subagent 都允許改。論文用 Ω(H) 代表「從 H 出發，改任意原始碼所能到達的所有 harness」，並刻意讓它保持開放。
- 提案端是對「怎麼提 PR」的規範：一個 PR 最多改幾件事（A）、提之前要看過去被退回的紀錄（B）、很久沒進展時要去動沒碰過的模組（C）。
- 篩選端是 merge 的關卡：CI 分數變高還不夠，還要沒有寫死測試答案（D）、不是 flaky test 運氣好（E）、沒有讓 build 時間暴增卻沒換到對等效益（F）。
- 「永久狀態」就是 merge 進 main：被選中的 H\_{t+1} 會成為下一輪所有提案的起點，選錯一次，錯誤會疊在後面每一輪。

這個比喻有一個不成立的地方：真實的 code review 有獨立的人和獨立的測試，而 RRSI 的「CI」就是同一批 evolve set 的評分，這批評分本身有雜訊，還會被反覆使用。所以 D、E、F 只是補洞，不能取代獨立的驗證（推論）。

RRSI regularizes the search trajectory, not restricting the potential harness edit space: proposal-side constraints control how search capacity is used, while selection-side constraints control which measured improvements are allowed to become a permanent state."* 圖分三塊：左邊是提案端 A、B、C，右邊是篩選端 D、E、F、G，中間是把兩邊串起來的轉移規則。

兩側的分法只是概念分類，不是程式分工：Algorithm 1（提案端）裡就已經包含了 D 的評分前篩檢，以及 G 的剪枝目標計算。

### 2.3 轉移規則：和舊規則相比只改了兩處

舊規則（Eq. 2，見第一節）的選擇範圍是「所有候選加上 H\_t」。RRSI 的版本（論文 Eq. 8）：

```latex
\mathcal{H}_t \sim P_{\text{reg}}(\cdot \mid H_t, \mathcal{F}_t, \mathcal{L}_t, b_t, \mathcal{E}_t, \mathcal{B}_t), \qquad H_{t+1} = \arg\max_{H' \in \mathcal{H}_t \cap \mathcal{A}_t} \hat{S}(H')
```

若沒有任何候選通過（交集是空集合），則 H\_{t+1} = H\_t。

- P\_reg：受限的提案分布。它其實就是 proposer LLM，只是輸入多了下面幾項。
- F\_t：這一輪的失敗回饋（概念五）。
- 𝓛\_t：過去所有修改的歷史紀錄（零件 B）。
- b\_t：這一輪每個候選最多綁幾個修改（零件 A）。
- 𝓔\_t：探索指令，停滯時要去試沒試過的元件（零件 C）。
- 𝓑\_t：結構剪枝的刪除目標（零件 G）。
- 𝓐\_t：admissible set（可接受集合），也就是通過所有關卡的候選，由 D、E、F 與領域 guard 決定誰進來。
- ∩：交集。只有「候選」與「可接受」同時成立的才能參賽。

所以只改了兩處：提案分布從無限制的 P\_0 換成受限的 P\_reg；挑最高分的範圍從全部候選縮成通過關卡的候選，全滅就維持原樣。

自編例子：H\_t 的分數是 90.0，本輪有三個候選。X 是 91.0，被 D 擋下（寫死題目資訊）；Y 是 90.8，被 F 擋下（成本漲太多）；Z 是 90.5，全部通過。舊規則會選 X，RRSI 選 Z。如果 Z 也沒通過，H\_{t+1} = H\_t，這一輪什麼都不改。

### 2.4 為什麼叫「正則化」，以及為什麼不是傳統的正則化

傳統正則化在最佳化的目標函數裡加一項懲罰，限制模型「能長成什麼樣子」。RRSI 沒辦法這樣做：harness 的候選空間是異質的，一個候選改 prompt，另一個新增 subagent，第三個改控制流程，這些東西放不進同一個參數向量，也就無法定義「參數有多大」。論文在 Appendix C 也直說，它沒有在最佳化任何範數懲罰的目標函數。所以 RRSI 改成限制搜尋「怎麼一步步走」：不動假設空間，只管提案規則和接受規則。

論文把 A 稱為 L0 風格、G 稱為 L1 風格、F 稱為 L2 風格。這只是比喻，名詞不會帶來稀疏或收縮的性質，詳見〈概念三〉。

## 三、提案端：A、B、C

提案端的三個零件都是交給 proposer 的輸入，只有 A 有明確的數字，B 和 C 是餵給 LLM 的資訊；論文沒有描述怎麼確保 proposer 照做。

### 3.1 A：退火式編輯預算

**問題**：proposer 可以把很多不相關的修改綁在一個候選裡。綁越多，越容易擬合眼前這批 feedback 的特例（容量高），而且分數變了也不知道是哪個修改造成的（難歸因）。

**做法**：每一輪規定一個候選最多能綁 b\_t 個「獨立可歸因的修改」，而且 b\_t 隨輪數遞減。早期允許綁多個修改去探索新機制，後期逐步收緊。這就是一個 learning rate scheduler 式的排程，只是被排程的對象是「一次能改幾件事」。論文 Eq. 4：

```latex
b_t = \left\lceil\, b_{\min} + (b_{\max}-b_{\min})\cdot \tfrac{1}{2}\Big(1+\cos\big(\pi t/T\big)\Big) \right\rceil
```

- t：第幾輪（從 0 開始）；T：總輪數；b\_max：起始預算；b\_min：終點預算；⌈ ⌉：向上取整。
- 中間那個係數會從 1 平滑降到 0，所以 b\_t 從 b\_max 降到 b\_min（推導見〈概念六〉）。

用 Table 5 的 coding 設定（T = 20、b\_max = 4、b\_min = 1）把 20 輪全部算出來（這是用公式算的，論文沒有列）：

| 輪數 t | 預算 b\_t | 持續幾輪 |
| --- | --- | --- |
| 0 到 7 | 4 | 8 輪 |
| 8 到 12 | 3 | 5 輪 |
| 13 到 19 | 2 | 7 輪 |

論文的真實例子在 Table 6（Coding R0-A）：第 0 輪的候選同時加了「完成前的驗證檢查」和「長時間任務的非阻塞輪詢指引」，evolve set 進步 3.93 分，被接受。第 0 輪預算是 4，允許這樣綁。

**兩個發現**（都是用公式與論文超參數推出來的）：

- 預算永遠到不了 b\_min = 1。t < T 時係數一定大於 0，向上取整前的值一定大於 1，所以最小是 2。b\_t = 1 只會在 t = T 出現，但 Appendix C.1 說一次進化只跑 t = 0 到 T − 1。agentic 與 engineering 的最後一輪也都是 2。但 Table 5 把 b\_min 標成 "final-round edit budget"，值是 1。兩種讀法：照公式字面，最後幾輪仍可綁兩個修改，歸因沒有論文宣稱的那麼乾淨；或實作的取整方式或輪數編號不同，最後一輪真的是 1。論文文字無法判定。
- 餘弦形狀幾乎是包裝。取整之後整個排程只剩 4、3、2 三個台階，跟「前 8 輪 4 個、中間 5 輪 3 個、後 7 輪 2 個」的階梯函數沒有實質差別。餘弦只決定台階在哪一輪切換，換成直線遞減會得到幾乎一樣的結果（推論）。論文也沒有單獨對排程形狀或「退火」做 ablation。

### 3.2 B：證據感知的功勞分配（歷史紀錄）

**一句話**：替每個被評估過的候選寫一筆「實驗紀錄」，之後每一輪都讓 proposer 讀這份紀錄，避免重試已失敗的點子，也記得已成功的點子。

**紀錄格式**（論文 Eq. 10）：

```latex
\mathcal{L}_t = \big\{\,(t_i,\ \ell_i,\ h_i,\ d_i,\ \Delta S_i,\ \Delta C_i,\ a_i) \;:\; i \le n_t \,\big\}, \qquad a_i \in \{0,1\}
```

每筆紀錄是一個七元組：

- t\_i：這個修改是第幾輪提出的。
- ℓ\_i：修改的元件類別（component），例如 prompt、control\_flow、memory、subagent。
- h\_i：這個修改想驗證的假設（hypothesis）。
- d\_i：實際的程式碼差異（source diff）。
- ΔS\_i：分數變化，候選相對在位 harness 的分數增益。
- ΔC\_i：成本變化，token 成本增加的比例。
- a\_i：有沒有被採用。a\_i = 1 表示這個修改所屬的候選在該輪贏了；a\_i = 0 包含所有其他情況，包括被規則擋下的，也包括通過了規則但輸給另一個分數更高的候選（Appendix C.2 明講）。
- n\_t：第 t 輪之前累積的紀錄總數。

一個候選如果綁了多個修改，每個修改各寫一筆，但這些紀錄共用同一組 ΔS、ΔC 和結果。

請翻到 **Table 6**，caption 開頭是：*"Representative harness-evolution decisions from RRSI. The examples show that evolution is not driven by score alone…"* 下面是其中三筆改寫成紀錄的樣子：

| 案例 | 修改內容 | ΔS | ΔC | a\_i |
| --- | --- | --- | --- | --- |
| Coding R0-A | 完成前的驗證檢查 + 長任務的非阻塞輪詢指引 | +3.93 分 | 論文未列 | 1 |
| Coding R0-B | 類似的驗證提醒 + 長任務指引 | +1.69 分 | +26.1% | 0（被成本規則拒絕） |
| Engineering R2 | 針對「workdir must be an existing directory」錯誤的復原提示 | 122/244 到 128/244 passes | +1.6% | 1 |

**名詞來歷**：credit assignment（功勞分配）出自強化學習，問題是「一連串動作之後才拿到一個獎勵，該把功勞分給哪個動作」，常被追溯到 Minsky 1961（一般知識，不是論文內容）。這篇論文用得偏重：實際只是「保留一份實驗紀錄給 proposer 看」，並沒有計算每個修改各自的貢獻。

**要保留的地方**：

- 綁在一起的修改，功勞沒有被真正分開。R0-A 的兩個修改（把它讀成兩個修改是我的解讀）會各有一筆 +3.93 的紀錄，看起來像各自進步 3.93，實際只是合起來進步 3.93。這使 B 的品質綁在 A 上。
- a\_i = 0 混了兩種意思：「規則擋下」與「輸給更好的同輪候選」。後者不代表點子失敗。R0-B 就是例子：假設方向和 R0-A 相同，被拒絕是因為只進步 +1.69、又多花 26.1%，意思是「這個版本不划算」，不是「驗證提醒沒用」。論文沒說 proposer 怎麼區分。
- 論文沒說 proposer 怎麼「條件在這份歷史上」（整份放進 prompt？先摘要？），也沒說 ℓ\_i 與 h\_i 兩個標籤由誰標。
- 被 critic 在評分前擋掉的候選沒有量測值，可能不在紀錄裡（概念八）。
- 「把歷史給 proposer 看」不是新東西：Appendix B 描述的基線 Meta-Harness 與 AHE 已經在做類似的事，B 的差別只剩格式更結構化，論文沒有單獨量這個差別，Table 2 也沒有單獨拿掉 B。

### 3.3 C：結構化探索

**一句話**：一條防偏食規則，搜尋連續幾輪沒有進展時，把停滯訊號與「這次進化裡還沒碰過的元件類別」清單交給 proposer，並保留一個候選名額給探索。

**它要解決什麼**：論文舉的例子是 proposer 一直改寫 prompt，agent 的結構性機制（工具、記憶、subagent）都沒動過。B 讓 proposer 看到歷史，但歷史本身不保證它會去試新方向。

**機制**（論文 Eq. 13、Appendix C.2）：

```latex
\sigma_t = \mathbb{1}\big[\hat S_t - \hat S_{t-w} \le \delta\big], \qquad U_t = \mathcal{K} \setminus \mathcal{T}_t, \qquad \mathcal{E}_t = (\sigma_t,\ U_t,\ m_{\text{draft}})
```

- Ŝ\_t：第 t 輪在位 harness 的評分；w：停滯偵測的視窗大小，看最近 w 輪。
- δ：雜訊帶（概念四），進步不超過它，就當作跟雜訊分不開。
- 1\[ \]：括號裡成立就是 1，否則是 0。σ\_t = 1 表示「停滯中」。
- 𝓚：元件類別的全集，共 9 類：prompt、control\_flow、config、output\_plumbing、context\_mgmt、client\_tool、skill、memory、subagent。
- 𝓣\_t：到目前為止，至少有一筆被量測過的修改所屬的類別；U\_t 是 𝓚 減去 𝓣\_t，也就是還沒碰過的類別。
- m\_draft：停滯時保留給探索的候選名額數。

用 Table 5 的 coding 設定（w = 3、δ = 0.017、m\_draft = 1）走一次（分數是自編例子）：Ŝ\_5 = 0.780、Ŝ\_8 = 0.792，差 0.012 ≤ 0.017，所以 σ\_8 = 1，判定停滯；若 Ŝ\_8 = 0.805，差 0.025 > 0.017，σ\_8 = 0，不觸發。假設前 8 輪碰過 prompt、control\_flow、context\_mgmt 三類，則 U\_8 是其餘 6 類，proposer 會拿到這份清單並被要求留 1 個候選名額給它們。

**要保留的地方**：

- 論文沒有描述怎麼確保 proposer 照做，用詞只有 reserved、redirect，沒有任何強制機制（概念七）。
- 「沒碰過」的判定很粗：碰過 prompt 一次就算試過，不管改的是哪一段；被拒絕的修改也算數。
- 推論：𝓚 只有 9 類，每輪又有好幾個候選，U\_t 可能很快變空，論文沒說變空時怎麼處理。
- 元件標籤由誰標（proposer、程式或另一個分析 LLM），論文未說明，而 C 的判定完全依賴這些標籤。
- Table 2 沒有單獨拿掉 C，Table 6 的案例也沒有停滯觸發的例子，沒有證據顯示它有作用。

### 3.4 提案端的整體判斷

A、B、C 是三份給 LLM 的軟性指示，只有 b\_t 是明確的數字。方向都合理，工程上也容易實作，但論文沒有證明每一個各自有效。整個提案端唯一的證據是 Table 2 的一列 "w/o proposal regularizers"（見第五節）。推論：B 最可能有用，因為把過去的結果給 proposer 看，是所有基線都在做的事；A 和 C 的效果最不確定。

## 四、篩選端：D、E、F、G 與最終選擇

篩選端是一串各擋不同東西的關卡，候選必須依序全部通過，最後在倖存者裡挑分數最高的；每一關的設計都合理，但沒有任何一關有單獨的驗證。

### 4.1 D：leakage screening（洩漏篩檢）

**一句話**：在候選被拿去評分之前，先由一個 critic（一個專門負責審查的 LLM）讀它的程式碼差異（diff），把「寫死題目資訊」的修改擋在門外。

**論文明講的**（Section 3.3、4.1、Appendix C.3）：

- 擋的東西：明確寫進任務名稱、實體名稱、任務特定數值、答案，或其他只對 evolve benchmark 成立的邏輯；另外也擋 "inert machinery"（加了但沒有作用的程式）。
- 管的是內容，不是元件類別：通用的 prompt 或工具說明改進仍然可以通過。
- 時機在評分之前。理由是被擋的候選永遠拿不到那個會讓它顯得有吸引力的 evolve set 高分。
- 執行者是 Claude Opus 4.8，和 proposer、analyst 同一個模型。

**名詞來歷**：leakage 出自機器學習的 data leakage，指測試資料的資訊漏進訓練過程，讓評估失真。這裡用得貼切，不是包裝：如果候選把 evolve 題目的答案寫進 harness，就等於評分標準漏進了被評分的對象，evolve 分數會被灌水。

**例子**（自編）：候選 P 在 prompt 加一句「遇到 Acme 公司的併購合約，違約金條款固定寫 15%」，被擋（寫死實體名稱與數值）；候選 R 新增一個從沒被呼叫的輔助函式，被擋（inert machinery）。放行的真實例子是 Table 6 的 Engineering R2：針對「workdir must be an existing directory」這個反覆出現的工具錯誤，加一個有界的復原提示。它不含任何題目資訊，被接受了（122/244 到 128/244 passes，token 只多 1.6%），論文拿它當「task-agnostic 修正」的代表。

**要保留的地方**：critic 的判準與提示詞沒有公開，也沒有可調的門檻；「通用」與「針對這個 benchmark」的界線完全是 LLM 的判斷；只擋明確寫死的內容，沒有寫死名稱卻恰好貼合 evolve 題目分布的修改（例如假設每題都要附摘要表），critic 不太可能抓到（推論）；critic 與 proposer 是同一個模型，盲點可能高度重疊（推論）；Table 6 的案例裡沒有任何一個是被 critic 擋下的，也沒報告擋掉的比例。

### 4.2 E：雜訊帶 δ 與分數底線

**一句話**：進化開始前，先把沒改過的 H\_0 重複評分幾次，看分數自然會晃多大，這個幅度就是 δ；之後任何候選的分數，都不准比「歷史最高分減去 δ」還低。

**δ 怎麼來**：論文只給方法的一句話（進化前重複評估沒改過的 base harness，估出 empirical noise band），之後 δ 固定不變。論文給了三個領域的結果與對應的實際數量（Table 5、Appendix D.1），我驗算過：3/178 ≈ 0.0169、60/14,100 ≈ 0.0043、5/244 ≈ 0.0205，與表上一致。

| 領域 | δ | 對應的實際數量 |
| --- | --- | --- |
| coding | 0.017（1.7 分） | 3 個 pass，總共 89 題 x k = 2 = 178 次試驗 |
| agentic workspace | 0.004（0.4 分） | 60 個評分項目，總共約 14,100 個 |
| engineering design | 0.020（2.0 分） | 5 個 pass，總共 61 題 x k = 4 = 244 次試驗 |

論文沒說重複評估幾次、用什麼統計量當 δ（標準差、全距還是某個分位數）。

**分數底線**（論文 Eq. 5）：

```latex
\hat S(H') \;\ge\; S^{\star} - \delta
```

- Ŝ(H')：候選 H' 在 evolve set 上實測的分數。
- S\*：到目前為止，整個進化過程中觀察到的最高 evolve 分數。起點是 Ŝ(H\_0)，每輪更新成 max(S\*, Ŝ(H\_{t+1}))。
- δ：上面量出來的雜訊帶。

它是接受候選的必要條件，而且不能被其他項目抵銷（論文稱 non-compensatory）。Table 6 的 Coding R8-B 是唯一實例：把原始任務指令釘進完成關卡，分數 −2.81、成本 −13.6%，coding 的 δ 是 1.7 分，退步超過了，省成本也救不回來。

**底線為什麼綁在歷史最高分，而不是在位 harness**：為了防止搜尋「連續走下坡」，每一步的退步都小到可以當作雜訊，累積起來卻很多。數字例子見〈概念四〉。

**它防的其實不是「假進步」**：論文 Section 3.3 用 noise chasing 來描述 E，但 Eq. 5 只設了下限，擋的是連續小退步；一個靠運氣多量到 0.3 分的候選，不會被它擋住。若要真的擋掉運氣造成的假進步，統計上更合理的是要求 Ŝ(H') ≥ S\* + δ，代價是會誤殺運氣差的真進步。兩種做法的取捨在〈概念四〉。

**其他要保留的地方**：δ 只在 H\_0 上量過一次，之後套用到所有候選，論文沒驗證這個假設，而進化後的 harness 步驟更多（Figure 4(b)：21.2 步增加到 26.3 步），雜訊未必和 H\_0 一樣（推論）；S\* 記錄的是被選中候選的實測分數，而被選中的是最高的那個，所以可能被運氣墊高（贏家詛咒，概念二）；Algorithm 2 沒說在位 harness 的分數 Ŝ\_t 是沿用當初選中時的量測，還是每輪重量；Table 2 只有整組拿掉的一列，看不出 E 單獨的貢獻。

### 4.3 F：成本規則（進步超過 δ 的候選）

**一句話**：多花的 token 要用分數進步來換，進步越多，允許多花越多。

先定義兩個量（論文 Eq. 6），再看規則（Eq. 7）：

```latex
\Delta S = \hat S(H') - \hat S(H_t), \qquad \Delta C = \frac{\hat C(H') - \hat C(H_t)}{\hat C(H_t)}
```

```latex
\Delta C \le \beta_0 + \beta_1 \times \Delta S \qquad (\text{只在 } \Delta S > \delta \text{ 時使用})
```

- ΔS：候選比目前在位的 harness 多拿了幾分（用比例表示，多過 7 題 / 178 題 = 0.039）。注意是跟在位 harness 比，不是跟歷史最高分比。
- ΔC：每次試驗平均 policy tokens 的相對變化。1.0M 變 1.5M 就是 0.5，變省則是負數。
- β0：基本額度，不管進步多少都先給這麼多（coding 是 0.10，即 10%）。
- β1：換算率，每進步一單位，額外允許多少成本增加（coding 是 44.5）。

白話：允許增加的成本 = 基本額度 + 換算率 x 分數進步。實際增加的成本沒超過這個額度就通過，超過就拒絕。

自編例子，用 coding 的設定（β0 = 0.10、β1 = 44.5）：

|  | 候選 A | 候選 B |
| --- | --- | --- |
| 多過幾題 | 7 題 | 4 題 |
| ΔS | 7/178 = 0.039 | 4/178 = 0.022 |
| 允許增加的成本 | 0.10 + 44.5 x 0.039 = 1.85（185%） | 0.10 + 44.5 x 0.022 = 1.10（110%） |
| 實際增加的成本 | 50% | 150% |
| 結果 | 50% <= 185%，通過 | 150% > 110%，拒絕 |

進步 7 題，多花 50% 划得來；進步 4 題，多花 150% 就不划算。

β 的實際意思（Appendix D.1，我驗算過）：coding 的 β1 = 44.5 相當於每多過 1 題允許多 25% token；agentic 的 β1 = 35.4 是每多 100 個評分項目多 25%；engineering 的 β1 = 24.4 是每多過 1 題多 10%。β0 分別是 0.10、0.10、0.15。

**要保留的地方**：額度很寬，而且是相對在位版本算的，沒有對 H\_0 的絕對上限，連續接受三次各多 30% 的候選，累計是 1.3 的三次方，約 2.2 倍（算術）；β 的選法沒有敏感度分析；Table 2 沒有單獨拿掉 F。

### 4.4 進步落在雜訊帶內的候選（Eq. 17）

**一句話**：進步沒超過 δ 的候選（包含小幅退步），不看成本上限，改用一個加減分數的算式決定要不要收。

```latex
w_s\,\Delta S \;-\; w_c\,\Delta C \;+\; w_n\,\nu \;>\; 0
```

- ΔS、ΔC：同上。ΔS 進步為正；ΔC 變貴為正、變省為負。
- ν：這個候選碰到的結構性元件（client\_tool、skill、memory、subagent 四類）裡，有幾類從來沒出現在「被採用的修改」中。
- w\_s、w\_c、w\_n：三項各自的權重。

白話：進步加分、變貴扣分、試了沒人成功過的新結構加分，加總大於 0 就通過。coding 設 w\_s = 0，分數變化在這條規則裡完全不算分，算式只剩 −w\_c x ΔC + w\_n x ν > 0。

自編例子，三個 coding 候選，都在雜訊帶內、都通過分數底線：

|  | 分數 | 成本 | 碰新結構 | 算式 | 結果 |
| --- | --- | --- | --- | --- | --- |
| P | +1 題 | +26% | 沒有 | −w\_c x 0.26 | 拒絕，不管權重多少 |
| Q | 持平 | −10% | 沒有 | +w\_c x 0.10 | 通過（只要 w\_c > 0） |
| R | 持平 | +5% | 首次加 memory | −w\_c x 0.05 + w\_n | w\_n > 0.05 x w\_c 才通過 |

P 就是 Table 6 的 Coding R0-B（+1.69 分、+26.1% 成本，被拒絕）。R0-B 進步 3 題，coding 的 δ 約 3 題，不算「超過」，所以走的是這條規則，這是我用數字對出來的，論文沒有明寫。

**要保留的地方**：

- 論文說 w\_s、w\_c、w\_n 列在 Table 5，實際的 Table 5 沒有這三個，所以新奇加分到底多強無從得知。
- 分支邊界是一個懸崖：coding 裡多過 3 題、多花 26% 被拒；多過 4 題（ΔS 超過 δ，改走 Eq. 7）允許多花約 110%，多花 80% 也能過。3 題和 4 題只差 0.56 分，遠小於雜訊帶本身。
- 這條規則是論文裡比 C 更硬的探索推力，因為它直接改變誰能被收；但它只管雜訊帶內的候選，也只對四類結構性元件有效。
- 為什麼 coding 的 w\_s = 0，以及它是不是為了讓小進步過關，見〈概念九〉。

### 4.5 G：結構剪枝

**一句話**：如果某類元件最近幾輪的修改都沒有帶來進步，就把它列為刪除目標，交給 proposer，請它提出「把這類東西拿掉」的修改。

```latex
g_t(\ell) = \max\{\Delta S_i : \ell_i = \ell,\; t - t_i \le n_{\text{prune}}\}, \qquad \mathcal{B}_t = \{\ell \in \mathcal{T}_t : g_t(\ell) \le 0\}
```

- ℓ：元件類別，共 9 類；ΔS\_i：第 i 筆紀錄的分數變化（紀錄格式見 B）。
- t − t\_i <= n\_prune：只看最近 n\_prune 輪的紀錄（coding 是 4，engineering 是 5）。
- g\_t(ℓ)：這類元件最近幾輪裡，最好的一次分數變化。
- 𝓣\_t：到目前為止至少被修改過一次的類別；𝓑\_t 是 g\_t(ℓ) <= 0 的那些類別，即剪枝目標。

白話：最近 4 輪裡，這類元件最好的一次也沒有進步（小於等於 0），就列入刪除目標。

自編例子，第 8 輪、n\_prune = 4，只看第 4 輪以後的紀錄：

| 元件類別 | 紀錄（輪次：分數變化） | 窗口內最好的一次 | 結果 |
| --- | --- | --- | --- |
| memory | 第 3 輪 +0.02、第 5 輪 −0.01、第 6 輪 0.00 | 0.00（第 3 輪已超出窗口） | 列為刪除目標 |
| skill | 第 6 輪 +0.01 | +0.01 | 保留 |

**它只是建議，不是強制刪除**：每一輪開始時，程式用歷史紀錄算出 𝓑\_t 放進 proposer 的輸入，Appendix C.2 說 proposer 被指示要移除沒有產出的機制。程式不會直接刪任何東西，proposer 提出刪除的候選之後，還是要走完全部關卡。所以誤列的代價只是 proposer 白白花了一個提案名額：如果那個元件其實有用，刪掉後分數會掉，被 E 擋下；如果刪掉沒影響又省了成本，這個候選在成本規則裡反而加分。

**要保留的地方**：公式規定空集合的最大值是負無限大，所以「以前試過、但窗口內完全沒紀錄」的類別按字面也會被列入，而 Appendix C.2 的文字說的是「最近有被動過但沒進步」，論文未判定是哪一種；「元件」在這裡是 9 個大類別，論文沒說實際刪的是整類，還是類別底下的某一段；Table 2 沒有單獨拿掉 G。另外，G 在 Figure 2 與 Section 3.3 被放在篩選端，但 Algorithm 1 是在提案端算出剪枝目標，靠 proposer 執行。

### 4.6 領域專屬 guard 與最終選擇規則

**guard**（Appendix C.3）：coding 與 agentic 沒有 guard，這一關等於直接放行。engineering 的候選只要符合下面任一條就被拒絕，而且不能被分數抵銷：

- 有效輸出率（valid-output rate）比在位版本掉了超過 0.03。
- 沒有提交率（no-submission rate）比在位版本升了超過 0.02。

用意是避免「通過率上升，但基本執行有效性大幅變差」的候選被收進來。自編例子：在位版本有效輸出率 0.95，候選的通過率進步了，但有效輸出率掉到 0.90，掉了 0.05，超過 0.03，被拒絕。兩個門檻（0.03、0.02）不在 Table 5，論文沒說怎麼選，兩個比率也只有名稱，沒有定義。

**候選要被收，依序要過這幾關**（Algorithm 2）：

1. D：critic 檢查（評分之前）。
2. 在 evolve set 上評分，得到 ΔS、ΔC。
3. E：分數不能比歷史最高分低超過 δ。
4. ΔS > δ 走 F（Eq. 7），否則走雜訊帶內規則（Eq. 17）。
5. 領域 guard（只有 engineering）。
6. 全部通過的候選裡，挑分數最高的當 H\_{t+1}，並更新 S\*；沒有任何候選通過，H\_{t+1} = H\_t。

圖中右側是每一關擋下的東西；D 在評分之前，其餘都在評分之後，沒有任何候選通過時，這一輪什麼都不改。

最後一步仍然是「挑分數最高的」，所以贏家詛咒（概念二）並沒有被完全消除，只是前面的關卡先把明顯有問題的濾掉了。

## 五、實驗與結果

最扎實的證據是 agentic 領域的 Table 1 與 Table 2：RRSI 在進化用題目上進步最小，在沒看過的 benchmark 上進步最大，而且拿掉正則化後這個優勢就消失。其餘實驗都是補強，方向一致，但每個都只有一個數字、沒有變異數。

| --- | --- | --- | --- | --- |

這張表說三件事：在進化用的題目上，RRSI 進步最小（+1.1），Meta-Harness 最大（+3.6）；在同一個 benchmark 沒用過的題上，大家差不多，RRSI 與 Meta-Harness 並列最高（+2.3）；差距出現在完全沒看過的 benchmark，RRSI 平均進步 +3.9，比最強對手 Meta-Harness 高 3.0 分，另外兩個對手掉到 H\_0 以下。三個 benchmark 上 RRSI 都是第一，比各自最強的對手高 3.5（JobBench）、3.2（GDPval）、2.2（APEX-Agents）分。也就是說，進化時進步越多的方法，換題目後越不穩，RRSI 刻意用 evolve 分數換取轉移能力。

要保留的地方：

- 論文沒說每個方法重跑幾次進化，也沒有標準差。推論：三個 benchmark 全部第一，而且差距比對手彼此的差距（最好 40.6 對最差 38.0）還大，比較不像單純運氣，但這不是統計檢定。

## 六、整體評價

這篇的價值在於提醒「harness 自動進化很容易過擬合，要加護欄」，而不在於護欄本身有多新：研究價值偏低，工程參考價值中等偏上。

### 6.1 扣掉包裝後，它真正做到什麼

最乾淨的對照是「沒有任何正則化的進化」對「RRSI」，同樣的 agentic 設定（Table 2）：

|  | Evolve 分數 | OOD 平均 | Token 成本 |
| --- | --- | --- | --- |
| 沒有正則化 | 92.8 | 40.3 | 3.80M |
| RRSI | 90.5 | 43.6 | 2.42M |
| 差異 | −2.3 | +3.3 | −36% |

這是這篇最扎實的證據：加上護欄後，進化用的題目少拿 2.3 分，沒看過的題目多拿 3.3 分，還省了三分之一的成本。摘要裡其他數字都是挑最好看的那個（14.1 分是較弱模型在進化用題目上的進步，4.7 分是三個 OOD benchmark 裡最好的，22.9% 來自很小的基期）。真正穩的只有上面這張表，而且只在 agentic 一個領域。

### 6.2 研究價值與工程價值

研究價值偏低：研究貢獻接近「一個好的問題定義加上一組合理的工程規則」，沒有新的演算法或理論。論文也沒有推導任何泛化保證，「正則化搜尋軌跡」是設計上的框架加類比，效果靠實驗支持，不是靠理論。工程參考價值中等偏上：規則具體、可以照著實作，而且設計原則脫離這篇論文也成立。

| 面向 | 優點 | 缺點 |
| --- | --- | --- |
| 研究 | 把「harness 進化會過擬合」講清楚，並指出三個具體行為；反覆用同一批題目評分的風險本身是真實的問題 | 各個零件大多是常見做法的組合：評分前審查、雜訊底線、成本換分數、保留歷史紀錄（這是判斷）；L0、L1、L2 只是命名（概念三） |
| 研究 | 有整組 ablation，方向與論文的說法一致；有換 policy、換模型、換評分方式的補強實驗 | 沒有單一零件的 ablation，不知道哪個零件真的有用；所有比較都沒有標準差，跨方法比較只有一個領域 |
| 工程 | 規則都很具體，可以直接照著實作；程式碼與完整的逐輪紀錄有公開（Appendix E 說在專案網站，含 proposal、critic 決定、接受決定與完整 diff） | 關鍵超參數有的沒交代、有的沒列出（β 怎麼選、δ 怎麼量、guard 門檻、w 權重）；進化本身花多少錢沒報，只報了最後 harness 的成本 |
| 工程 | 每個護欄各自對應一個明確的失敗模式，出問題時比較好排查 | critic 與 proposer 是同一個 LLM，盲點可能重疊（推論） |

值得帶走的工程觀念：進化用的題目和驗證用的題目要分開、先量出評分自己會晃多少再決定什麼算進步、成本要用分數換、每個修改留紀錄。這幾條脫離這篇論文也成立（第七節）。

### 6.3 最大的三個保留

1. **沒有變異數。** 每個數字都是一次進化的結果，沒說重跑幾次。3.3 分的 OOD 差距有多穩，無法判斷。
2. **「泛化」只是同類任務之間換題。** 沒有測跨領域，例如用 coding 進化的 harness 去測 workspace 任務。
3. **每個零件都沒有單獨的證據。** 論文的核心賣點是「這一整包護欄有效」，不是「這個零件有效」。

### 7.1 第一類：這篇論文本身的貢獻

| 中 | 把「harness 自動進化會過擬合」講清楚，並歸納出三個行為：擬合特定 benchmark、追逐雜訊、複雜度累積 | 問題定義本身有價值，是這篇最實在的貢獻 |

### 7.2 第二類：脫離這篇論文也成立的東西

#### 一、反覆用同一批資料做決策，會製造假進步

這是最耐久的一條。任何「自動改進、自動評估」的系統（prompt 優化、skill 進化、agent 進化）都有這個結構：改一版、在題目上量分數、根據分數決定下一版怎麼改。問題出在第二步和第三步共用同一批題目：第 t 輪的決定依賴前幾輪在這批題目上的結果，這批題目就不再是「沒看過的」檢驗資料，而是被搜尋過程一步步看過的資料。再加上每一輪都是從一堆帶雜訊的分數裡挑最高的（見第二條），evolve 分數自然一路上升，但換到新題目就不一定成立。原理與數字見〈概念一〉。

實際做法只有一個：進化用的題目和最後檢驗用的題目要分開，而且檢驗用的題目不能參與任何決策，包括調超參數。這篇論文的超參數就只用 evolve 環境選定，沒有參考 held-out 或 OOD（Table 5 caption）。

```python
# 有問題的寫法：進化與檢驗用同一批題目
for t in range(T):
    candidates = propose(current, feedback(current, tasks))
    current = max(candidates + [current], key=lambda h: score(h, tasks))
final_score = score(current, tasks)   # 這個數字被搜尋過程「看過」，偏高

# 較好的寫法：檢驗題目不參與任何決策
evolve_tasks, holdout_tasks = split(tasks)
for t in range(T):
    candidates = propose(current, feedback(current, evolve_tasks))
    current = max(candidates + [current], key=lambda h: score(h, evolve_tasks))
final_score = score(current, holdout_tasks)   # 只在最後量一次
```

#### 二、贏家詛咒：從有雜訊的分數裡挑最高的，被挑中的幾乎一定被運氣墊高

只要流程裡有「一堆候選挑最高分」這一步，就要假設那個最高分偏高，不要當成真實水準。候選越多，被墊高的幅度越大。這個詞最早來自拍賣：得標者往往是對物品估價最樂觀的人，付的價錢通常高過物品的真實價值。RRSI 的護欄只是減輕這個問題，沒有消除，因為最後一步仍然是在倖存者裡挑最高分。詳見〈概念二〉。

#### 三、先量出評分自己會晃多少，再決定什麼算進步

評分有雜訊時，「這個候選比現在的好 0.4 分」本身沒有意義，除非你知道同一個版本重複評分會自然晃多少。做法是進化前把沒改過的版本重複評分幾次，量出波動幅度 δ。

接受規則有兩種取捨，選哪個要看你更怕哪種錯：

```python
# 進化前：量雜訊
scores = [evaluate(H0, tasks) for _ in range(R)]   # 重複評估沒改過的版本
delta = spread(scores)                             # 自然波動幅度，統計量要自己選

# 接受規則
lenient = score >= best_so_far - delta   # 只擋連續小退步；放行運氣好的假進步（論文的做法）
strict  = score >= best_so_far + delta   # 擋假進步；但會誤殺運氣差的真進步
```

lenient 的代價是 false positive（把假進步當成真進步），strict 的代價是 false negative（把真進步擋掉）。嚴格版不是論文的做法，見〈概念四〉。另外要注意，δ 是在原始版本上量的，進化後的版本雜訊未必一樣。

#### 四、三種傳統正則化各自在做什麼

正則化是在最佳化的目標裡加一項複雜度懲罰，讓模型別為了擬合有限資料而變得太複雜。L0 直接數非零參數的個數，L1 加總參數的絕對值，L2 加總參數的平方。Lasso（L1）會把不重要的參數壓到剛好 0，Ridge（L2）只會讓所有參數一起縮小，原因是絕對值的斜率永遠是 1，一路推到 0，而平方越靠近 0 推力越小，到不了 0。這是通用的機器學習基礎，與這篇論文的類比無關，完整推導見〈概念三〉。

#### 五、成本要用分數換，而且換算率要設計成一條線

做法：允許增加的成本 = 基本額度 + 換算率 x 分數進步。

```python
allowed_extra_cost = beta0 + beta1 * delta_score
accept = extra_cost <= allowed_extra_cost
```

設計教訓在邊界：這篇論文的規則有兩個分支（進步超過雜訊帶走一條、沒超過走另一條），兩條規則在邊界兩側寬鬆度差很多，造成一個懸崖：coding 裡多過 3 題、多花 26% 被拒，多過 4 題卻允許多花約 110%，兩者只差 0.56 分，遠小於雜訊帶本身。設計門檻規則時，要檢查邊界兩側是不是差太多。

#### 六、一次改太多，就分不清是誰造成的

把多個修改綁在同一個候選裡，它們共用同一組量測結果，紀錄看起來像各自貢獻，其實只是合起來的貢獻。所以每次變更盡量單一、可歸因；不得不綁時，別把共用的分數當成各自的分數。這也是 RRSI 把「一次最多綁幾個修改」做成預算並逐輪遞減的原因。如何在不得不綁定時把功勞分給各個修改，是另一個獨立的主題，這裡沒有展開。

#### 七、在評分之前先審查，而不是評分之後

能在拿到誘因之前擋掉的東西，不要等拿到之後再處理。RRSI 讓 critic 先讀修改內容、擋掉寫死題目資訊的候選，被擋的候選就永遠拿不到那個會讓它顯得有吸引力的高分，後續輪次也不會被它的高分誤導。

```python
if critic_flags(diff):
    reject(candidate)               # 先審查，沒有分數可以偏袒它
else:
    score = evaluate(candidate)     # 通過審查才拿去評分
```

這個順序本身是通則。代價是被擋的候選沒有量測值，所以不能寫進「每個修改附上分數」的歷史紀錄（概念八）。

#### 八、一個有價值的負面結果：進化分數很高，不代表有真進步

沒有任何正則化的進化，進化用題目的分數最高（92.8），沒看過的題目卻只進步 0.6（39.7 到 40.3），token 卻多了 144%（Table 2）。意思是進化分數很高不代表有真進步，而且可能只是多花運算換來的。這條可以拿來提醒自己：評估任何自動進化系統，不要只看它自己在進化用題目上的分數，要看沒參與決策的題目，也要看成本。

## 第二部分：概念詳解

以下九段是讀這篇論文時最容易卡住、也最容易忘記的觀念。每一段都標記為「概念」，脫離這篇論文也成立，可以單獨閱讀，不需要先讀第一部分。論文用到這些觀念的地方，只在段落末尾簡短交代。

### 【概念一】反覆用同一批資料做決策，為什麼會製造假進步

**先看一個最簡單的情境**：你有 100 題可以評估一個系統。如果你只評估一次，再用這個分數當成「這個系統的水準」，這是一個沒有偏差的估計，最多有隨機雜訊。問題出在你不只評估一次：你看了結果，根據結果改了系統，再用同一批題目評估，再改，如此反覆。

**為什麼這樣會出問題**：第二次修改的方向，是根據第一次在這批題目上的結果決定的。這代表修改內容已經帶著「這批題目的特徵」。等到第三次評估時，你量到的分數有一部分是「我針對這批題目調整過」的成果，不是真的變強。這批題目已經不再是獨立的檢驗資料，統計上叫 adaptive data reuse（適應性資料重用），相關的研究領域叫 adaptive data analysis（Dwork 等人 2015 年是代表性的一篇，這篇論文引用它來說明問題存在，沒有自己推導）。

**兩個放大器**（以下是統計的一般知識，不是論文內容）：

1. 每次評分帶隨機雜訊，而每一輪都是「從一堆候選挑最高分」。取最大值會系統性地挑出被雜訊墊高的那個（見〈概念二〉）。以每個候選的真實效果都是 0、雜訊標準差 σ 為例：4 個候選挑最好的，期望值約 +1.03σ；100 次評分挑最好的，期望值約 +2.51σ。什麼都沒改進，看起來也會進步，而且看的次數越多，假進步越大。
2. 空間越大、越靈活，越容易找到「恰好貼合這批題目」的修改。harness 進化的搜尋空間是「改任意原始碼」，屬於表達力異常大的空間，所以論文說它是 adaptive empirical optimization over an unusually expressive search space。

**怎麼避免**：進化用的資料與最後檢驗用的資料要分開，而且檢驗用的資料不參與任何決策。RRSI 沒有做到「進化中完全不重用同一批題目」（它做不到，evolve set 就是要被反覆評分的），而是用一組護欄降低重用造成的傷害（論文的 D、E、F 等）。

**論文的位置**：論文沒有推導任何泛化保證（generalization bound）。「正則化搜尋軌跡」是一個設計框架加類比，效果靠實驗支持。

### 【概念二】贏家詛咒（winner's curse）

**一句話**：從一堆帶有運氣成分的分數裡挑最高的，被挑中的那個，分數幾乎一定被運氣墊高了，所以它的真實水準比看到的分數低。

**用一個例子看**：4 個候選，真實實力完全一樣，都是 90.0 分。但每次評分都有隨機波動（LLM 每次跑結果不同，每題也只跑幾次），所以量到的分數會在 90.0 上下晃：

| 候選 | 真實實力 | 這次量到的分數 |
| --- | --- | --- |
| A | 90.0 | 89.7 |
| B | 90.0 | 90.4 |
| C | 90.0 | 89.9 |
| D | 90.0 | 90.1 |

挑最高分，選中 B（90.4）。看起來 B 進步了 0.4 分，但 B 其實跟其他人一樣是 90.0，多出來的 0.4 純粹是這次運氣好。這個 0.4 就是「詛咒」：你選中它，是因為它運氣好，但下一次重新評分時，運氣不會跟著它走，分數會掉回 90.0 附近。

```python
import random

def measure(true_score=90.0, noise=0.4):
    return random.gauss(true_score, noise)   # 每次評分帶隨機雜訊

scores = [measure() for _ in range(4)]       # 4 個真實實力相同的候選
best = max(scores)                           # 「贏家」
# best 平均比 90.0 高約 1.03 * noise，這個差距是運氣，不是實力
```

**為什麼叫詛咒**：「贏」的那個人，贏的原因有一部分是運氣，所以贏得的東西（那個高分）不能當真。這個詞最早來自拍賣：得標者往往是對物品估價最樂觀的人，付的價錢通常高過物品的真實價值。

**候選越多，幅度越大**：4 個候選挑最高，期望被墊高約 1.03 個雜訊標準差；100 個約 2.51 個（統計的一般知識）。

**跟這篇論文的關係**：

- 每一輪 RRSI 都是「一堆候選挑分數最高」，所以每一輪都有這個問題。
- 被選中候選的分數會被記成歷史最高分 S\*，這個被墊高的數字會影響之後的分數底線判斷（概念四）。
- RRSI 前面的關卡（critic、分數底線、成本規則）把明顯有問題的候選濾掉，但最後仍是在倖存者裡挑最高分，所以贏家詛咒沒有被消除，只是被減輕。

### 【概念三】正則化，以及 L0、L1、L2 各自在做什麼

**正則化解決什麼問題**：訓練資料只有有限的 n 筆，模型太靈活的話，會連資料裡的雜訊都背起來，訓練誤差很低，換一批資料就很差。正則化的做法是在最佳化目標裡多加一項複雜度懲罰：

```latex
\min_{\theta}\;\; \frac{1}{n}\sum_{i=1}^{n}\ell\big(f_\theta(x_i),\,y_i\big)\;+\;\lambda\,R(\theta)
```

- θ：模型的參數，可以想成一排旋鈕。
- f\_θ(x\_i)：模型對第 i 筆輸入 x\_i 的預測；y\_i：第 i 筆的正確答案。
- ℓ：單筆預測的誤差；1/n 乘上加總，就是對 n 筆誤差取平均，也就是訓練誤差。
- R(θ)：複雜度懲罰，例如「旋鈕總共轉多大」。
- λ（大於等於 0）：懲罰強度，越大越偏好簡單的模型。

自編數字例子：λ = 0.1。模型 A 的訓練誤差 0.0、複雜度 R = 10，總分 0.0 + 0.1 x 10 = 1.0；模型 B 的訓練誤差 0.5、複雜度 R = 3，總分 0.5 + 0.1 x 3 = 0.8。總分越低越好，所以選 B：A 雖然把訓練資料背得滿分，但太複雜，被懲罰扣掉了。

注意兩個關鍵：懲罰的對象是「模型本身的參數 θ」，作用的位置是「最佳化的目標函數」。這就是「限制假設空間」，假設空間（hypothesis space）指所有可能的模型的集合。

**三種範數**：範數（norm）是「量一個向量有多大」的方法。設 θ = (θ\_1, ..., θ\_d)：

```latex
\|\theta\|_0 = \#\{\, j : \theta_j \neq 0 \,\}, \qquad \|\theta\|_1 = \sum_{j=1}^{d} |\theta_j|, \qquad \|\theta\|_2^2 = \sum_{j=1}^{d} \theta_j^2
```

- 第一式：不等於零的參數有幾個。第二式：每個參數的絕對值加總。第三式：每個參數的平方加總。

自編例子：θ = (3, 0, −1, 0)。L0 = 2（兩個非零）；L1 = 3 + 0 + 1 + 0 = 4；L2 的平方 = 9 + 0 + 1 + 0 = 10。

把它們放進上面的懲罰項 λ R(θ)，就得到三種正則化：

| R 取什麼 | 名稱 | 效果 | 備註 |
| --- | --- | --- | --- |
| L0 範數 | L0 正則化 | 直接數「開了幾個旋鈕」，限制非零參數的個數 | 「數個數」沒辦法用梯度下降，最佳化困難，實務少見 |
| L1 範數 | Lasso（Least Absolute Shrinkage and Selection Operator，最小絕對值收縮與選擇算子） | 把不重要的參數壓到剛好 0，得到稀疏的模型 | 兼具選擇變數的效果 |
| L2 範數的平方 | Ridge（嶺迴歸） | 讓所有參數一起縮小，但很少變成剛好 0 | 在 ML 裡最常見，weight decay 本質上就是它 |

**為什麼 Lasso 會歸零，Ridge 不會**：看斜率。把一個參數從 0.1 降到 0，L1 的懲罰少掉 0.1，L2 的懲罰只少掉 0.1 的平方，也就是 0.01。|θ| 的斜率永遠是 1，所以一路把參數推到 0；θ 平方的斜率是 2θ，越靠近 0 推力越小，到不了 0。

**這篇論文怎麼借用這三個名字**（輕描淡寫，因為它只是比喻）：論文把零件 A 稱為 L0 風格、G 稱為 L1 風格、F 稱為 L2 風格。

| 論文的名稱 | RRSI 實際在做的事 | 對應程度 |
| --- | --- | --- |
| L0：退火式編輯預算（A） | 一個候選最多綁 b\_t 個修改，形式上是個數上限 | 形式對得上，但它是硬性上限不是懲罰項，把「L0」拿掉資訊沒有損失 |
| L1：結構剪枝（G） | 近期沒有正增益的元件，列為刪除目標 | 只有「稀疏化」的意圖相同，機制更接近神經網路壓縮裡的 pruning |
| L2：複雜度感知接受（F） | 多花的 token 要有分數增益來抵 | 是一個成本效益門檻，沒有平方、沒有收縮，對應最弱 |

論文在 Appendix C 也承認這是功能上的類比，不是最佳化任何範數懲罰的目標函數。所以這些名詞不會讓 RRSI 繼承 L1 的稀疏性或 L2 的收縮性，看到「L1 風格」時，只需要理解成「剪掉沒貢獻的東西」。另外，Figure 2 把 F 標成 L1、G 標成 L0，與正文（A 是 L0、G 是 L1、F 是 L2）不一致，我判斷是筆誤（推論，論文沒有明說）。

### 【概念四】雜訊帶 δ 與分數底線，以及一個更嚴格的版本

**雜訊帶是什麼**：一個系統重複評分，每次的分數都不會完全一樣（LLM 每次執行結果不同，每題只跑有限次）。把「完全沒改過的版本」重複評分幾次，分數自然晃動的幅度，就是雜訊帶 δ。分數的差距如果小於 δ，就分不清是真的差異還是雜訊。

**分數底線（論文 Eq. 5）**：

```latex
\hat S(H') \;\ge\; S^{\star} - \delta
```

- Ŝ(H')：候選在 evolve set 上實測的分數；S\*：整個進化過程中到目前為止的最高分；δ：雜訊帶。
- 白話：候選分數不能比歷史最高分低超過 δ。

**為什麼底線綁在歷史最高分，而不是在位版本**：防止搜尋「連續走下坡」，每一步的退步都小到可以當作雜訊，累積起來卻很多。自編例子，用 coding 的 H\_0 = 74.2、δ = 1.7 分：

| 輪次 | 底線綁在「在位版本」 | 底線綁在「歷史最高分」（Eq. 5） |
| --- | --- | --- |
| 起點 | 在位 74.2，底線 72.5 | S\* = 74.2，底線 72.5 |
| 第 1 輪，候選 72.6 | 通過。在位變成 72.6，底線降到 70.9 | 通過。底線仍是 72.5 |
| 第 2 輪，候選 71.0 | 通過。在位變成 71.0，底線降到 69.3 | 拒絕（71.0 < 72.5） |
| 第 3 輪，候選 69.4 | 通過。累計已退步 4.8 分 | 不會發生 |

每一步的退步（1.6、1.6、1.6）都在 δ 內，但累積起來很多。綁在歷史最高分，底線只會隨最高分上升，不會下降，所以整個進化過程最多比最高分低 δ。

**一個容易忽略的事實：Eq. 5 只設下限，不擋「運氣好的假進步」**。論文用 noise chasing（追逐雜訊）來描述這個零件，但一個真實水準沒變、只是這次評分多量到 0.3 分的候選，會輕鬆通過 Eq. 5。要擋掉這種假進步，統計上合理的做法是同時設上限：要求候選比歷史最高分高出至少 δ。

**兩種規則的取捨**（下面的數字是自編的）：設 S\* = 78.0、δ = 1.7。

| 情況 | 寬鬆版（論文，Ŝ >= S\* − δ = 76.3） | 嚴格版（Ŝ >= S\* + δ = 79.7） |
| --- | --- | --- |
| 真實水準與現在打平，但這次運氣好量到 79.5 | 通過。若這輪它最高就會被選中，成為假進步 | 不通過（79.5 < 79.7），假進步被擋下 |
| 真實水準高 1 分（真進步），但這次運氣差量到 77.5 | 通過，但低於 S\* 所以不會刷新 S\* | 不通過（77.5 < 79.7），真進步被誤殺 |

這就是取捨所在：寬鬆版的代價是 false positive（放行雜訊撐出來的假進步），嚴格版的代價是 false negative（擋掉運氣差的真進步）。兩者解決的是不同的問題：寬鬆版防連續小退步，嚴格版防假進步。論文只做了前者。推論：論文可能是怕門檻設太嚴，20 輪下來幾乎沒有候選能通過，搜尋會卡住，但這只是猜測，論文沒有為這個選擇辯護。選哪個，要看你更怕哪種錯：搜尋預算充裕、假進步代價高，就選嚴格；預算緊、怕搜尋停滯，就選寬鬆。

**另外兩個要記得的限制**：δ 是在原始版本上量的，進化後的版本雜訊未必一樣；而且 S\* 記錄的是被選中候選的實測分數，被選中的是最高的那個，所以 S\* 本身可能被運氣墊高（概念二），之後的底線也跟著偏高，實力相同的候選可能被誤擋。

### 【概念六】退火預算排程：公式怎麼算，名詞從哪來

**一句話**：一個「前期放寬、後期收緊」的數值排程，本質就是 learning rate scheduler，只是被排程的對象是「一個候選一次最多能綁幾個修改」。

**名詞來歷**（一般知識，不是論文內容）：

- 「退火」原本是冶金：金屬加熱後慢慢降溫，讓內部結構穩定。
- 進入最佳化領域：模擬退火（simulated annealing）用一個「溫度」隨時間下降的排程，前期允許大幅度亂走，後期只允許小幅度微調。
- 餘弦退火（cosine annealing）：2016 年 SGDR 論文把餘弦形狀用在深度學習的學習率排程，現在訓練 LLM 很常見。
- 這篇論文借的只有「前期放寬、後期收緊」的形狀，沒有用到溫度或機率式接受的機制。

**公式怎麼拆**（論文 Eq. 4，符號見第三節 A）：

1. π t / T 是一個角度，隨 t 從 0 走到 π，也就是從 0 度走到 180 度。
2. cos 隨之從 1 降到 −1。
3. (1 + cos) / 2 把它變成一個從 1 降到 0 的係數，形狀是起頭平、中段陡、尾巴又平的 S 形，不是一條直線。
4. b\_t = ⌈ b\_min + (b\_max − b\_min) x 係數 ⌉，也就是起點 b\_max 與終點 b\_min 之間依係數內插，最後向上取整成整數（因為是「幾個修改」）。

用 coding 的設定（T = 20、b\_max = 4、b\_min = 1）走三個點：

| t | 角度 | cos | 係數 | b\_t |
| --- | --- | --- | --- | --- |
| 0 | 0 度 | 1 | 1 | ⌈1 + 3 x 1⌉ = 4 |
| 8 | 72 度 | 約 0.309 | 約 0.6545 | ⌈1 + 3 x 0.6545⌉ = ⌈2.96⌉ = 3 |
| 19 | 171 度 | 約 −0.988 | 約 0.006 | ⌈1 + 3 x 0.006⌉ = ⌈1.018⌉ = 2 |

**取整帶來的兩個後果**（用公式推出來的，論文沒有討論）：

- 係數要到 t = T 才會是 0，但一次進化只跑 t = 0 到 T − 1，所以預算永遠到不了 b\_min，最小停在 2。
- 取整之後整個排程只剩 4、3、2 三個台階（完整的 20 輪表格在第三節 A）。餘弦形狀只決定台階在哪一輪切換，與學習率排程不同：學習率是連續值，形狀真的影響訓練；這裡是整數，餘弦與直線遞減會得到幾乎一樣的結果。

### 【概念八】被 critic 擋掉的候選去哪了

**一句話**：被 critic 在評分前擋掉的候選沒有分數，而歷史紀錄的每一筆都需要分數，所以它們大概不在歷史紀錄裡，proposer 也就看不到「哪些點子因為洩漏被擋」。

**一個候選經過的順序**（論文 Section 3.3 與 Appendix C.3 都寫 critic 在完整評估之前執行）：

1. proposer 提出候選。
2. critic 讀程式碼差異，判斷有沒有寫死題目資訊。被擋：到此為止，不會被拿去跑 evolve set。
3. 通過的候選在 evolve set 上完整評分，得到 ΔS、ΔC。
4. 寫進歷史紀錄 L\_t。

分數（ΔS、ΔC）是第 3 步跑完才會產生的。被擋的候選停在第 2 步，從來沒被執行過，所以沒有分數。歷史紀錄的每一筆是七元組，ΔS 與 ΔC 是必填欄位（見 3.2 節），沒有分數就填不完。論文 Appendix C.2 在寫出紀錄公式之前有半句 "Ignoring candidates that fail before a valid measurement is obtained"，意思是先不考慮那些還沒拿到有效量測就失敗的候選。

**後果**：proposer 是讀 L\_t 來調整提案的，被擋的候選不在裡面，它就不知道有哪些點子曾經被擋過。自編例子：某一輪候選 W 在 prompt 裡加了一句「遇到 Acme 公司的報表要用 YY 格式」，被 critic 擋掉；下一輪 proposer 讀 L\_t，完全沒有 W 的痕跡，可能再提出類似的東西，critic 又擋一次。代價是浪費一個提案名額加一次 critic 呼叫；推論：不會浪費 evolve set 的評分預算，因為被擋的候選不會被評分。

**這裡有個不確定**：上面那半句是寫公式時的記法，沒有明說「critic 擋掉的候選一定不進紀錄」。論文文字有兩種讀法：

|  | 讀法一 | 讀法二 |
| --- | --- | --- |
| "fail before a valid measurement" 指什麼 | 包含被 critic 擋掉的候選 | 只指執行失敗、環境壞掉這類，沒有包含被 critic 擋掉的 |
| 後果 | proposer 看不到洩漏被擋的紀錄，可能重複提出 | 被擋的紀錄可能透過別的管道（例如本輪的 F\_t）傳給 proposer |

論文文字無法判定。旁證：Appendix E 說專案網站公開完整的逐輪紀錄，包含 critic 的決定，所以 critic 的決定有被記錄下來，但記到哪裡、proposer 有沒有讀到，論文沒有寫。

### 【概念九】雜訊帶內規則的兩個疑問

這裡的規則指 Eq. 17（見 4.4 節）：候選進步沒超過雜訊帶 δ 時，用「w\_s x 進步 − w\_c x 成本 + w\_n x 新結構 > 0」決定要不要收。

**疑問一：coding 為什麼把 w\_s 設成 0？**

論文沒有說原因，只寫了結果：coding 的 w\_s = 0，所以雜訊帶內的分數進步不能單獨讓候選通過，要靠省成本或試新結構；agentic 與 engineering 用正的 w\_s，也沒解釋為什麼三個領域不一樣。

推論（論文沒這樣寫）：這條規則的目的是「不要把小幅的分數波動當成足夠的證據」（Appendix C.3），w\_s = 0 是把這個原則做到最徹底，雜訊帶內的分數變化完全不算數。但這個推論有個破洞：coding 的 δ 是 0.017，engineering 的 δ 是 0.020，比 coding 還大，engineering 卻用正的 w\_s。所以「δ 大，所以不信分數」不能解釋三個領域的差異，找不到一致的理由。

**疑問二：這條規則是為了讓小幅進步的修改也有機會被接受嗎？**

只對一半。

|  | 說法 | 判斷 |
| --- | --- | --- |
| 論文寫的目的 | 避免把小幅分數波動當成充分證據 | 目的偏向防守，不是幫小進步開門 |
| 這條規則的角色 | 雜訊帶內的候選不受 Eq. 7 的成本上限約束，需要另一套規則決定收不收 | 它處理的是「分不出是真進步還是雜訊」的灰色地帶 |
| 小進步能不能被收 | 可以，但走的路不是靠進步 | 對的部分 |

小進步的候選確實有機會被收，但在 coding 裡，被收的原因是「省成本」或「試了新結構」，分數進步本身不算分。用兩個自編候選看（coding，都在雜訊帶內）：

| 候選 | 分數 | 成本 | 結果 |
| --- | --- | --- | --- |
| S | 多 1 題 | 省 10% | 通過，因為省成本（只要 w\_c 大於 0） |
| T | 多 1 題 | 多 26% | 拒絕 |

兩個候選的分數進步一樣，結果不同，決定因素完全是成本。所以在 coding 裡，這條規則更像是「雜訊帶內的候選，只有更便宜或更新奇才留」。agentic 與 engineering 因為 w\_s 是正的，小進步才真的有加分。
