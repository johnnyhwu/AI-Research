# 答案對了，就代表 agent 真的會用技能嗎？讀 SkillCoach 的自我演化評分機制

## 前言

現在不少企業級的 agent 系統，會把內部的標準作業流程寫成一份份 `SKILL.md`，堆成一個技能庫讓 agent 自己去查、去用。庫小的時候沒什麼問題，庫一大就開始出事：該用的技能沒看到、選到長得很像但用不上的那一份、步驟跳著做、做完不檢查。麻煩的是，這些狀況發生的時候，**最後那個答案還是有可能是對的**。

SkillCoach（arXiv:2607.01874v1，京東與香港科大廣州）這篇論文處理的就是這件事。它的主張很直接：只看最終答案的對錯，你根本分不出 agent 是學會了照流程做事，還是純粹瞎猜蒙對。它的做法是把執行軌跡拆成四個可以分開打分的維度，再設計一套機制，讓這些評分規則能從真實跑出來的軌跡裡自己修正、自己變好。

這篇文章會走過它的問題設定、四個維度怎麼算分、評分規則（rubric）怎麼演化，以及最關鍵的那組實驗數據。文末也會誠實談這篇論文在整條研究線上的定位——有些結論其實不是它發明的。

## 一、為什麼「答案對」不等於「用對技能」

論文開頭用一個防洪任務的例子把問題講得很清楚。同一道題，兩條執行軌跡，最後都算出了正確的淹水天數：

| | Trajectory A | Trajectory B |
|---|---|---|
| 有沒有讀技能文件 | 有 | 完全沒讀 |
| 執行方式 | 照文件步驟做：下載官方閾值資料 → 計算門檻表 → 檢查結果 | 自己猜資料來源，反覆試錯 |
| 最終答案 | 正確 | 正確 |
| verifier 給的分數 | 通過 | 通過 |

用外部 verifier 去看，這兩條軌跡的分數一模一樣。但只有 A 展現出可重複、可信賴的行為；B 是撞對的，換一道題八成就翻車。

這個落差會在兩個地方咬人。評估的時候，pass/fail 這個訊號太粗，你看不出 agent 到底學會了什麼、哪一環最弱。訓練的時候更糟：如果你把所有「verifier 通過」的軌跡都當成好示範餵去做監督式微調（SFT），B 那種繞過流程、亂試一通的行為也會一起被學進去。這個擔憂不是空談，論文後面的實驗直接把它打出來了。

## 二、把過程拆成四個可打分的維度

SkillCoach 把 agentic skill-use 當成一種軌跡層級的能力，拆成四個維度分開評分：

| 維度 | 在測什麼 | 預設權重 |
|---|---|---|
| `skill_selection`（技能選擇） | 有沒有選到該用的 gold skill（這題的標準答案技能）、有沒有誤用干擾技能 | 0.40 |
| `skill_following`（步驟遵循） | 有沒有真的照技能文件的關鍵步驟做，而不是只提到技能名稱 | 0.30 |
| `skill_composition`（組合順序） | 多個技能之間的先後順序、中間產物有沒有正確傳遞（單一技能任務不適用） | 0.20 |
| `skill_reflection`（結果反思） | 交答案前有沒有明確的自我檢查行為 | 0.10 |

四項加權後得到總分 `Smeta`。外部 verifier 則是完全獨立的第五個訊號，不併進這個加權分數裡。

`skill_selection` 拿到最高的 0.40，而且扮演閘門的角色：選錯技能，下游三個維度的分數會被打折。邏輯很好懂，技能都挑錯了，後面步驟做得再漂亮也是在做錯的事。

### 公式其實沒那麼難

四條公式本質上都是加權平均的變形，只有 selection 那條稍微特別。

**技能選擇**用的是 F1 score。`Sb` 是 agent 實際用到的技能集合，`Gt` 是這題真正需要的 gold skill 集合：

```
ssel = 2 * |Sb ∩ Gt| / (|Sb| + |Gt| + ε)
```

用 F1 而不是單純的命中率，是為了同時罰「漏選」跟「濫選」——把整個技能庫全部塞進來當然一定包含正確答案，但那不叫選對。另外有一種特殊情況：如果這題本來就不需要任何技能，那評分就變成 `ssel = I[Sb = ∅]`，看 agent 有沒有正確地「什麼都不選」。

**步驟遵循**這條藏著全篇最值得抄走的設計。`wk` 是步驟權重，`ck ∈ {0, 0.5, 1}` 是完成程度，`mk ∈ {0, 1}` 是軌跡裡有沒有可見證據：

```
sfol = Σ_k [ wk * ck * mk ] / Σ_k wk
```

眉角在 `mk` 是**乘法項**而不是加法項。agent 就算在輸出裡白紙黑字寫「我已經完成了資料驗證」（`ck = 1`），只要軌跡裡找不到對應的事件證據（`mk = 0`），這一步直接歸零。這條就是專門用來擋「靠嘴巴宣稱來拿分」的。

**組合順序**和**結果反思**的形式類似，前者看每一組先後依賴 `(u,v)` 有沒有真的先做 u 再做 v、中間產物有沒有正確傳遞；後者看每一項預期檢查 `c` 的執行品質 `rc ∈ {0, 0.5, 1}`。都是「規定好的事有沒有做到」的加權平均。

## 三、誰在打分？規則、LLM judge 與外部 verifier 的分工

這裡有個很容易誤會的點：**不是四個維度全都丟給 LLM 打分**。

| 維度 | 誰來判 | 為什麼這樣設計 |
|---|---|---|
| `skill_selection` | 規則為主，機械式偵測 | 論文明講目前的實作是 rule-dominant：直接看軌跡裡有沒有出現「讀取 SKILL.md」這類事件，避免 LLM 幻覺出「它選對了」的假證據 |
| `skill_following` | LLM judge，但強制引用具體證據（`event_index`） | 判斷步驟有沒有真的做需要理解語意，逃不掉 LLM；但要求指出證據在軌跡的第幾個事件，防止空口判斷 |
| `skill_composition` | 同上 | 同上 |
| `skill_reflection` | 同上 | 同上 |
| verifier（外部結果） | 完全不是 LLM，是 code-level 的硬性檢查器 | 直接讀 benchmark 產出的結果檔案，與 LLM 判斷完全獨立 |

這個分工的意義在於，最重的那個維度反而最不依賴 LLM 的主觀判斷，而最依賴 LLM 的三項都被「必須指出證據位置」綁住。

至於訓練資料怎麼挑，規則是兩個條件同時成立：`Smeta ≥ 0.95` **而且** verifier 通過。缺一不可，過程分數不會蓋掉結果訊號，結果訊號也不能單獨放行。

## 四、Rubric 自我演化：讓評分規則自己變好

寫 rubric 本身是件很花人力的事，尤其每個任務的關鍵步驟都不一樣。SkillCoach 的另一半貢獻，就是讓每個任務專屬的 rubric 能自己迭代。

整個迴圈長這樣：

1. 從 `SKILL.md`、任務指令、oracle 解法、verifier 資訊建構出初版 rubric `R⁰`。
2. **Rollout**：讓 agent 在真實環境跑出一批軌跡。
3. **Judge**：用目前版本的 rubric 對每條軌跡打四個維度的分數。
4. **Arbitration**：另一個 LLM 看過打分結果，提出一個局部修改建議（patch）。
5. **Validation Gate**：用保留的軌跡驗證這個 patch 到底有沒有變好。接受就升版本繼續跑，拒絕就留著舊版換下一輪。

迴圈最多跑 6 輪，連續被拒 3 次就提早收工。收工之後不是直接拿最後一輪的版本，而是從**所有曾被接受過的版本**裡挑驗證分數最高的那個當 `R^best`。

每一輪的軌跡會切成兩份：10 條校準集給 arbitration model 看去提案，5 條驗證集**對 arbitration model 隱藏**，只用來檢驗 patch。概念上就是 train/validation split，防止 rubric 對那少數幾條校準軌跡過度擬合。

patch 也不是想改什麼就改什麼。硬性限制包括：不能動 `key_steps` 的定義、不能改 `score_weights`、不能繞過 verifier，只能修改判定標準這一層（criteria、evidence_requirements、score_rules 之類）。每次改動都被限制在局部、可控的範圍。

實際跑起來的規模也值得記一下：28 個任務總共只跑了 94 輪演化，平均每個任務 3.36 輪，最少 3 輪、最多才觸頂 6 輪。換句話說，多數任務的初版 rubric 品質本來就不差，小修小補就收斂了。

這裡有個論文沒交代清楚的地方：這 15 條軌跡（10 校準 + 5 驗證）到底怎麼生成的？是同一題用不同 temperature 重跑、同一個任務家族下的不同實例、還是換不同 agent backend？全文沒有明講。附錄的任務表顯示每個任務家族底下有多個 instance，暗示軌跡池可能包含不同題目實例，但這是推論，不是論文說的。

### Validation Gate 不是「評審中的評審」

直覺上，要比較舊版和候選版 rubric 誰比較好，好像得再設計一個 LLM 當「評審中的評審」。實際機制不是這樣。

它做的是：**同一套 judge、同一個 LLM、同一批驗證軌跡，只換規則版本，然後用程式碼去比較兩份輸出的差異**。概念上更接近 A/B test，而不是疊一層新的評審上去。

```
驗證軌跡 Ut（5 條）
    ├──→ 套「舊版 rubric」跑 Judge Prompt → 結構化 JSON
    └──→ 套「候選版 rubric」跑同一套 Judge Prompt → 結構化 JSON
                    ↓
    程式碼（非 LLM）機械式比對兩份 JSON：
      有幾個 key step 引用了有效證據？
      process 分數的方向跟 verifier 的 pass/fail 一不一致？
      有沒有「沒證據卻判 completed」這種違規？
                    ↓
            算出 ∆H（hard gate）與 ∆Q（soft objective）
```

候選版本要被接受，得同時滿足四個條件：

1. **Hard gate 不能退步**：不能出現破壞性行為——沒證據卻給分、忽略干擾項、刪掉關鍵步驟、繞過 verifier。這些都能機械化偵測。
2. **Soft objective Q 的改善要超過閾值 ε = 0.2**（與前面 F1 式子裡的 ε 無關）：Q 由證據覆蓋率、證據品質、reflection 證據紮實度、process 分數與 verifier 的一致性、規則精簡度組成。
3. **要有實質改善**：不能只是「judge 變得比較有信心」，必須有實際變化，例如證據覆蓋率提升要過 0.02、維度分數提升要過 0.01。
4. **patch 本身沒有結構性違規**：沒有偷改 `key_steps`、`score_weights`，也沒刪掉整個維度。

Q 的精確公式論文沒有給，只列了它包含哪些子項。其中「evidence quality」「reflection grounding」這兩項究竟是純機械統計（例如數證據引用次數）算出來的，還是背後也讓 LLM 給了品質分，全文沒有交代——這對於「這套機制到底有多少是可重現的程式邏輯」是個關鍵細節，可惜缺了。

**另外有個容易搞混的東西**：論文裡確實存在一個真正的 judge-of-judge，但那是**離線的、一次性的驗證研究**，跟上面的 validation gate 是兩回事。它拿演化前的 `R⁰` 和演化後的 `R^best`，找一個獨立的 LLM 去跟人工標註的 gold reference 比對：

| 指標 | R⁰ | R^best |
|---|---|---|
| gold-keypoint coverage | 71.56 | 83.70 |
| usability | 81.53 | 94.33 |
| hallucination rate | 2.00 | 0.00 |
| filtering consistency | 82.00 | 96.00 |

這組數字證明演化後的 rubric 品質確實變好了，但它不是每輪演化都跑的東西，只是拿最終結果去做一次外部體檢。

## 五、關鍵實驗結果

### 5.1 用過程分數篩訓練資料，比只看結果好

這是全篇最重要的證據。在 Gold + Distractors（正確技能中混入干擾技能）設定下訓練 Qwen3.5-4B 與 9B，最終正確率（%）如下：

| 訓練資料的篩選方式 | 4B | 9B |
|---|---|---|
| Base（沒訓練） | 8.0 | 14.0 |
| Outcome-only SFT（只挑 verifier 通過的軌跡） | 6.0 | 18.0 |
| 用 `R⁰` 篩選 | 16.0 | 28.0 |
| 用 `R^best` 篩選 | **24.0** | **32.0** |

最刺眼的是 4B 那一格：只看結果去篩訓練資料，模型從 8.0 掉到 6.0，**訓練反而把它教壞了**。第一節那個「B 軌跡也會被當成好示範學進去」的擔憂，在小模型上直接應驗。

另外兩件事也很清楚。`R⁰`（還沒演化的初版 rubric）就已經大幅贏過 outcome-only，代表光是把過程拆開來評分就有價值；而 `R^best` 又贏過 `R⁰`，代表 rubric 演化本身還有額外的增量貢獻，不是多此一舉。

至於四個維度誰最重要，ablation 給了答案：拿掉步驟遵循（`skill_following`）傷害最大，4B 從 24 掉到 10、9B 從 32 掉到 16；拿掉組合順序（`skill_composition`）也有明顯傷害；拿掉結果反思（`skill_reflection`）影響較小，但仍看得出來。挑訓練資料的時候，「有沒有照步驟做」是訊號最強的那一項。

不過測試集只有 10 個任務家族、50 個 instance，論文也沒有報告這些百分點差異的信賴區間。方向性可以信，具體數字引用時要保守一點。

### 5.2 干擾項邊界分析：技能庫變大之後會怎樣

這節對做系統的人參考價值最高。它問的是：當技能庫規模膨脹、語意相近的技能愈來愈多，模型還選不選得對？

測試方式是讓模型透過一個**類似瀏覽器的多輪互動介面**去探索技能庫——`list` 列出候選、`search` 搜尋、`read` 讀內容、`final` 輸出選定技能或放棄——而不是把所有候選技能一次塞進 context window。這個設計刻意把「技能選擇」這個能力單獨抽出來測，不跟工具呼叫失敗、環境錯誤混在一起。

要提醒的是，論文沒說 `search` 底層是關鍵字搜尋還是語意檢索；如果是後者，代表模型過程中其實有輔助工具幫忙縮小範圍，對「模型判斷力有多強」的解讀就要打點折扣（這是我的推論，不是論文明講的）。

同一套機制、不同的技能庫規模，量出兩條邊界：

- **Degradation boundary**（F1 第一次掉超過 0.10 且回不去）：Gemini 3.1 Pro 大約在 45–46 個干擾項、GPT-5.5 約 55–56 個、Opus 4.7 撐到 194–195 個。
- **Collapse boundary**（80% 的樣本選不到任何 gold skill）：DeepSeek V4 Flash 在 6.4k–6.5k 崩潰、Kimi K2.6 在 20k–21.25k、Gemini 3.1 Pro 在 35k–35.5k；GPT-5.5 和 Opus 4.7 測到 5 萬個干擾項都還沒崩。

（模型名稱依論文原文照抄：這裡標的是 DeepSeek V4 Flash，下面那張相似度表格標的是 DeepSeek V4。）

數量之外，還有個更實用的發現：**干擾項的語意相似度比數量更致命**。固定 50 個干擾項，只換干擾項的類型，技能選擇的表現是這樣：

| 模型 | 隨機無關的干擾項 | 高相似度的干擾項 |
|---|---|---|
| GPT-5.5 | 0.84 | 0.59 |
| Opus 4.7 | 0.87 | 0.71 |
| DeepSeek V4 | 0.70 | 0.46 |

50 個明顯無關的技能幾乎不構成威脅，但同樣是 50 個、換成語意高度相似的，分數直接掉三成上下。放到實務場景就是：真正會害你誤選的，不是那些一看就無關的技能，而是「不同部門的相似合規檢查腳本」「同一份報表流程的舊版本」這種近鄰。

## 六、這篇論文的定位，以及可以帶走的東西

先說一件公道話：**「過程監督比結果監督更適合當篩選訊號」這個原則，不是這篇論文發明的**。在 RLHF 和數學推理的 process reward model 文獻裡，這早就是成熟共識，論文自己在 Related Work 也承認站在這條線上。

它真正的貢獻是把這個已知原則**工程化、自動化**，並綁到「企業技能庫」這個具體場景：rubric 不需要大量人工逐步標註，而是能從真實 rollout 自己演化出來。如果你已經熟悉 process reward 這條文獻，這篇論文對你的邊際價值主要就集中在兩塊——rubric 自動演化的機制設計，以及技能選擇在大規模技能庫下的失效邊界分析。

以下幾點則是脫離這篇論文也還站得住的觀念：

**驗證證據的乘法設計，是個可以直接搬走的 pattern。** 判斷「某件事有沒有完成」時，「宣稱完成」和「有可見證據支持」應該用乘法而不是加法結合（`ck * mk`），任一項為零就整項歸零。這不限於 agent 技能評估——任何拿 LLM 當 judge 的場景，都需要一個機制擋掉「靠自我宣稱拿分」。

**設計技能檢索或路由系統時，抗性測試不能只測數量。** 語意近鄰才是誤觸發的主要來源，測試集裡一定要放進去。

**Degradation 與 Collapse 是兩種失效訊號，對應的解法不同。** 效能開始下滑，代表該優化檢索、排序、候選過濾；效能幾乎完全失效，代表技能庫規模已經超出模型可靠判斷的範圍，光調排序救不回來，得換架構——例如先用檢索大幅縮小候選集，而不是讓模型直接面對整個庫。

**要驗證新舊版評分規則誰好，不一定要疊一層新的評審。** 同一套 judge、同一批資料、只換規則版本，再用可計算的機械指標比較輸出差異，這比另外設計一個 judge-of-judge 更輕量也更可控。（論文裡也保留了一個真正的 judge-of-judge，但用途不同：那是離線的最終體檢，不是線上的接受判準。）

## 結論

SkillCoach 想解決的是一個很實際的落差：verifier 說「過了」，不代表 agent 真的會用技能。它的處理方式是把執行過程拆成技能選擇、步驟遵循、組合順序、結果反思四個維度分開打分，最重的技能選擇交給規則機械判定，其餘三項讓 LLM judge 判但強制引用證據，外部 verifier 則全程獨立保留。

最有說服力的一組數據是訓練資料篩選：只看 verifier 是否通過去篩，4B 模型反而從 8.0 退步到 6.0；改用過程分數篩，同一個模型跳到 24.0。這直接說明了一件事——把「結果對」當成「示範好」，代價是真的會付出來的。

至於它的限制也不必迴避：測試集規模偏小又沒有信賴區間、Q 的計算公式沒公開、軌跡池怎麼生成沒交代。加上核心的過程監督原則本來就是既有共識，讀的時候把「這篇獨創的」和「站在已知結論上的應用」分開看，會比較準確。
